# 企业级测试框架架构评审 —— 总览与结论

> 评审视角：资深测试架构师
> 评审对象：`Automation_WebUI_Framework_BDD`（HSBC CMB DBB HK WebUI 自动化框架）
> 评审方式：**纯代码实证**——以源码、POM、CI 配置、门禁配置为唯一依据，不参考仓库内既有 `*.md` 说明文档
> 评审日期：2026-09-08

---

## 一、一句话结论

> **这是一个"技术深度超标、工程基建欠账"的框架。**
> 核心引擎（route）与报告（reporting）的设计密度达到甚至超过企业级平均水准；但 **CI 不存在、依赖治理失效、质量门禁形同虚设** 三大基础设施短板，使其**当前不具备企业级准入资格**。
>
> 综合评级：**2.9 / 5.0 —— 部门级优秀框架，尚未达到企业级平台标准**。

## 四、全局性致命问题（P0，跨模块）

### P0-1｜CI/CD 完全缺失 —— 全部门禁从未被执行
- **证据**：`.github/workflows/` 下仅有 2 个文件——`doc-drift-check.yml`（仅比对 README 与 POM 版本号）、`serenity-report-push.yml`（手动触发部署报告）。**没有任何 workflow 执行 `mvn verify` 或 `mvn test`**。
- **连锁后果**：根 POM 中配置的 Checkstyle、SpotBugs、JaCoCo、OSV-Scanner 四道门禁，全部绑定在 `verify` 阶段，**在 CI 中从不触发**。门禁只在开发者本地手动执行 `mvn verify` 时才可能生效。
- **判定**：这是**一票否决级**缺陷。企业级框架的首要特征是"质量约束自动化执行"，当前所有门禁均为"自愿遵守的君子协定"。

### P0-2｜依赖治理失效 —— 父 POM 的 `<dependencies>` 被全量继承
- **证据**：根 `pom.xml:82-269` 使用 `<dependencies>`（**非** `dependencyManagement`）声明 40+ 外部依赖，注释自陈"子模块继承"。`core/pom.xml` 声明 **0 个** `<dependency>`，却因此获得 Playwright、Serenity 全家桶、Selenium、HikariCP、jieba、pinyin4j、axe-core 的完整 classpath。
- **实证**：`core` 模块的 `ConfigSource.java:4` 直接 `import net.thucydides.model.environment.SystemEnvironmentVariables` —— 最底层模块**编译期强耦合 Serenity**，架构地基已被污染。
- **后果**：① 模块边界名存实亡（任何模块可误用任何依赖）；② 无法做依赖收敛；③ 制品体积与 CVE 暴露面无谓放大；④ `framework-core` 无法被非 Serenity 项目复用。

### P0-3｜共享 Browser 模式并发竞态（数据正确性风险）
- **证据**：`web/.../PlaywrightManager.java` 类注释（第 82 行）明确声明"共享模式下必须使用进程级 `SHARED_BROWSER_LOCK`，per-thread 锁无法跨线程互斥"，并已提供 mode-aware 的 `browserLock()`（632-634 行）。但第 **690** 行（`getBrowser()`）与第 **742** 行（`handleBrowserTypeSwitch()`）**实际调用的是 `perThreadBrowserLock()`**。
- **后果**：共享模式并发下双线程各自持锁 → 同时进入 `initializeBrowser()` → Browser 双发射、旧实例泄漏、Playwright 子进程未回收。属于**已识别但未修复**的已知缺陷（注释写了正确方案，代码未采用）。

### P0-4｜API 配置跨 Scenario 串扰
- **证据**：`api/.../ConfigProvider.java:61,213` —— `config(Entity)` 方法虽为 `synchronized`，但将结果写入**全局** `volatile Config config` 字段。类注释（56-59 行）自认"并行 scenario 会互相覆盖配置"。
- **后果**：并发执行 API 用例时，线程 A 的 entity 配置可能被线程 B 覆盖，导致**间歇性、不可复现的失败**——这是测试框架最危险的失效模式（信任崩塌）。

### P0-5｜断言失败可能不置用例失败（静默漏测）
- **证据**：`route/.../HandlerExecutor.java:261-267` —— 捕获 `ApiAssertionException` 后仅 `LOGGER.error` + 置 fail-fast 标志，**不 rethrow**，也未确认接入 Serenity 失败上报链路。
- **后果**：接口断言失败可能只落日志与报告，而**用例仍标记为 PASS**。静默漏测在金融级测试体系中是不可接受的风险。

## 六、值得肯定的设计（应保留并推广）

评审不能只挑毛病。以下设计**达到或超过企业级平均水准**，是后续重构应保留的内核：

1. **✅ route 模块的规则引擎设计**（`RouteHandleType` 单一定义优先级/执行序/终止性；`PriorityPolicy.selectCapability` 单一裁决点；`WeakHashMap` 弱键防泄漏；per-context 引擎隔离）—— 全项目技术密度最高，可作为其他模块的架构范式。
2. **✅ 安全工程**：`ConfigCipher` 采用 **AES-256-GCM**（非自造算法），主密钥走 `CONFIG_MASTER_KEY` 环境变量；`SensitiveDataSanitizer`（927 行）在 DB / File / Record / 日志 / 报告 5 处统一收口脱敏；报告文件 600 权限。**全项目零硬编码凭据**（已全量 grep 验证）。
3. **✅ reporting 的 Golden Test 策略**：逐字节比对 + 确定性设计（钉死 project.name / startTime / 路径时间戳）+ **基线缺失即 fail（防假绿）** + ArchUnit 固化与 route 解耦。这是报告类代码测试的最佳实践。
4. **✅ 架构即代码**：`ArchitectureTest` 用 ArchUnit 落地 7 条分层约束（L1-L5 + C1 + G1），并包含 API 边界门禁（禁止业务代码使用 `BasePage.by*` 内部定位器工厂，防类型泄漏）。
5. **✅ 崩溃恢复有界**：`BrowserCrashGuard` 重跑严格限 1 次 + 进程级单飞锁，不会无限循环。
6. **✅ 并发基础设施意识**：`AsyncPool` 提供队列/线程使用率阈值告警、有界队列、`DiscardOldestPolicy` 防反压、`getStatusSnapshot()` 集中监控——具备生产级可观测性雏形。
7. **✅ 统一关闭编排**：`ShutdownCoordinator` 将散落的 `addShutdownHook` 收口为单一有序钩子（ORDER 100→900），解决 JVM 退出顺序不确定问题。

## 八、整改路线建议（三期）

### 第一期：止血（P0，2–3 周）
目标：让质量约束**真正自动执行**，修复 3 处数据正确性缺陷。
- 建立 CI（build + test + 全门禁）
- 修复 P0-3 共享 Browser 锁、P0-4 api 配置串扰、P0-5 断言不上报
- 父 POM 依赖下沉至 `dependencyManagement` ✅ 已完成（ENG-P0-2：根 `<dependencies>` 移入 `dependencyManagement`，7 模块显式声明实际依赖）

### 第二期：固本（P1，4–6 周）
目标：门禁真实生效，架构边界可机器校验。
- Checkstyle 规则扩充 + 全量源码覆盖；JaCoCo 阈值门禁；CVE 基线清理（至少清零 CRITICAL）
- ArchUnit 补齐模块级（非包级）依赖规则，检出 route→web
- 统一配置体系；拆分 test-automation（框架自测回归各模块）

### 第三期：提质（P2，持续）
- 上帝类拆分（PlaywrightManager / BasePage / FrameworkConfig）
- 引入 DI seam 提升可测试性，补齐单测至 40%+ 行覆盖
- codegen 改用模板引擎 + 冲突检测；包名与模块对齐
