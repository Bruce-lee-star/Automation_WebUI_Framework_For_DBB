# 01 总体分层架构与依赖治理

> 评审基线：`e11a847` · 技术栈 JDK21 / Playwright 1.62 / Serenity BDD 4.2.0 / Cucumber 7.31 / JUnit 5 / Maven 多模块
> 评审日期：2026-09-12

---

## 一、模块职责

父 POM（`Automation_WebUI_Framework_BDD:1.0.0`）承担版本钉定、插件编排与质量门禁；7 个子模块按"能力栈"纵向切分，依赖方向收敛为 DAG：

```
core ← reporting / api ← web ← route ← test-automation
                          ↑
                       codegen
```

| 模块 | 职责 | 源文件量级 |
|---|---|---|
| core | 框架内核：配置解析、测试上下文、日志脱敏、断言、异步池、关闭编排 | ~38 java |
| reporting | Serenity 结果适配 + FreeMarker 二次汇总报告 | 7 java + 8 ftlh |
| api | RestAssured/SerenityRest 封装的 REST 测试能力 | 30 java |
| web | Playwright 生命周期、PageObject、定位、截图、监听、无障碍、云 | ~160 java |
| codegen | 运行时 DOM 扫描生成带注解的 Page 源码 | 27 java |
| route | 基于 Playwright `route` 的 API 流量拦截/录制/回放与监控 | 57 java + 5 sql |
| test-automation | feature、步骤定义、Runner、配置与数据 | 155 java + 16 feature |

## 二、现状评估

### 2.1 依赖治理（做得好的部分）

`ENG-P0-2` 已完成依赖下沉：父 POM 只保留 `dependencyManagement`，各子模块显式声明真实用到的依赖。这一条是整个工程最扎实的基建——模块边界可以在 pom 里直接读出来，而不是靠"父 POM 全量继承"的黑盒。

`maven-enforcer-plugin` 启用 `requireUpperBoundDeps` + `banDuplicatePomDependencyVersions`，配合大量中文注释说明每个版本钉定的原因（如 byte-buddy 1.17.8 覆盖 serenity 父 POM 的 1.14.18），说明团队**踩过坑并留下了决策记录**，这在同类框架里少见。

### 2.2 门禁现状（名不副实）

| 门禁 | 配置位置 | 实际强度 |
|---|---|---|
| Checkstyle | 父 POM `verify`，`includes=**/framework/**`，`includeTestSourceDirectory=false` | **极弱**：`checkstyle.xml` 全文只启用 1 条规则 `EmptyCatchBlock` |
| SpotBugs | 父 POM `verify`，`threshold=Medium`，`includeTests=true` | 中：有基线冻结文件，新增违规硬失败 |
| Enforcer | `validate` 默认阶段 | 强：`requireUpperBoundDeps` 真实生效 |
| OSV CVE | 父 POM `verify`，`inherited=false` | 弱：依赖本地二进制，缺失即跳过 |
| ArchUnit | 仅 2 个测试类 | 弱：只覆盖 reporting↔route、web↔codegen 解耦 |

### 2.3 构建生命周期（存在反模式）

父 POM 把 `maven-install-plugin` 绑到 `package` 阶段，目的是让 `verify` 阶段的 OSV 扫描能解析兄弟模块：

```xml
<execution>
  <id>install-modules-for-sca</id>
  <phase>package</phase>
  <goals><goal>install</goal></goals>
</execution>
```

后果：**每一次 `mvn package/test` 都会把 7 个模块写进本地 `.m2`**。开发机本地仓库被快照污染、CI 并行构建存在写同一 GAV 的竞态、且构建耗时无谓增加。这是典型的"为了一个门禁，牺牲整个构建模型"。

### 2.4 版本管理的文档漂移

`pom.xml` 中 `junit.platform.version=1.14.0`，但紧邻注释仍写着"launcher/suite 维持 `${junit.platform.version}`=1.11.4（离线仓库无 1.14.0）"；同时 `junit-platform-engine`/`commons` 又硬编码 `1.14.0` 字面量而非引用属性。**值与注释矛盾、字面量与属性混用**，后续升级极易再次踩坑。

### 2.5 工程卫生

- 根目录 `1.txt`（1.7 MB）是一次 Maven 构建日志，已 gitignore 但未清理。
- `.playwright/browsers/` 落在工程根（Firefox/Chromium 二进制），虽已 gitignore，但会被 IDE 索引、备份工具扫描。
- `core/common/action`、`core/common/env`、`core/common/persistence` 是**空目录**，`core/utils` 包**不存在**。目录结构与实际能力不符，会误导新人。

## 三、优势

1. **物理多模块 + 单向依赖**：DAG 无环，并用 SPI（如 `common.route.RouteLifecycle`、`codegen.spi.RoleCodegenBridge`）做依赖倒置打破潜在环路，架构自觉性高于平均水准。
2. **依赖版本决策可追溯**：大量"为什么钉这个版本"的注释，把踩坑经验固化在构建脚本里。
3. **JDK 强封装适配到位**：surefire/failsafe 的 `--add-opens` 覆盖 `java.lang`/`java.lang.reflect`/`java.util`，且用 `@{jacocoArgLine}` 做属性晚绑定，说明对 JDK16+ 模块化有实操经验。
4. **关闭编排统一**：`ShutdownCoordinator` 单点管理 JVM 钩子，带 order 排序与幂等。

## 五、优化方案

### 5.1 让 Checkstyle 真正成为门禁（P0）

当前规则集只有 1 条，直接补到"能拦住真实问题"的量级。建议分两期：先上**低噪声、高价值**规则，避免一次性引入上千违规。

```xml
<!-- checkstyle.xml：TreeWalker 内补充 -->
<module name="TreeWalker">
  <module name="EmptyCatchBlock"/>
  <!-- 第 1 期：零争议 -->
  <module name="NeedBraces"/>
  <module name="EqualsHashCode"/>
  <module name="MissingOverride"/>
  <module name="UpperEll"/>
  <module name="ArrayTypeStyle"/>
  <!-- 第 2 期：配合基线文件渐进启用 -->
  <module name="LineLength"><property name="max" value="140"/></module>
  <module name="MethodLength"><property name="max" value="120"/></module>
  <module name="CyclomaticComplexity"><property name="max" value="15"/></module>
  <module name="IllegalCatch"><property name="illegalClassNames" value="java.lang.Throwable,java.lang.Error"/></module>
</module>
```

执行策略：先用 `checkstyle:check -Dcheckstyle.violationSeverity=warning` 出全量报告，把存量违规写入 `checkstyle-baseline.xml`（`suppressionsFile`），**基线只允许减少不允许增加**，并在 CI 加一条"基线文件行数不得增加"的校验。

### 5.2 移除 install 反模式，改用 reactor 内扫描（P0）

OSV 扫描需要的只是"能解析 `framework-*` 的 GAV"，不必真 install。两种改法：

```xml
<!-- 方案 A（推荐）：OSV 直接用 -r 递归扫目录，靠 lockfile/pom 自解析；
     兄弟模块未发布时通过 --experimental-actions 或预先 mvn install -DskipTests 一次性准备 -->
<execution>
  <id>osv-scanner-cve-gate</id>
  <phase>verify</phase>
  <inherited>false</inherited>
  <configuration>
    <skip>${cve.gate.skip}</skip>
  </configuration>
</execution>
```

```xml
<!-- 方案 B：把 install 从 package 挪到独立 profile，只在需要 SCA 时显式开启 -->
<profiles>
  <profile>
    <id>sca</id>
    <build>
      <plugins>
        <plugin>
          <artifactId>maven-install-plugin</artifactId>
          <executions>
            <execution>
              <id>install-modules-for-sca</id>
              <phase>package</phase>
              <goals><goal>install</goal></goals>
            </execution>
          </executions>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>
```

CI 侧：`mvn -B -Psca verify` 才触发安装 + 扫描，日常 `mvn test` 完全不碰 `.m2`。

### 5.3 补齐 ArchUnit 分层门禁（P1）

把现有 2 个解耦测试扩展为**全模块分层规则**，作为 `core` 模块的测试（依赖最少，天然适合放架构测试）：

```java
@AnalyzeClasses(packages = "com.hsbc.cmb.hk.dbb.automation.framework",
                importOptions = ImportOption.DoNotIncludeTests.class)
class LayeringArchTest {

    @ArchTest
    static final ArchRule coreMustNotDependUpward =
        noClasses().that().resideInAPackage("..framework.core..")
            .should().dependOnClassesThat().resideInAnyPackage(
                "..framework.web..", "..framework.route..", "..framework.api..");

    @ArchTest
    static final ArchRule routeMustNotDependOnWeb =
        noClasses().that().resideInAPackage("..framework.route..")
            .should().dependOnClassesThat().resideInAPackage("..framework.web..");

    @ArchTest
    static final ArchRule noCycles = slices()
        .matching("com.hsbc.cmb.hk.dbb.automation.framework.(*)..")
        .should().beFreeOfCycles();

    @ArchTest
    static final ArchRule noJunit4 =
        noClasses().should().dependOnClassesThat()
            .haveFullyQualifiedName("org.junit.Test")
            .because("JUnit 5 迁移已完成，禁止回退到 JUnit 4");

    @ArchTest
    static final ArchRule noThreadSleepInFramework =
        noClasses().that().resideInAPackage("..framework..")
            .should().callMethod(Thread.class, "sleep", long.class)
            .because("框架层禁止硬等待");
}
```

### 5.4 统一 JUnit Platform 版本（P1）

```xml
<properties>
  <!-- 单一事实来源，注释与值必须一致 -->
  <junit.platform.version>1.14.0</junit.platform.version>
</properties>
<!-- engine/commons 改为引用属性，不再硬编码 -->
<dependency>
  <groupId>org.junit.platform</groupId>
  <artifactId>junit-platform-engine</artifactId>
  <version>${junit.platform.version}</version>
</dependency>
```

同时删除或修正"离线仓库无 1.14.0"的过期注释——过期注释比没有注释更危险。

### 5.5 清理结构噪声（P2）

- 删除 `core/.../common/{action,env,persistence}` 空目录；确认 `utils` 是否已在重构中迁移（实际落点在 `web/.../utils/NlsNameTranslator.java`），若是则同步更新文档。
- 把 `1.txt` 删除；`.playwright/` 通过环境变量 `PLAYWRIGHT_BROWSERS_PATH` 指到工程外（如 `~/.cache/ms-playwright`）。
- 在 `.gitignore` 增加 `docs/architecture-review/*.tmp` 之类无关条目不必改，但应补 `*.iws`、`.m2/` 已存在无需动。

## 六、结论

分层骨架（DAG、SPI 倒置、依赖下沉）是这套框架最值钱的资产，方向正确且执行到位。真正的短板在**门禁的"名义强度"与"实际强度"严重脱节**：Checkstyle 只有 1 条规则、ArchUnit 只有 2 个测试、CVE 门禁在 CI 上静默跳过。修好这三处，架构防腐成本会下降一个数量级。
