# 09 测试数据与多环境配置

> 评审范围：`test-automation/src/test/resources/**`（config / payload / mocks / nls）、`serenity.conf`、`serenity.properties`、`application.conf`、`routedemo.conf`
> 评审基线：`e11a847`

---

## 一、模块职责

为用例提供三类输入：环境配置（URL / 浏览器 / 凭据）、业务静态数据（payload / mock / 多语言字典）、以及动态造数（目前主要靠 route-demo-service 后端）。

---

## 二、现状评估

### 2.1 配置源四分天下

| 文件 | 职责 | 证据 |
|---|---|---|
| `serenity.conf` | 浏览器启动参数、环境 URL、用户凭据 | `:29-111` 浏览器、`:114-118` environment、`:123-145` userinfo |
| `serenity.properties` | 框架行为（截图、超时、代理、BrowserStack、axe、报告 URL、错误分类） | `:25` 截图、`:48-69` 超时、`:157` axe、`:183` 报告 URL、`:200` 错误分类、`:208` BrowserStack |
| `application.conf` | Typesafe Config：路径 / HTTP / API base.uri | `:8-75`，`base.uri=localhost:8080` |
| `routedemo.conf` | demo service 地址 | `:10-18`，`base=localhost:8888` |

四者职责边界**在文件头注释里写清楚了**（`serenity.conf:1-7` 明确分工），这点值得肯定。但：

- 前两者由 Serenity 的 `SystemEnvironmentVariables` 合并读取，后两者由 Typesafe Config 读取，**是两套完全独立的解析机制**；
- 取值优先级（系统属性 vs 文件 vs 环境变量）没有一处文档说明；
- 新增配置项时，开发者必须自己判断"该放哪个文件"。

### 2.2 多环境切换

`serenity.conf:114-118` 定义三套环境：

```hocon
environment {
  O63_SIT1 : "https://www.qualityassurance-amh-gbb-sit.p2g.netd2.hsbc.com.hk/portalserver/logon"
  O38_SIT2 : "https://qualityassurance-amh-gbb-sit2.p2g.netd2.hsbc.com.hk/portalserver/logon"
  O88_SIT3 : "https://qualityassurance-amh-gbb-sit11.p2g.netd2.hsbc.com.hk/portalserver/logon"
}
```

凭据按环境前缀分组：`userinfo_O63` / `userinfo_O38` / `userinfo_O88`（`:123-145`）。

**问题**：
1. **没有 profile 机制**。Maven 侧只有 `shared-browser-e2e` 一个 profile（`test-automation/pom.xml:289`），**没有按环境切分的 profile**。切环境靠什么？没有明确入口——core 模块里也找不到环境选择器（见 02 文档 C-6）。
2. 环境命名 `O63_SIT1` / `O38_SIT2` / `O88_SIT3` 是内部代号，无语义。
3. `application.conf:8-75` 里 `ssl.relax-validation=true` 是**全局默认值**，意味着本地跑也可能放宽 SSL 而不自知。

### 2.3 凭据存储（高危）

```hocon
# serenity.conf:120-121（注释）
# 测试凭据加密说明：password 以 ENC(...) 密文存储（由 common.security.ConfigCipher 生成，AES-256-GCM 绑定本地主密钥）；
# 也可不加 ENC(...) 包裹，裸 base64 密文同样会被 `SecretValue` 透明解密（双格式均支持，且同样绑定主密钥）。
# 密文形态但解密失败（key 不匹配/密文损坏）→ 失败快（抛 IllegalStateException）；仅明显非密文形态（非 base64 或长度过短）才原样返回。
# 默认严格：不配置 security.secret.strict 即不降级；仅排障可临时设 -Dsecurity.secret.strict=false。
# 本地运行时需设置主密钥：CONFIG_MASTER_KEY=00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff
# 生产/CI 请改用自有主密钥重新 encrypt，切勿将真实主密钥提交入库。

# serenity.conf:125（实际）
password: "b3g3ifd"
```

**三个问题叠加**：

1. **注释声明用 `ENC(...)` 密文，实际是明文**（`:125`、`:133`、`:142` 三处）。
2. **主密钥示例值写在注释里**（`:121`）。虽然注释说"切勿提交真实主密钥"，但这串 64 hex 会被误认为是可用密钥（且 `ConfigCipher` 的第二段来源是 `config.master.key` 系统属性，任何人配上这串就能解密）。
3. **`token.security.url` 内嵌明文 `username=...&key=...`**（`:127`、`:135`、`:143`）——这是**获取 OTP 的接口地址和密钥**，比密码本身更敏感。

**判定**：框架的加密能力（AES-256-GCM，见 02 文档）是齐备的，但**没有真正用起来**。这是"有能力但未启用"，属于最可惜的一类问题。

### 2.4 测试数据

| 类型 | 文件 | 特点 |
|---|---|---|
| 请求体 | `payload/api-demo-login-valid.json` 等 4 个 | 静态，如 `{"username":"admin","password":"password123"}` |
| Mock 响应 | `mocks/login-response.json`、`mocks/users.json` | 静态，`"token":"real-token-from-file"` 是占位假值 |
| 多语言字典 | `nls/NLS_idv_logon.json`、`nls/NLS_footer.json` | 静态，驱动 `@RoleElement` 定位 |
| 动态造数 | route-demo-service 后端 | 由 glue 的 `@Before` 写真实数据 |

**问题**：
1. **没有数据工厂/Builder**（全仓 grep `Builder|Factory|PayloadFactory`，只有 `PageObjectFactory` / `ConfigFactory` / `HikariConfigFactory`，无测试数据构造器）。多场景需要变体数据时只能复制 JSON 文件。
2. **用例间存在隐式数据依赖**：`RouteDemoCompositeGlue.java:16,30` 的 `@Before` 会**真实改动 route-demo-service 的后端列表**，靠 `@Before` 重置来规避污染。这是"A 用例造数据 → B 用例依赖"的隐式耦合，一旦并行执行或某个 `@Before` 漏写，就会互相污染。
3. **静态 JSON 里的密码**（`password123`）虽是测试值，但强化了"明文凭据可以入仓"的坏习惯。
4. **无数据清理的事务性保证**：`@Before` 重置失败会怎样？没有兜底。

## 三、优势

1. **配置文件职责分工写进注释**（`serenity.conf:1-7`），边界清晰。
2. **多语言字典驱动定位**（`nls/*.json`），直接支撑 `@RoleElement` 的多语言能力（见 04 文档）。
3. **凭据按环境前缀分组**（`userinfo_O63/O38/O88`），结构上有扩展性。
4. **加密能力齐备**（`ConfigCipher` AES-256-GCM、三段主密钥来源），启用成本低。
5. **route demo 的 glue 做了 `@Before` 重置**，至少意识到了数据污染问题。

## 五、优化方案

### 5.1 凭据加密落地（P0）

**三步走，缺一不可。**

**第一步：加密现有凭据。** 用框架自带的 `ConfigCipher` 生成密文：

```java
// 一次性工具类（跑完即删，不要留在仓库里）
public final class EncryptCredentials {
    public static void main(String[] args) {
        // 主密钥从环境变量读，绝不硬编码
        String enc = ConfigCipher.encrypt(args[0]);
        System.out.println("ENC(" + enc + ")");
    }
}
```

```bash
export CONFIG_MASTER_KEY=$(openssl rand -hex 32)
java -cp ... EncryptCredentials '实际密码'
```

**第二步：替换配置文件。**

```hocon
userinfo_O63 {
  WP7UAT2_2 {
    password: "ENC(a1b2c3...base64...)"
    profile: "W1-HKHBAP001060698838PUSER1"
    token.security.url: "ENC(...)"     # 整条 URL 一起加密
  }
}
```

**第三步：删除注释里的主密钥。**

```hocon
# 测试凭据：password 与 token.security.url 均以 ENC(...) 密文存储。
# 主密钥通过环境变量 CONFIG_MASTER_KEY 注入（64 hex），CI 中配置在 Secrets 里。
# 严禁将主密钥写入本文件或任何注释。
# 生成密文：mvn -q exec:java -Dexec.mainClass=...ConfigCipherTool -Dexec.args='<明文>'
```

**配套**：`SecretValue` 已默认严格模式（见 02 文档 5.3），解密失败（主密钥缺失/不匹配）在启动即失败快，无需额外开启；仅排障可临时设 `-Dsecurity.secret.strict=false` 降级保留原串。

**另外**：`token.security.url` 这种 OTP 获取接口，建议从配置文件移出，改由 CI Secrets 注入环境变量——它不应该以任何形式（明文或密文）留在仓库里。

### 5.2 建立环境 profile（P1）

```xml
<!-- 根 pom.xml -->
<profiles>
  <profile>
    <id>sit1</id>
    <properties>
      <env.code>O63</env.code>
      <base.url>https://www.qualityassurance-amh-gbb-sit.p2g.netd2.hsbc.com.hk</base.url>
    </properties>
  </profile>
  <profile>
    <id>sit2</id>
    <properties>
      <env.code>O38</env.code>
      <base.url>https://qualityassurance-amh-gbb-sit2.p2g.netd2.hsbc.com.hk</base.url>
    </properties>
  </profile>
</profiles>
```

```xml
<!-- failsafe 注入 -->
<systemPropertyVariables>
  <env.code>${env.code}</env.code>
  <environment>${env.code}_SIT1</environment>
</systemPropertyVariables>
```

CI 编排：`mvn verify -Psit1 -Dtags="@smoke"`。

同时把 `serenity.conf` 里的 `environment` 块拆成 `environment-sit1.conf` / `environment-sit2.conf`，按 profile 激活，**避免所有环境 URL 都堆在一个文件里**。

### 5.3 引入数据工厂（P1）

```java
public final class PayloadFactory {

    public static Payload login(String user, String password) {
        return Payload.of("api-demo-login-valid")
            .with("username", user)
            .with("password", password);      // 值来自 SecretValue，不落盘
    }

    /** 基于模板 + 变体，避免复制 JSON 文件 */
    public static Payload createUser(Map<String, String> overrides) {
        return Payload.ofTemplate("api-demo-create-user", overrides);
    }

    /** 随机化，保证用例间数据不冲突 */
    public static Payload uniqueUser() {
        return createUser(Map.of(
            "username", "user_" + UUID.randomUUID().toString().substring(0, 8),
            "email",    "u" + System.nanoTime() + "@test.local"));
    }
}
```

**关键改进**：`uniqueUser()` 生成的唯一数据让用例之间**天然不冲突**，比"靠 `@Before` 重置"可靠得多。

### 5.4 消除用例间数据依赖（P1）

从"重置共享数据"改为"每个用例用自己的数据"：

```java
// 反例（现状）：A 用例写后端列表，靠 @Before 重置
@Before public void reset() { demoClient.resetUsers(); }

// 正解：每个用例用唯一数据集，互不干扰
@Before
public void prepareOwnData(Scenario scenario) {
    String namespace = "s" + Math.abs(scenario.getId().hashCode());
    TestDataScope.begin(namespace);            // 与 02 文档 ScenarioContext 联动
    demoClient.createUser(PayloadFactory.uniqueUser());
}

@After
public void tearDownOwnData() {
    demoClient.deleteByNamespace(TestDataScope.current());
    TestDataScope.end();                        // 只删自己的，不影响别人
}
```

这样即使并行执行也不会互相踩踏，且不再依赖"重置成功"这个前提。

### 5.5 配置源收敛（P2）

**目标：把四套收敛为"两源一入口"。**

```
serenity.properties   ← 框架行为（保持不变，Serenity 原生）
environment-{env}.conf ← 环境相关（URL + 凭据，按 profile 激活）
application.conf       ← 应用/API 侧（保留 Typesafe Config）
```

删除 `routedemo.conf`（并入 `application.conf` 的 `routedemo { }` 块）。在 `serenity.conf` 头部写明完整优先级链：

```
系统属性 > 环境变量 > -Pprofile 指定的 environment-*.conf > serenity.conf > 默认值
```

并把 `ssl.relax-validation` 默认值改为 `false`，只在本地 profile 里显式开启。

## 六、结论

这一块的核心判断是：**加密能力建好了，但没有启用**。`ConfigCipher` 的 AES-256-GCM 实现、三段主密钥来源、带校验位的脱敏器都是高水准的，可配置文件里躺的还是明文密码，注释里还写着主密钥样例——**安全水位取决于最短的那块板**。

D-1 / D-2 / D-3 三项的修复工作量不到半天（加密现有值 + 改注释 + 配置 CI Secrets），却是从"看起来安全"到"真的安全"的跨越，应当列为第一优先级。

数据层面，从"重置共享数据"转向"每用例唯一数据"（D-6）是并行化的前置条件——不解决这个，10 号文档的并发改造无法落地。
