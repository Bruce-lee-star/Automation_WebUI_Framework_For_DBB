## 四、新增发现（N-1 ~ N-12）

### N-1｜`ROUTE-P1-N1` — 数据库方言识别与 DDL 实现不匹配（P1）

- **位置**：`route/.../route/persistence/ApiMonitoringRepository.java`
- **证据**：`detectDialectFromUrl()` 可返回 `MYSQL / POSTGRESQL / H2 / ORACLE / SQLSERVER` 五种；而 `buildDdl()` **仅实现了 POSTGRESQL、H2、MySQL(default) 三支**。ORACLE 与 SQLSERVER 会静默落到 MySQL 分支执行 `ENGINE=InnoDB ... MEDIUMTEXT ... COMMENT '...'` 语法。
- **影响**：一旦有人配 `jdbc:oracle:...`，建表必然失败；`init()` 捕获异常后 `initFailed=true` **永久不再重试**，监控数据全程静默丢失（只有一条 ERROR 日志）。
- **建议**：① 未支持的方言在 `init()` 前置校验并 fail-fast，明确报错；② 或改为按方言加载外部 DDL 资源文件。
- **工时**：1.0 人日

### N-2｜`ROUTE-P1-N2` — 数据库 Schema 无版本治理（P1）

- **证据**：表结构由 Java 代码内硬编码 DDL + `CREATE TABLE IF NOT EXISTS` 自动建表（同文件 `ensureTableExists`），无版本号、无迁移脚本、无回滚、无变更审计。
- **影响**：表结构一旦演进，历史库无法升级；**金融级审计要求"结构变更可追溯、可回放"不满足**；`IF NOT EXISTS` 还会掩盖"字段已变更"的事实（旧表缺列 → 插入时才报错）。
- **建议**：引入 Flyway/Liquibase，`V1__init.sql` 起版，DDL 移出 Java；保留 `IF NOT EXISTS` 仅作为本地开发便利。
- **工时**：2.0 人日
- **状态**：✅ 已修复（2026-09-08）。引入 Flyway（`flyway-core` 9.22.3）；DDL 外置为 `route/src/main/resources/db/migration/{mysql,postgresql,h2,oracle,sqlserver}/V1__create_route_monitor_record.sql`（按各库语义对齐：MySQL/PG/H2 保留 `IF NOT EXISTS`，Oracle/SQLServer 依赖基线跳过）；`ApiMonitoringRepository.migrateSchema` 按方言选目录 + `baselineOnMigrate(true)`：新库建表、旧库（已有表无历史）自动基线零丢数据；SUPPORTED_DIALECTS 扩为 5 种（MSSQL→SQLSERVER）。`ApiMonitoringRepositoryE2ETest` 新增 Oracle/SQLServer 方言路由用例；route 及上游编译零报错、E2E 6 例全绿。

### N-3｜`CORE-P1-N3` — ConfigCipher 主密钥校验缺失 + 每次解密重复解析（P1）

- **位置**：`core/.../common/security/ConfigCipher.java`
- **证据**：
  - `hexToBytes()` **只校验偶数长度，不校验必须为 32 字节（64 hex）**。传入 32 hex（16 字节）会静默降级为 **AES-128**；传入 40 hex（20 字节）则 `Cipher.init` 抛 `InvalidKeyException`，被 `SecretValue.tryDecrypt` 的 `catch (Exception)` 吞掉并 **返回原串** → 配置"看似加载成功，实际仍是密文"。
  - `resolveMasterKey()` 每次 `decrypt` 都重新读 env → SystemProperty → **文件 IO**，且无缓存。
- **影响**：① 算法强度可被错误配置静默削弱；② 解密失败静默降级为"使用密文当密码"，认证失败时排查成本极高；③ 高频配置读取存在重复文件 IO。
- **建议**：① `resolveMasterKey()` 强校验 64 hex，否则抛明确异常；② 主密钥解析结果缓存（`static volatile` + 一次性解析）；③ `SecretValue` 解密失败时区分"非密文"与"密文但解密失败"，后者应告警级别提升到 ERROR 并输出 key 名（不含值）。
- **工时**：1.0 人日

### N-4｜`CORE-P1-N4` — `ContextKey` 类型安全被 equals 破坏（P1）

- **位置**：`core/.../core/context/ContextKey.java`
- **证据**：类注释声明"类型安全的上下文键"，但 `equals()`/`hashCode()` **仅基于 `name`，完全忽略 `type`**。而 `ThreadLocalTestContext` 用 `HashMap<ContextKey<?>, Object>` 存储。
- **影响**：两个同名不同类型的 Key（如 `ContextKey.of("x", String.class)` 与 `ContextKey.of("x", Long.class)`）在 HashMap 中**互相覆盖**，`cast()` 处抛 `ClassCastException`——且是**运行期**才炸，编译期无任何提示。类型安全键的设计收益被抵消。
- **建议**：`equals/hashCode` 纳入 `type`；或改为 `enum` 常量定义全部 Key（推荐，兼得编译期唯一性与类型安全）。
- **工时**：0.5 人日

### N-5｜`CORE-P1-N5` — `ShutdownCoordinator` 并发与一次性闩缺陷（P1）

- **位置**：`core/.../common/ShutdownCoordinator.java`
- **证据**：`register()` 是 `synchronized`，但 `runAll()` **遍历 `TASKS` 时无任何同步**；`running` 是一次性 `AtomicBoolean` 闩——`runAll()` 执行过之后再 `register()` 的任务**永不执行**。
- **影响**：① 关闭过程中并发注册 → `ConcurrentModificationException`；② 长驻 JVM / 多套件串行执行（本框架 `SummaryReportGenerator` 注释明确提到"多套件同 JVM 运行"）场景下，第二轮注册的组件不会被清理。
- **建议**：改用 `CopyOnWriteArrayList` 或 `runAll()` 内快照复制；`running` 改为允许"执行后仍可注册并立即补执行"的语义，或提供显式 `reset()`。
- **工时**：0.5 人日

### N-6｜`CORE-P2-N6` — `AsyncPool.getCompletedTaskCount()` 指标重复计数（P2）

- **位置**：`core/.../common/async/AsyncPool.java` L386、L405
- **证据**：`return POOL.getCompletedTaskCount() + completedTaskCount.get();` —— 后者在 `submitTask` 的 `finally` 中对**同一批任务**再次 +1，二者语义重复。
- **影响**：完成数指标虚高约 2 倍，`getStatusSnapshot()` 同步失真 → 容量判断与告警阈值失效。
- **建议**：只保留 `POOL.getCompletedTaskCount()`，自建计数器仅用于监控回调执行器。
- **工时**：0.25 人日

### N-7｜`CORE-P1-N7` — 配置读取存在三套彼此割裂的体系（P1）

- **证据**：
  1. Web 域：`ConfigSource.resolve()` → Serenity `SystemEnvironmentVariables`（serenity.conf / serenity.properties / ENV）
  2. API 域：Typesafe Config（`application.conf` + `ConfigProvider`）
  3. `AsyncPool`：**直接 `System.getenv("ASYNC_*")`**，绕过上述两者
- **影响**：`ASYNC_CORE_THREADS` 等 8 个参数**无法**通过 serenity.conf / serenity.properties / `-D` 系统属性覆盖，也无法走 `ENC()` 加密；运维侧"统一配置入口"的承诺在此处不成立。同一框架内三套配置语义（优先级、类型解析、加密）不一致。
- **建议**：`AsyncPool` 改走 `ConfigSource`；长期目标统一到单一配置门面（`ConfigSource` 为唯一入口，Typesafe 作为 API 域的 provider 挂在其下）。
- **工时**：0.5 人日

### N-8｜`ROUTE-P1-N8` — `codegen` 模块缺失 `spotbugs-exclude.xml`（P1）

- **证据**：根 POM 配置 `<excludeFilterFile>${project.basedir}/spotbugs-exclude.xml</excludeFilterFile>`；实测 core / web / route / api / reporting / test-automation **6 个模块均有**该文件，**唯独 codegen 缺失**。
- **影响**：codegen 的 SpotBugs 行为与其他模块不一致（依赖插件对缺失文件的容错），属"构建配置漂移"；一旦插件版本升级收紧校验即构建失败。
- **建议**：补齐 `codegen/spotbugs-exclude.xml`（可先为空基线）；更好做法是**根 POM 用 `spotbugs.excludeFilterFile` 属性 + 单一共享文件**，避免 7 份副本漂移。
- **工时**：0.25 人日

### N-9｜`WEB-P1-N9` — 全局静态锁导致并行场景串行化（P1）

- **位置**：`web/.../page/base/BasePage.java` L107；`web/.../lifecycle/PlaywrightManager.java` L88-89
- **证据**：`private static final Object PAGE_SWITCH_LOCK = new Object();` —— **所有页面实例、所有线程共享同一把锁**；`PlaywrightManager` 另有 `CONTEXT_LOCK`、`PAGE_LOCK` 两个静态锁。
- **影响**：并行 scenario 下页面切换被**全局串行化**，并发度越高损耗越大；同时多把静态锁 + 99 处 `synchronized` 块构成复杂锁序，`ConcurrentContextNoDeadlockTest` 的存在本身即说明死锁风险真实。
- **建议**：锁对象改为 per-instance 或 per-context；统一梳理锁顺序并形成文档化约定（禁止"持 A 锁求 B 锁"的交叉）。
- **工时**：2.0 人日

### N-10｜`CORE-P2-N10` — `TestContext` 不向子线程传播，与"消灭全局状态"目标自相矛盾（P2）

- **位置**：`core/.../core/context/TestContextHolder.java`
- **证据**：`ThreadLocal.withInitial(ThreadLocalTestContext::new)`，非 `InheritableThreadLocal`。`AsyncPool` 工作线程、Playwright 事件线程、Monitor 回调线程均**取不到父线程上下文**。
- **影响**：`AsyncPool` 类注释已自认——为了让用户回调"影响主线程"，只能把 `NLSUtils` 等状态**重新全局化**。这与 T3-1「消灭静态 ThreadLocal」的目标直接冲突，形成"收拢了又漏出去"的循环。
- **建议**：要么提供显式的上下文传播桥（提交异步任务时捕获并 restore），要么明确承认"异步回调不共享 scenario 上下文"并在文档中禁止依赖。
- **工时**：1.0 人日（方案设计）+ 视传播点数量

### N-11｜`WEB-P2-N11` — `RouteLifecycle` SPI 为 14 方法的胖接口（P2）

- **位置**：`core/.../common/route/RouteLifecycle.java`
- **证据**：单个 SPI 接口聚合了采集控制、场景名管理、注册表清理、引擎停止、URL 脱敏 **14 个方法**；且 `clearContext(Object ctx)` / `stopContextEngine(Object ctx)` 使用 **`Object` 裸类型**。
- **影响**：违反接口隔离原则；任何新实现（含测试桩）必须实现全部 14 个方法；`Object` 参数使类型错误只能在运行期暴露。
- **建议**：按职责拆为 `CaptureControl` / `RegistryControl` / `EngineControl` 三个接口；`Object ctx` 提取为 `RouteContextHandle` 标记接口。
- **工时**：1.0 人日

### N-12｜`CG-P2-N12` — 约 18.5k 字符浏览器 JS 内嵌于 Java 字符串，无 lint / 无测试（P2）

## 七、本轮最优先的 3 件事（若只在本轮增量里挑）

1. **`ROUTE-P1-N1`（1.0 人日）** — 方言不匹配会让整个监控持久化在未知方言上静默失效，且 `initFailed` 后**永不重试**，属"无声数据丢失"。（已修复：Oracle/SQLServer 已纳入 SUPPORTED_DIALECTS 按各自 V1 迁移 SQL 正确建表；仅真正未知方言 fail-fast 退回，杜绝无声丢失）
2. **`CORE-P1-N3`（1.0 人日）** — 主密钥校验缺失可导致加密强度被静默降级到 AES-128，或解密失败后拿密文当密码用；在金融场景下这是**安全基线**问题，建议**提升至 P0** 并优先于一般 P1。
3. **`ROUTE-P1-N2`（2.0 人日）** — Schema 无版本治理是审计项硬伤，越晚做迁移成本越高（表一旦上量，加列需停机）。

## 八、给评审使用方的一句提醒

这个框架最值得警惕的不是"写得不好"，而是**"写得很好但没有网"**：

- 它的核心引擎（route 的 WeakHashMap 防泄漏 / 单一裁决点 / DSL 编译期校验）、报告（Golden Test / 安全 sink）、core（AES-256-GCM / 有序关闭编排）都达到了企业级设计水准；
- 但 **CI 不存在、门禁覆盖 3.2%、框架模块自有单测 6 个文件**——意味着上述优秀设计**没有任何自动化手段防止其退化**。

因此整改的**第一优先级不是重构代码，而是先建 CI 与门禁基线**（`ENG-P0-1`），否则后续 96 个任务都无法被验证是否真的完成。
