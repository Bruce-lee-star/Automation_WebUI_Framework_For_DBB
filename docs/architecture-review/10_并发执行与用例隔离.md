# 10 并发执行与用例隔离

> 评审范围：JUnit Platform / Cucumber 并行配置、`ConcurrentContextExecutor`、上下文与状态的隔离边界
> 评审基线：`e11a847`

---

## 一、现状：一个必须澄清的认知错位

**框架"有并发能力"，但"测试引擎完全串行"。**

证据链：

| 事实 | 证据 |
|---|---|
| 全仓**无 `junit-platform.properties`** | 全量 find 零命中 |
| failsafe `forkCount=1`，无 `parallel` / `threadCount` | `test-automation/pom.xml:178` |
| 并发执行器只能被显式调用的用例使用 | `ConcurrentContextExecutor.runAll:70-121` |
| 只有 2 个 feature 走并发 | `parallel_logon_dbb.feature`、`concurrent_logon_dbb.feature` |
| 并发度默认 4、硬上限 16 | `ConcurrentContextOptions.java:12,56,65` |

**结论**：除了那 2 个专用 feature，其余全部 15 个 feature 都是**严格串行**执行的。`ConcurrentContextExecutor` 提供的是"用例内部的多 Context 并发"，不是"用例之间并行"。

这是一个**预期落差**问题：看到 `ConcurrentContextExecutor`、共享 Browser 模式、锁中介器这些精巧设施，很容易以为套件是并行的。实际不是。

### 串行执行的代价

按当前规模（16 个 feature、DBB 登录类 UI 用例单条 30-60 秒估算），全量回归在 10-20 分钟量级。随着用例增长会线性恶化，而 nightly 回归通常有时间窗约束。

## 二、隔离边界评估

即便当前串行，**隔离机制也必须先修好**——否则一旦开启并行就会爆发出随机故障。逐项盘点：

### 2.1 测试上下文：线程绑定，非用例绑定（C-1，P0）

`ThreadContextRegistry` 是 `WeakHashMap<Thread, TestContext>`，清理依赖上层显式调 `resetForCurrentThread()`。

- 串行：线程复用但每次都 reset，**暂时安全**；
- 并行：多个线程各自持有，只要 reset 到位仍安全，但**任何一处遗漏即串扰**；
- 虚拟线程：线程数量爆炸，`WeakHashMap` 无清理时会累积。

### 2.2 软断言 ThreadLocal（C-4，P1）

`SoftAssertions.FAILURES` 是 ThreadLocal，若 `assertAll()` 未被调用（场景跳过/前置失败），失败会残留到下一个用例。

### 2.3 route 模块进程级单例（R-2 / R-3，P1）

`ApiMonitorOrchestrator.registeredPatterns`（`:33`）与 `ApiCaptureManager.currentStore`（`:42,48,66`）是**进程级共享**，且 `clear()` 无人调用。并行下必然串扰。

### 2.4 测试数据共享（D-6，P1）

`RouteDemoCompositeGlue:16,30` 的 `@Before` 写真实后端数据，靠重置规避污染。并行下重置会互相打断。

### 2.5 语言态全局可变（C-8，P2）

`LanguageState.globalLang` 静态全局。

### 2.6 相对健康的部分

- **Browser 默认每线程独立**（`BrowserRegistryImpl.keyFor:88-99`），隔离性天然好；
- **锁顺序有纪律**（`PAGE_LOCK → CONTEXT_LOCK`），无死锁；
- **`LogonGlue:88` 的 `@After` 释放并发信号量**——说明作者考虑过并发资源限流；
- **`PlaywrightManager.cleanupAll` 在并发模式下主动抛异常防误关**——防御性设计。

## 三、优势

1. **锁顺序有明确纪律**（03 文档 W 部分），自研并发框架中的高水准。
2. **并发执行器支持虚拟线程**，技术选型前瞻。
3. **每线程独立 Browser 模型**（共享 Browser 模式已移除，见 03 文档 W-7），隔离性天然好、线程安全。
4. **信号量限流意识**（`LogonGlue:88`）。
5. **并发模式下的防御性检查**（`cleanupAll` 抛 `IllegalStateException`）。

## 五、优化方案

### 5.1 开启 Cucumber 引擎级并行（P0，但必须按依赖顺序）

**前置条件（必须先完成）**：X-2（用例绑定上下文）、X-3（route 单例改造）、X-4（每用例唯一数据）、D-1~D-3（凭据，因并行会放大失败暴露面）。**未完成前置就开并行 = 大规模随机故障。**

配置 `test-automation/src/test/resources/junit-platform.properties`：

```properties
# ---------- 并行开关 ----------
cucumber.execution.parallel.enabled=true
# fixed：固定线程数（推荐，行为可预测）
# dynamic：按 CPU 核数动态（CI 上不可预测，不建议）
cucumber.execution.parallel.config.strategy=fixed
cucumber.execution.parallel.config.fixed.parallelism=4
cucumber.execution.parallel.config.fixed.max-pool-size=8

# ---------- 隔离粒度 ----------
# 关键：以 scenario 为隔离单元，同一个 feature 内的 scenario 可并行
cucumber.execution.exclusive-resources.<tagname>.read-write=...

# ---------- 报告 ----------
# 并行下必须使用线程安全的 reporter
cucumber.plugin=io.cucumber.core.plugin.SerenityReporterParallel
```

**failsafe 侧配合**（`test-automation/pom.xml`）：

```xml
<configuration>
  <!-- forkCount 保持 1：进程内线程并行，不要起多 JVM（多 JVM 会让 Serenity 聚合复杂化） -->
  <forkCount>1</forkCount>
  <systemPropertyVariables>
    <cucumber.execution.parallel.enabled>${parallel.enabled}</cucumber.execution.parallel.enabled>
    <cucumber.execution.parallel.config.fixed.parallelism>${parallelism}</cucumber.execution.parallel.config.fixed.parallelism>
  </systemPropertyVariables>
</configuration>
```

```xml
<!-- 根 pom.xml -->
<properties>
  <parallel.enabled>false</parallel.enabled>   <!-- 默认关，稳定后再开 -->
  <parallelism>4</parallelism>
</properties>
<profiles>
  <profile><id>parallel</id><properties><parallel.enabled>true</parallel.enabled></properties></profile>
</profiles>
```

**推荐节奏**：先 `-Pparallel` 在 nightly 上跑两周，flaky 率稳定后再转为默认。

### 5.2 用 `@isolated` 标签保护不可并行的用例（P0 配套）

有些用例天然不能并行（改全局配置、清理共享数据、OTP 限流）。用 Cucumber 的 `exclusive-resources` 表达：

```properties
# junit-platform.properties
# 打了 @isolated 的 scenario 独占 resource:global，等价于串行执行
cucumber.execution.exclusive-resources.isolated.read-write=resource:global
```

```gherkin
@isolated @regression
Scenario: 修改全局参数后校验生效
```

这样既享受并行收益，又保护了少数"Must be serial"的用例。

### 5.3 上下文改为用例绑定（P0，见 02 文档 5.1）

核心是 `ScenarioContext.begin/end` + 运行期断言（`@After` 后 `CURRENT.get() != null` 即失败）。

**这里给一条并行的额外要求**：清理必须 `remove()` 而非 `set(null)`，且 `end()` 必须在 `finally` 中执行，否则异常路径会留下绑定。

```java
@After
public void afterScenario(Scenario scenario) {
    String id = scenarioIds.remove(scenario.getId());
    try {
        // ... 报告、截图、数据清理
    } finally {
        ScenarioContext.end(id);     // 必须 finally
    }
    assertClean();                    // 断言式校验：无残留
}
```

### 5.4 并发度自适应（P1）

```java
// ConcurrentContextOptions.defaults()
int cores = Runtime.getRuntime().availableProcessors();
int parallelism = Integer.getInteger(
    "PLAYWRIGHT_CONCURRENT_PARALLELISM",
    Math.max(2, Math.min(cores / 2, Integer.getInteger("PLAYWRIGHT_CONCURRENT_MAX", 16))));
```

CI 上显式指定：`-Dparallelism=2`（GitHub-hosted runner 是 2 核）。

### 5.5 浏览器资源模型（P1，共享 Browser 模式已移除）

> **变更（DEV-V3 收尾）**：原「默认切换到共享 Browser（`serenity.playwright.shared.browser.enabled=true`，把 N 进程降为 1 进程 + N Context）」的建议**已作废**——共享 Browser 模式已从框架彻底移除（03 文档 W-7）。并发默认即**每线程独立 Browser**（N 并行 = N 进程），资源开销见 X-7。

在不引入共享 Browser 的前提下降低浏览器资源压力的可行路径：
- 单 worker 串行多用例（减少同时存活的 Browser 数）；
- 虚拟线程（9.4，用例内多 Context 并发，但 Browser 仍每线程独立）；
- 在 CI 上显式指定较小并行度（5.4）。

若未来确需共享 Browser，须先在 Playwright for Java 层解决对象非线程安全问题（客户端对象注册表 `__adopt__` / `pausedStateChanged` 损坏），否则不得重新启用。

### 5.6 开启受控重试（P2）

```xml
<!-- 根 pom.xml：默认 0 改为 1，配合失败分类只对"环境/崩溃"重试 -->
<rerunFailingTestsCount>1</rerunFailingTestsCount>
```

**注意**：盲目重试会掩盖真实缺陷。正确做法是结合 07 文档的失败分类（E-4）——**只对"环境问题 / 浏览器崩溃"重试，断言失败不重试**。failsafe 本身不支持按原因重试，需要在 `FrameworkHooks` 里自行实现：

```java
@After
public void maybeRerun(Scenario scenario) {
    if (scenario.isFailed() && FailureCategory.of(lastError).isRetryable()) {
        RetryRegistry.requestRetry(scenario.getId());
    }
}
```

### 5.7 隔离自检清单（P1，落地为自动化检查）

在 `FrameworkHooks.@After` 里统一跑一遍，**任何一项不通过即让用例失败**：

```java
private void assertClean() {
    List<String> leaks = new ArrayList<>();
    if (ScenarioContext.isBound())            leaks.add("ScenarioContext 未解绑");
    if (SoftAssertions.hasPending())          leaks.add("软断言未 assertAll");
    if (PageRegistry.hasOrphanPages())        leaks.add("存在未关闭的 Page");
    if (RouteMonitorScope.isDirty())          leaks.add("route 监控态未清理");
    if (TestDataScope.isDirty())              leaks.add("测试数据未清理");
    if (!leaks.isEmpty()) {
        throw new FrameworkException("用例隔离检查失败: " + leaks);
    }
}
```

**这条"断言式清理"是整个并发改造的保险丝**——它把"以后某个用例莫名失败"变成"当场指出是谁没清理干净"。

## 六、结论

这一块的核心结论是：**框架的并发"零件"是齐的（锁顺序、共享 Browser、虚拟线程、信号量限流），但"电路"没接通**——引擎层没有并行配置，15/16 的 feature 仍在串行跑。

更重要的是**顺序问题**：不要直接开并行。X-2（上下文用例绑定）、X-3（route 单例）、X-4（数据唯一化）是三条前置依赖，缺任何一条，开并行都会把稳定的串行套件变成随机失败的炼狱。

建议路径：**先修隔离（含断言式自检）→ 再开 `-Pparallel` 灰度两周 → 最后转默认**。这条路径的风险可控，收益是回归耗时从线性恶化转为可水平扩展。

### 7.3 梯度压测 4→8→16 本地代理实测（2026-09-21 执行）

**对象**：`CucumberRouteDemoParallelSmokeRunnerIT`（8 scenario：4 monitor + 4 mock；真实 Chromium + 本地 `route-demo-service:8888`，只读 GET + 拦截式 MOCK，不写后端）。命令同运行器 javadoc，另加 `-Dtest=NoSuchTestXYZ -Dsurefire.failIfNoSpecifiedTests=false` 跳过单测以隔离 IT 墙钟：

```bash
mvn -o -pl test-automation -am verify -Pparallel -Dparallelism=N -DmaxPoolSize=N \
  -Dit.test=CucumberRouteDemoParallelSmokeRunnerIT -Dtags=@route-parallel-smoke \
  "-Dcve.gate.skip=true" "-Dcheckstyle.skip=true" "-Dspotbugs.skip=true"
```

**实测（干净机器：先清理全部残留 JVM/Playwright Chrome；每档 2 次）**

| 档位 | IT 墙钟 | 并发 worker | 用例结果 | 8 次浏览器启动跨度 |
|---|---|---|---|---|
| 串行（不加 `-Pparallel`） | 56.8s / 59.2s | 0 | 8/0/0/0 | —（串行故无跨度） |
| `-Dparallelism=4` | 51.6s / 50.9s | 4 | 8/0/0/0 | 32.1s（均隔 4.6s） |
| `-Dparallelism=8` | 63.7s / 50.4s | 8 | 8/0/0/0 | 37.9s / 24.5s |
| `-Dparallelism=16` | 52.7s / 53.9s | 8（=场景数上限） | 8/0/0/0 | 31.8s |
| `-Dparallelism=8` + `-Dplaywright.browser.headless=true` | 52.9s | 8 | 8/0/0/0 | 32.9s |

**结论**

1. ✅ **并行度真生效、隔离健康、无 flaky**：worker 数 = min(parallelism, 场景数)（16 档受 8 个 scenario 封顶）；每档两次均 `8/0/0/0`；页面分类 `managed=8 / extra=0`（无跨 scenario 串页）；同档两次结果一致（极差来自机器负载而非用例）。
2. ⚠️ **墙钟收益封顶在 ~10%，且落在噪声内**：串行 ~58s → 各档 51~54s（`p=8` 有一次 63.7s 反超串行；同档极差最大 13s）。**当前模型不具备「耗时随并发度水平下降」的能力。**
3. **根因（已量化；2026-09-21 更正）＝ 进程级 `PAGE_LOCK`/`CONTEXT_LOCK` 的长临界区**：`PageRegistryImpl.getPage` 在 `withPageLock`（原为进程级 `static final` 单例）内调用 `PlaywrightManager.getContext()` → `createContext()` → `getBrowser()` → **Chrome 启动**（1~10s）与 `createPage()`。`jstack` 实测 **7 个 worker 同时 `waiting to lock <同一个 java.lang.Object>`（即 PAGE_LOCK）**；日志中 8 次 `Launching browser` 恒定错开 4.5~5.4s、总跨 24~38s（与并行度 4/8/16 无关）；且**先跑完的 scenario 关不了窗**（`closePage` 要抢同一把锁）——8 个 Context 关闭挤在末尾 0.3s 内爆发。
   ⇒ 这正是 WEB-C1（doc 13 **P1-1**）所述"进程级锁使并行下 Context/Page 创建与关闭全局串行"，是"并行≈0 加速"与"窗口最后一起关"的**共同根因**。
   （曾把根因写成「`synchronized initialize()` 串行化启动」——实测更正：启动只是该长临界区中**最长的一段**，真正的锁是 PAGE_LOCK。）
4. **排除项（对照实验）**：headless 与有头无差异（52.9s vs 50.4~63.7s，启动跨度 32.9s vs 24.5~37.9s）⇒ 瓶颈不是「有头窗口/桌面争用」，而是上述框架启动锁 + per-scenario 启动模型。
5. ⚠️ **环境陷阱（本次踩到，须进 nightly 规程）**：首轮测量被**残留进程污染** —— 机器上有一具 07:12 启动、已运行 **11+ 小时** 的 `RoutePerformanceStressTest`（maven + failsafe fork），另 2 具残留 maven/fork 与 67 个 Chrome。污染期 `parallelism=16` 出现数分钟停滞（线程栈显示多个线程等待 `LifecycleLockMediator.withPageLock`，`PageRegistryImpl.closePage` ← `PlaywrightSerenityBridge.cleanupForScenario`）；清理后**同参数 88s 跑完且可复现**。⇒ **压测前后必须校验「无残留 JVM/浏览器」并给 IT 配超时看门狗**，否则会把环境噪声误判为框架缺陷（本次差点如此）。

**⇒ 对「是否转默认」的答复**：**不因"提速"转默认**（收益封顶 ~10% 且不稳定）；但**保留 `-Pparallel` 作为并发正确性回归手段**——本框架的并发类缺陷（F-11 键空间/闸门、页面归属判定等）正是在并行下才暴露。若要真正降耗时，需独立专项评估「Browser 跨 scenario 复用」（与 WEB-F1 避免有头窗口堆积的取舍）或把启动移出 scenario 关键路径；不在本次验证范围。

**残余验证（仍需 nightly/内网，本地代理覆盖不到）**：① 真实 SIT 凭据 + 内网（logon/SSO 互踢，`partition.enabled=true`）；② `forkCount>0` 分叉下的 P1-2 跨 JVM 登录锁（本代理不涉登录路径）；③ 两周 flaky 率统计。nightly 起步建议仍为 `-Dparallelism=2`（GitHub-hosted 2 核）配合 `@isolated` 保护串行用例。

### 7.4 修复记录（2026-09-21）：Context/Page 锁改 per-thread —— 闭合 doc 13 **P1-1（WEB-C1）**

**触发**：用户观察「并行跑 case 时先跑完的用例窗口不关，最后一起关」，与 WEB-F1 宣称的"每 scenario 收尾即关本线程 Browser"矛盾。

**定位**：`jstack` 实测 7 个 worker 同锁等待（进程级 `PAGE_LOCK`）＋ 日志时间线（launch 逐个排队、8 个 Context 关闭末尾爆发）⇒ 即 §7.3 第 3 条更正后的根因。

**改动**：`LifecycleLockMediator` 的 `CONTEXT_LOCK`/`PAGE_LOCK` 由进程级 `static final` 单例改为 **per-thread**（复用
`BROWSER_LOCK_KEY` 同款 `ContextKey` 机制），调用点（`ContextRegistryImpl`/`PageRegistryImpl`）**零改动**。
依据：Browser/Context/Page 本就每线程独立，全部调用点只读写本线程状态（`TestContextHolder` + 线程级记录），
跨线程路径（`BrowserCleanupImpl` 遍历 `browser.contexts()`）本就不经该锁 ⇒ 进程级锁在正确性上非必需
（该结论原已写在类 javadoc，且 doc 13 P1-1 已列为"并行上线前必修"）。
