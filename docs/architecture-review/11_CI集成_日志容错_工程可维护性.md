# 11 CI 集成、日志容错与工程可维护性

> 评审范围：`.github/workflows/**`（3 个 yml）、`tools/`（32 文件）、日志配置、仓库卫生
> 评审基线：`e11a847`

---

## 一、现状评估

### 1.1 CI：三条 workflow，但主链路是断的

**`build.yml`（主构建）**：

```yaml
# :3-6（注释）
# ENG-P0-1：建立 CI，触发四道门禁（编译 / Checkstyle / SpotBugs / 单测）。
# 分两期：一期仅 `mvn -B test`（已含 compile + Checkstyle(validate) + 单测）；
# 门禁基线稳定后，将下面的命令升级为 `mvn -B verify` 以纳入 SpotBugs/PMD(verify)。
# :28（实际执行）
run: mvn -B test
```

**这是整套工程最严重的一处断裂**：

| 环节 | 绑定阶段 | CI 是否执行 |
|---|---|---|
| 编译 + Checkstyle(validate) + 单测 | `test` | ✅ |
| **Cucumber E2E（所有 IT）** | `integration-test` | ❌ 从未执行 |
| **Serenity 报告聚合** | `post-integration-test` | ❌ 从未执行 |
| **汇总报告生成** | `verify` | ❌ 从未执行 |
| **SpotBugs 门禁** | `verify` | ❌ 从未执行 |
| **OSV CVE 门禁** | `verify` | ❌ 从未执行 |

也就是说：**CI 上从来没有真正跑过一个 E2E 用例**。注释里写着"门禁基线稳定后升级为 verify"，但这个升级一直没有发生——这是一张开给自己的、忘了兑现的支票。

**`build.yml` 其它问题**：
- **没有 Playwright 浏览器安装步骤**。三个 workflow 全都没有。即使把命令改成 `verify`，在干净的 runner 上也会因为找不到浏览器而失败。
- `upload-artifact` 用 `if-no-files-found: ignore`（`:36`）。因为 E2E 从没跑过，`target/site/serenity` 根本不存在，这个归档步骤每次都静默跳过——**"报告归档"形同虚设，而且永远不会报错**。
- 只有 `cache: maven`，无浏览器缓存，每次冷启动。
- 无 matrix、无并发、无失败分类、无重试。

**`serenity-report-push.yml`**：推送到外部仓库 `hsbc/dbb-serenity-reports` 的 gh-pages（`:37,:62-71`），用 `PERSONAL_TOKEN`。`:54` 会校验 `report-src/serenity-report/index.html` 存在。**没有脱敏门禁**（见 07 文档 E-1）。

**`doc-drift-check.yml`**：执行 `tools/check-doc-drift.sh`（`:25`）校验 README 与 pom 版本一致。有用，但——

### 1.2 tools/：22 个一次性脚本留在仓库

| 类别 | 脚本 | 判断 |
|---|---|---|
| CI 依赖 | `check-doc-drift.sh` | ✅ 唯一被 CI 使用 |
| 安全配套 | `cve-gate.ps1`、`install-osv-scanner.ps1`、`gen-osv-baseline.ps1` | ⚠️ 需要但 CI 未安装二进制 |
| 迁移遗留 | `migrate_junit4_to_junit5.ps1`、`_phase4_migrate/.ps1`、`_pkgfix/.ps1`、`_pkgmove.ps1`、`fix_assert_order_v3.ps1`、`fix_junit5_assertion_args.ps1`、`prune_unused_lifecycle_imports.ps1`、`rename_api_frameworkconfig.ps1` 等 | ❌ 一次性，应清理 |
| 乱码治理 | `clean_log_typographic.ps1` | ⚠️ 症状治理，非根因 |
| 中间产物 | `gate-inline-source.txt`、`gen_picker_*.txt/js`、`picker_merge_test.js`、`_rewritten_RolePickerScripts.java` | ❌ 应清理 |

`clean_log_typographic.ps1` 的存在，加上提交 `e11a847` 里"ASCII-ize western typographic punctuation in log output strings (kill GBK mojibake)"这条，说明团队曾遭遇日志乱码（GBK 控制台输出西文标点），最终选择**"干脆不用西文标点"**来规避。

这是典型的**症状治理**：根因是 Windows 控制台/文件编码与 UTF-8 的不匹配，正确解法是在 logback 里显式指定 encoder charset + JVM `-Dfile.encoding=UTF-8`，而不是限制开发者不许用破折号。

### 1.3 日志容错

- **脱敏不覆盖异常栈**（C-2）：`SanitizingMessageConverter` 只接管 `%msg`，`%ex` 里的敏感值明文落盘。
- **异步线程不传播 MDC**（C-5）：`AsyncPool` 提交的异步任务日志没有 `scenarioId`，排障时无法归因。
- **`ApiTrafficLogger` IOException 仅 debug**（C-10，`ApiTrafficLogger.java:198-199`）：流量日志静默丢失。
- **日志配置只在 `test-automation` 有 `logback-test.xml`**，框架模块（core/web/route）无统一日志配置，本地跑框架单测时日志行为不一致。
- **脱敏器异常回退原文**（`SanitizingMessageConverter.java:36-60` 注释提到）：脱敏失败时输出原文——这是**安全方向上的错误默认值**，失败应抑制而非放行。

## 二、优势

1. **已有 CI 意识**：三条 workflow 覆盖了构建、报告发布、文档漂移，方向完整。
2. **`doc-drift-check` 是好设计**：用脚本校验文档与 pom 版本一致，防止文档腐化。**（2026-09-20 复核：该门禁曾因根 `README.md` 于 `aa02d27` 被批量误删而永久失效——脚本要求 `pom.xml` 与 `README.md` 同时存在，否则 `exit 2`，使每次 pom 变更都点亮一个必然失败的红叉；已恢复 README 并修正脚本中失效的 `junit.version` 映射（实为 `junit.jupiter.version`）+ 补 `junit.platform.version`，门禁重新生效。）**

> **同类问题（2026-09-20 发现并修复）：SpotBugs 门禁链此前在 `route` 模块断开。** `route/spotbugs-exclude.xml` 顶部注释已自述「`mvn verify` 的 SpotBugs 门禁因上游模块（core/reporting/web/codegen）先失败而**从未真正执行到本模块**」；上游打通后，本模块存量告警（测试类 `ApiMonitoringRepositoryConcurrencyTest` 的 `DMI_EMPTY_DB_PASSWORD`，非新引入）立即暴露并使 `verify` 失败，**连带使排在其后的 test-automation 门禁从未跑到**。已修：测试侧连接获取收敛为单一 `openConnection()`（登记面 2 → 1）+ 按「类+模式」登记该探测器（H2 测试专属内存库无凭据语义，且 SpotBugs 有空口令/硬编码口令两个姐妹探测器，不能用改常量"绕过"）。修后实测 **全 8 模块 `mvn verify` 全部 SUCCESS**。教训与 `doc-drift-check` 同源：**门禁链路自身的缺陷会长期掩盖真实告警**，故"CI 绿"必须区分「真的都跑了且都通过」与「前面的环节先失败所以后面的根本没跑」。
>
> **同批：并发压测护栏的连接泄漏断言也做了同口径修正。** `RouteDemoConcurrencyGuardrailTest` 首跑失败于 `活跃连接实际 1` —— 活跃连接数是**瞬时状态**（刷库器在途 INSERT 期间该连接必然非 Sleep），点采样会把"正在干活"误判为"泄漏"。已改为**有界等待归零**（真泄漏永不归零、逾时即失败并 dump processlist），连跑 3/3 通过。
3. **构建注释里记录了分期计划**，说明有路线图思维（只是未兑现）。
4. **`--add-opens` 配置完整**，JDK 强封装适配到位。
5. **`logback-test.xml` 存在**且框架有专门的脱敏 Converter，日志治理有意识。
6. **提交信息规范**（含 issue 编号如 `WEB-P1-6`、`CORE-P0-1`），可追溯性好。

## 四、优化方案

### 4.1 修复主构建链路（P0）

```yaml
name: Build & Test
on:
  push: { branches: [ main, master ] }
  pull_request: { branches: [ main, master ] }

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      # 【新增】安装 Playwright 浏览器（CI-2）
      - name: Install Playwright browsers
        run: mvn -B -q exec:java -e -Dexec.mainClass=com.microsoft.playwright.CLI
             -Dexec.args="install --with-deps chromium" -pl web
        # 或更稳妥：mvn -B -q test-compile 后 java -jar driver bundle

      # 【新增】缓存浏览器（避免每次冷下载）
      - uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: playwright-${{ runner.os }}-${{ hashFiles('pom.xml') }}

      # 【修复】由 test 升级为 verify（CI-1）
      - name: Build, test and verify
        run: mvn -B verify -Dtags="${{ github.event_name == 'pull_request' && '@smoke and not @skip' || '@regression and not @skip' }}"
        env:
          CONFIG_MASTER_KEY: ${{ secrets.CONFIG_MASTER_KEY }}

      # 【修复】产物归档改为严格（CI-3）
      - name: Upload Serenity reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: serenity-reports
          path: 'target/site/serenity/**'
          if-no-files-found: error      # ← 由 ignore 改为 error

      # 【新增】孤儿浏览器进程兜底清理（配合 03 文档 W-1）
      - name: Kill stray browsers
        if: always()
        run: pkill -f 'chrome|chromium|firefox' || true
```

**分阶段建议**：如果担心 `verify` 一次引入太多失败，可先加一个 `e2e` job 用 `continue-on-error: true` 跑两周收集基线，再转为阻塞。但**不能继续停留在"只跑 test"**——那样 CI 对 E2E 的验证价值是零。

### 4.2 修复 CVE 门禁（P1）

```yaml
      - name: Install OSV-Scanner
        run: |
          mkdir -p tools/osv-scanner
          curl -sSfL https://github.com/google/osv-scanner/releases/latest/download/osv-scanner_linux_amd64 \
            -o tools/osv-scanner/osv-scanner
          chmod +x tools/osv-scanner/osv-scanner
          echo "$PWD/tools/osv-scanner" >> $GITHUB_PATH
```

同时把 `cve-gate.ps1` 里"无二进制时仅告警跳过"的逻辑改为：**`OSV_CVE_GATE_REQUIRED=true` 时缺失即 fail fast**。

### 4.3 日志脱敏三项修复（P1）

```java
// 1) 覆盖异常栈（L-1）——见 02 文档 5.2 的 SanitizingThrowableConverter

// 2) 脱敏失败应抑制而非放行（L-3）
private static String safe(String s) {
    try {
        return SensitiveDataSanitizer.sanitize(s);
    } catch (RuntimeException e) {
        // 安全方向：脱敏失败宁可不输出，也不能输出原文
        return "[LOG SUPPRESSED: sanitizer failure]";
    }
}

// 3) 异步传播 MDC（L-2）——见 02 文档 5.4 的 MdcAware
```

```xml
<!-- 4) logback 显式 UTF-8，根治乱码（L-4） -->
<appender name="FILE" class="ch.qos.logback.core.FileAppender">
  <encoder class="ch.qos.logback.classic.encoder.PatternLayoutEncoder">
    <charset>UTF-8</charset>          <!-- ← 显式指定，不依赖平台默认 -->
    <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level [%X{scenarioId}] %msg%n%ex</pattern>
  </encoder>
</appender>
```

并把 `logback-test.xml` 提升为 `logback.xml` 放到 `core/src/main/resources`，让框架模块与测试模块共享同一套日志配置。

### 4.5 配置键统一注册表（P1）

见 02 文档 5.5 的 `ConfigKeys` 枚举方案。把 `WebFrameworkConfig`、`ApiFrameworkConfig`、`MonitorConfig` 的**键定义**收敛到一处，三侧只保留"读取门面"职责。

【2026-09-20 全量落地（完成）】三侧键定义已全部收敛至 core `ConfigKeys` —— 共 **184 个键**（`WEB_*` 141 + `API_*` 21 + Monitor / 持久化 22），`WebFrameworkConfig` / `ApiFrameworkConfig` / `MonitorConfig` 均退化为**引用注册表的门面**（不再持有任何 key / 默认值字面量）。守卫两道：`ConfigKeysGoldenTest`（golden 快照——以迁移前的 `key=default` 基线逐键逐字比对，防机械搬运写错默认值）+ `ConfigUnificationTest#facadesMustDelegateToRegistry`（门面不得重新长出本地定义）。收敛前的「镜像注册表」模型（同键两处定义 + 镜像默认值一致性校验）随之退役：
- 键名是**配置契约**（用户 `serenity.properties` / `-D` 按字面匹配），故迁移只搬家不加改名；`ConfigKeysRegistryTest` 的命名断言同步校正为真实成立的结构性规则（历史键存在驼峰段与连字符，如 `playwright.page.error.failOnError`、`http.ssl.relax-validation`）。

## 五、结论

三个维度里，**CI 是唯一存在"完全断裂"的维度**：CI 上从来没有跑过一个 E2E 用例（CI-1），而且即使改了命令也跑不起来（CI-2，无浏览器安装）。这意味着前面 10 份文档讨论的所有能力——生命周期、报告、并发、BDD——在 CI 上的实际验证次数是 **0**。

日志与可维护性则是"有意识、未收口"：脱敏框架建好了但漏了异常栈，日志配置有了但编码根因没修，配置枚举有了但没有统一注册表。

**优先级建议**：`4.1 修复主构建链路` 应与 05 文档的凭据修复并列第一——一个是"让自动化真的跑起来"，一个是"让敏感数据不外泄"，这两件事决定了这套框架是资产还是负债。
