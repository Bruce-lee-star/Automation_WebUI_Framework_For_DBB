## 七、明确不做的事（避免过度工程）

评审中识别到以下"看起来该做、实际不建议现在做"的项，供决策参考：

| 不做 | 理由 |
|---|---|
| 迁移到 Playwright 官方 `PageFactory` | 维持自有 `PageFactory`（组合式，不再要求业务 Page 继承 `BasePage`）；`@RoleElement` + 多语言字典是核心竞争力，官方方案不支持，迁移即丧失优势 |
| 引入 Allure / ReportPortal 替换 Serenity 报告 | 现有 Serenity + 二次汇总已满足需求，替换成本高收益低 |
| 引入 Testcontainers 做环境隔离 | 被测系统是外部 SIT 环境，容器化不适用 |
| 立即开启全量并行 | 隔离前置未完成时开并行 = 制造随机故障 |
| 追求高单测覆盖率数字 | 优先覆盖脆弱链路（脱敏、上下文、清理），比刷覆盖率有价值 |
| 引入 Groovy/JSON DSL 做数据驱动 | `RouteDsl` 已是 Java 流式 DSL，再加一套 DSL 是负担 |

## 八、一句话结论

这套框架的**架构骨架与设计品味在一线水准**——DAG 分层、SPI 依赖倒置、Playwright 生命周期的锁纪律、`@RoleElement` 语义定位、AES-GCM 脱敏，都是真刀真枪打磨出来的能力。

但它目前处于**"能力已建成、闭环未打通"**的状态：加密能力有而凭据仍是明文，并发零件齐而引擎仍串行，CI 存在而 E2E 从未被执行。

**P0 的 19 项里，真正决定成败的是 6 项**：`SEC-1/SEC-2`（堵住数据泄露）、`RUN-1`（让 CI 真的跑 E2E）、`RUN-2`（让默认执行集覆盖全量）、`PAR-1`（用例隔离）、`CON-1`（并行）。这 6 项合计不到 10 人日，做完后这套框架才从"看起来很完整"变成"真的在守护质量"。
