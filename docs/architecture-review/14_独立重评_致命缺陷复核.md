## 二、本轮确认"仍开放"的缺陷（按严重度）

### ⚪ 复核降级 — 非默认配置缺陷（原误判为 🔴 FATAL）

#### WEB-F1｜SINGLETON Page 共享可变 `this.page` → 仅显式 SINGLETON 时触发，默认配置安全
- **复核结论（推翻原 FATAL）**：报告原称 `PageObjectFactory.java:335-337`「默认 `LifecycleStrategy` 为 `SINGLETON`」，实为对 `switch` 分支（`case SINGLETON: / default:` 兜底）的误读。**真实默认策略在 `Builder.lifecycle` 第 126 行 = `THREAD_ISOLATED`**，`DEFAULT_CONFIG`（:183）→ `currentConfig`（:203）→ 无参 `getPage(Class)`（:267-268）均走该默认。故**默认全部 Page 为 per-thread 实例**，`resolveManagedPage()`（:129-144）对 `this.page` 的写入只发生在拥有该实例的线程上，**并行下无跨线程数据竞争**。
- **残留风险**：仅当用户显式 `LifecycleStrategy.SINGLETON` 时才共享可变 `this.page` 跨线程；而该枚举 Javadoc（:56-61）已明确「跨线程共享与 `ownerThread` 守卫冲突，并行下必抛 cross-thread access denied，故不再是默认」。即该路径已有文档级警示，非默认缺陷。
- **证据修正**：`singleInstances.clear()`（:524，仅套件结束调用）属实，但它是 SINGLETON 存储的清理，与默认策略无关。
- **处置**：从 FATAL 降级；**不阻塞 `-Pparallel` 生产化**。若需彻底消除显式 SINGLETON 风险，可后续给 `resolveManagedPage` 加锁或纯函数化（低优，非当前阻塞项）。

### 🟠 CRITICAL — 仅在开启 `-Pparallel` 时触发

#### CORE-LANG｜LanguageState 全局值被并发场景互相覆盖 → 多语言串语言
- **证据**：`LanguageState.java:30` 进程级 `globalLang`（带单调序号）；`:50-77` `setLanguage` 同时写全局值与线程副本，`getLanguage()` 取"写入更新的那个"。
- **致命机理**：场景 A（线程1）`setLanguage("zh")` → 全局 seq=1；并发场景 B（线程2）`setLanguage("en")` → 全局 seq=2。线程1 读 `getLanguage()`：全局 seq(2) ≥ 线程副本 seq(1) → 返回 **en**，但 A 本应 zh。**并行下任意两个场景交错 `setLanguage` 都会互相串语言**。
- **触发条件**：`-Pparallel` + 多场景设置不同语言。
- **修复**：`getLanguage()` 在并行下应优先/仅取线程副本（场景级），去掉"全局较新优先"的跨线程可见逻辑；或把语言状态彻底下沉到 per-scenario context，移除进程级 `globalLang`。

### 🟡 MEDIUM

#### CG-M1｜RolePickerCommandEngine `javaPickBySig.isEmpty()` 未加锁 → 并发 CME 风险
- **证据**：写端与多次读端已 `synchronized(javaPickBySig)`（`:61,84,133,197,488`），但 `:269`、`:486`、`:532` 的 `javaPickBySig.isEmpty()` 读取**未加锁**。
- **机理**：录制器在并发写入 `javaPickBySig` 时，未同步的 `isEmpty()` 可能抛 `ConcurrentModificationException`，导致录制会话崩溃。影响面限于"同一录制会话内的并发面板同步"，非跨场景，但仍是真实并发缺陷。
- **修复**：这三处 `isEmpty()` 同样包进 `synchronized(javaPickBySig)`，或改用 `ConcurrentHashMap` 后将 `isEmpty` 视为近似值。

#### ✅ RT-OBS（已修复，2026-09-20）｜MonitorHandler 队列饱和拒绝路径 fail-closed
- **证据**：`MonitorHandler.java:131` 观测执行器 `observationExecutor` 为有界 `ArrayBlockingQueue`(默认 4096) + `AbortPolicy`；`handle()`(:543) 把「waitForResponse + body 读 + 同步断言」提交该池。
- **机理（原 fail-open 风险）**：队列满时 `AbortPolicy` 直接拒任务，原 `catch(RejectedExecutionException)`(:546) 仅 `resume` 放行 + `LOGGER.error`，**断言任务整体丢弃** → 应判红的监控断言永不执行 → 用例假绿。
- **修复（已落地）**：抽取 `onObservationRejected(route, rule, ticket, bodyFuture)`，在拒绝时（仍保留幂等放行）调用 `ApiCaptureContext.signalFailFast()` 置失败标志（与 `recordUnavailable` 对齐，遵循 ROUTE-P0-1「宁可错报不可漏测」）+ `MonitorDataLossReporter.recordLoss("monitor_observation_dropped_queue_saturated", 1)` 登记数据损失供汇总报告红色提示。新增契约测试 `MonitorHandlerRejectFailFastTest` 固化该语义。请求放行不挂起、不反压事件线程的原有保证不变。

#### ✅ CI-E2E（代码已放开 `if`，2026-09-20）｜e2e job 已对 PR 开放，剩余仓库分支保护设置
- **证据**：原 `build.yml:77` `if: ${{ github.event_name == 'push' }}`（仅 push 触发）；文件头注释明确"若设为 required 需在 PR 放开 `if`"。
- **机理**：PR 合并前不会跑真实浏览器 IT（需 SIT 凭据/时长），真实 E2E 实际只在 push 后补救，回归窗口后移。
- **修复（代码部分已落地）**：`build.yml` 的 `e2e` job `if` 已放开为 `pull_request || push`（2026-09-20），PR 合并前即跑真实浏览器 IT（前提：SIT 凭据以 Repository Secrets 对 PR 可用——同仓库 PR 默认可用）。**剩余仓库设置（代码改不了，需仓库管理员）**：Settings → Branches → 分支保护规则，将本 workflow 设为 required status check，方使"PR 合并前真实 E2E 失败即阻断"真正生效。属半代码项——代码侧已闭合，仅差仓库策略设置。

### ⚪ LOW–MEDIUM

#### SEC-PRINT｜SanitizingPrintStream 与 Converter 脱敏失败策略不一致
- **证据**：`SanitizingPrintStream.java:20` 注释"脱敏异常不丢日志（**回退原文**）"；而 `SanitizingMessageConverter.java:56-59` 异常时**抑制（不回退原文）**。
- **机理**：两条出口策略相反。若 `log().all()` 流经的 `SanitizingPrintStream` 在脱敏抛异常时回退原文，**明文凭据可能经 REST 日志出域**。建议与 Converter 对齐为"失败即抑制"。
- **修复**：`SanitizingPrintStream.sanitize()` 在捕获异常时返回脱敏占位符（`[SUPPRESSED]`）而非原文。
