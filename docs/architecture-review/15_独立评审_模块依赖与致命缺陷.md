# 独立评审：模块依赖关系 + 逐模块逐文件致命缺陷（含 route↔web 关系勘误）

> **方法论**：结论仅来自源码与 pom 实证。依赖关系以各模块 `pom.xml` 的 `<dependencies>` 为准，并以框架自带的 **ArchUnit 架构门禁**（`ArchitectureTest` / `LayeringArchTest` / `CodegenDecouplingArchTest` / `ReportingRouteDecouplingArchTest`）作为"意图架构"的权威表述。
>
> **版本**：2026-09-20 第二轮独立评审 + 同日勘误合并。**勘误**：原"判断 B：route 不为 web 服务"结论经复核**推翻**（见第三章）。

## 一、真实依赖关系

依赖图有**两个视角**，混为一谈就会得出错误结论（本评审初稿正因此判错判断 B）：

### 1.1 编译期视角（pom 决定的静态边）

```
framework-core  (地基，内部零依赖)
   │
   ├── framework-reporting        → core
   ├── framework-api              → core, reporting
   ├── framework-route            → core, reporting, playwright    （不依赖 web）
   │        └── route-demo-service / route-demo-web → route        （仅测试夹具）
   │
   └── framework-web              → core, api, reporting, playwright   （web 依赖 api）
            └── framework-codegen → web                     （codegen 依赖 web）

framework-web  →  framework-codegen  （仅经 SPI：RoleCodegenBridge，ArchUnit 强制）

test-automation → core, reporting, api, web, route, codegen   （唯一"全量汇合"模块）
```

依据：`api/pom.xml:19-27`、`codegen/pom.xml:31-34`、`reporting/pom.xml:19-21`、`route/pom.xml:21-28,57-59`、`web/pom.xml:19-31,68-69`、`test-automation/pom.xml:25-52`。

### 1.2 运行时视角（对象流 + SPI 驱动的动态边）—— 初稿遗漏的关键边

```
        ┌──────────────────────────────────────────────────┐
        │   Playwright (library)  Page / BrowserContext     │  ← web 与 route 共享的集成缝
        └────────────┬──────────────────────▲──────────────┘
         生产 Page/Context              消费 Page/Context
                     │                      │
                  ┌──▼──┐             ┌─────┴─────┐
                  │ web │             │   route   │
                  └──┬──┘             └─────▲─────┘
                     │ 经 core SPI 驱动启停   │
                     └──► core: RouteLifecycle / RouteLifecycleRegistry ──┘
```

**web 生产 Page/Context，route 消费 Page/Context 做网络治理，web 经 core 的 `RouteLifecycle` SPI 反向驱动 route 启停。**

### 1.3 框架自带的架构门禁（意图架构）

| 规则 | 内容 | 位置 |
|---|---|---|
| L1 | api 不得依赖 web | `ArchitectureTest:92-97` |
| L2 | common 不得依赖 web | `ArchitectureTest:83-89` |
| L4 | common 不得依赖 api | `ArchitectureTest:120-126` |
| L3 | `web.page` 不得依赖 route | `ArchitectureTest:99-105` |
| L5 | route 不得依赖 `web.page` | `ArchitectureTest:128-135` |
| **L6** | **route 不得依赖 web（整模块）** | `ArchitectureTest:139-145` |
| G1 | framework 顶层切片无循环依赖 | `ArchitectureTest:148-153` |
| — | web 不得依赖 codegen 的 scan 实现（仅 SPI） | `CodegenDecouplingArchTest:28-46` |
| — | reporting 不得依赖 route 实现（仅 core SPI） | `ReportingRouteDecouplingArchTest:26-44` |
| — | 禁依赖 `com.microsoft.playwright.impl.*`、禁 JUnit4、禁 `Thread.sleep`、lifecycle 内部面封装 | `ArchitectureTest:169-451` |

**结论**：模块边界不是"口头约定"，而是**被 ArchUnit 固化进 CI 的硬门禁**，且门禁质量高（含 SPI 倒置、类型不泄漏、锁封装等企业级规则）。

> **但门禁守护的是编译图，不是运行时契约**：route 依赖 web 的**产出**（Playwright Page/Context），这条边 ArchUnit 看不见（见第三章 ★NEW-1）。

## 二、对三个架构判断的评判

### 判断 A：codegen 是为 web 服务的，没有 web 就没意义 → **✅ 成立**

- `codegen → web`（编译依赖，`codegen/pom.xml:31-34`）；codegen 的类物理上位于 `framework.web.page.scan.*` 包（属"web 命名空间"，单模块独占，避免 split package）。
- 反向由 SPI 倒置：web 核心仅依赖 `framework.web.codegen.spi.RoleCodegenBridge`，实现由 codegen 运行时注入；`CodegenDecouplingArchTest` 强制 web **不得** import scan 实现。
- codegen 本质是 **web 的运行时语义录制器 + 代码生成器**（生成 web 的 Page/Step 类）。**无 web 则 codegen 无目标产物 → 判断正确。**

### 判断 B：route 也是为 web 服务的，没有 web 就没意义 → **✅ 成立**（2026-09-20 勘误，原判"❌ 不成立"已推翻）

- **route 的能力定义就是 Playwright 网络拦截**：`route/package-info.java:2` —— "Playwright 网络拦截驱动的 **API 流量治理**模块（monitor / modify / delay / mock + 流量录制 + 持久化）"；`:6-11` 明确"本模块的 route **专指** `page.route(pattern, handler)` / `context.route(...)`"。`page.route()` 是**浏览器页面级** API。
- **route 的直接依赖是 Playwright 库，而非 web**：`route/pom.xml:57-59` 依赖 `com.microsoft.playwright:playwright`。它与 web 共享同一第三方类型 —— **Playwright 的 `Page`/`BrowserContext` 就是二者的集成缝**。
- **route 的 DSL 绑定 web 产出的 Page**：`RouteDsl.on(Page)`（`RouteDsl.java:92`）、`on(BrowserContext)`（`:102`）；`:67` 明说"业务用例（推荐）：用本 DSL —— 面向『一次注册一批规则并绑定 Page/Context』"。
- **web 主动驱动 route 生命周期（经 core SPI 倒置）**：`PlaywrightManager.java:221,223,225,236`、`PlaywrightContextManager.java:214,262`、`ContextRegistryImpl.java:211,220` 均在 Page/Context 收尾时调用 `RouteLifecycleRegistry.get().clearContext / stopContextEngine / stopCaptureFor`；`core/.../common/route/RouteLifecycle.java:18` 原文即写"所有调用点（**web 模块**经 `RouteLifecycleRegistry.get()` 调用）"。
- **`route-demo-service` / `route-demo-web` 是测试夹具**：提供"浏览器页面真会去调的真实 HTTP 后端 + 极简前端"，使 route 能在**不依赖真实 DBB 应用**的前提下被开发与验证（`RouteDemoApi.java:14`："要让 `RouteDsl` 的规则命中，就必须在**页面上下文内**发起调用"）。
- ArchUnit L5/L6 禁止 route→web **并不否认"route 服务 web"**：它禁的是**错误的耦合方向**。正因禁了编译期依赖，route 才能既被 web 调用（经 core SPI 倒置）、又可独立测试。

> **一句话**：**codegen 是编译期依附 web；route 是运行时服务 web（经 Playwright Page 缝 + core SPI 倒置）。二者对 web 的价值都成立，只是耦合方式不同。**

### 判断 C：api 和 web 应该是同级的 → **✅ 判断合理，且代码支持低成本落地**

现状是 `web → api`（web 在 api 之上）。但关键实证：

- web 生产代码对 api 的**编译期依赖仅 1 处**：`web/utils/NLSUtils.java:3` `import ...framework.api.utility.JsonUtils;`
- 即：**web 依赖整个 api 模块，只为用一个 JSON 工具类** —— 这是**偶然耦合（utility leakage）**，不是"web 需要 API 测试能力"。
- 框架门禁里有 L1（api↛web），却**没有** "web↛api"，说明现状是"被默许"，而非刻意设计。

**结论**：把 `JsonUtils` 下沉到 `core`（`common.utils`），web→api 即消失，api 与 web 成为真正同级（都只依赖 core）。判断正确，修复成本极低。

## 三、route↔web 关系勘误专节

### 3.1 原结论错在哪（方法学归因，不是判断分歧）

原结论建立在一条错误前提上："web 对 route 零引用"。该前提来自一次检索：

```
grep "framework\.route" web/src/main/java/**/*.java   →  0 命中
```

但 route 的生命周期 SPI 实际包名是 **`framework.common.route`**（多一层 `common`）：

| 真实类 | 完整包路径 | 是否被 `framework\.route` 命中 |
|---|---|---|
| `RouteLifecycle` | `...framework.**common.route**.RouteLifecycle` | ❌ 否 |
| `RouteLifecycleRegistry` | `...framework.**common.route**.RouteLifecycleRegistry` | ❌ 否 |

**这是一次"检索模式覆盖不足"导致的假阴性**。教训：**依赖边的判定必须基于 pom / 编译产物 / ArchUnit，而非关键词检索**——关键词检索在"包名同词不同域"时必然漏边。

### 3.2 由勘误暴露的新增风险

#### ★ NEW-1（中危）包名同词不同域 = 系统性的"漏边陷阱"

同一个单词 `route` 在本仓库有两处**语义完全不同的包**：

| 包 | 模块 | 含义 |
|---|---|---|
| `framework.route.*` | route | Playwright 网络拦截治理（真实现） |
| `framework.common.route.*` | core | route 的**抽象与生命周期 SPI**（非第二套实现） |

`route/package-info.java:13-21` 甚至用整段消歧三种含义（还含 `@route*` Gherkin 标签这第三种）。

**为什么是真风险**：任何**基于关键词/文本检索**的影响面分析（人工 grep，或 AI Agent 的 `impact_analyze`）都会**系统性漏掉 web↔route 这条边**——本次评审初稿即是活样本。
**对 AI Agent 项目的直接影响**：`docs/ai-agent-design/` 的 `impact_analyze` 若以 grep 为核心手段，将稳定复现该错误，给出"改 route 不影响 web"的错误影响面。**建议在 agent 治理中明令：依赖/影响面分析必须走 pom + 编译/字节码级证据，grep 仅作线索、不得作结论。**

#### ★ NEW-2（条件性，需验证）WEB-F1 爆炸半径可能外溢到 route

`PlaywrightManager.clearCurrentThreadRouteState()`（`:218-227`）按 web 侧登记的 context 逐个调 route 清理：

```java
for (BrowserContext ctx : browserCleanup.contextsForCurrentThread()) {
    safeClean("RouteRegistry.clearContext",   () -> RouteLifecycleRegistry.get().clearContext(ctx));
    safeClean("RouteEngine.stopContextEngine", () -> RouteLifecycleRegistry.get().stopContextEngine(ctx));
    safeClean("ApiCaptureContext.stop",        () -> RouteLifecycleRegistry.get().stopCaptureFor(ctx));
}
```

→ **route 规则/引擎/采集清理的"键"（context）由 web 决定**。若 WEB-F1（SINGLETON Page 跨场景共享）导致 web 侧拿到错配 Page/Context，则 route 可能**清错桶**（清了别的场景规则）或**漏清**（本场景规则残留）。
**影响**：WEB-F1 不再只是"web 侧断言串扰"，而可能表现为"**mock 规则/录制数据跨场景串**"，故障更隐蔽、更难归因。
**验证方式**：`-Pparallel` 下跑两个都用 `RouteDsl.on(page)` 注册不同 mock 的场景，观察 A 的 mock 是否命中 B 的请求。

#### ○ NEW-3（低危）SPI 空契约与调用点不一致

`RouteLifecycleRegistry.java:13-14` 明确契约：**"若 route 模块不在 classpath 上……`get()` 返回 null，调用方应做空判断"**。但七处调用点**均未判空**（直接 `.get().xxx()`）。

实际未爆，因为 `PlaywrightManager:221-236`、`ContextRegistryImpl:211,220` 包在 `browserCleanup.safeClean(...)` 内，`PlaywrightContextManager:214,262` 包在 `try/catch (Exception)` 内 → NPE 被兜住并降级为 warn 日志。仅 `BrowserStackManager.java:664`（`String masked = RouteLifecycleRegistry.get().sanitizeUrl(url)`）未见同等防护，建议核对。
**性质**：契约与实现不一致（文档说"需判空"、代码假设非空），非当前故障。

## 七、修复闭环（2026-09-20 执行）

经逐条读取源码核实，9 项缺陷 + 1 项 agent 治理约束全部闭环；仅 WEB-F1 的"并行压测"验收需 nightly/CI 实跑（见下表）。

| 项 | 级别 | 核实结论 | 修复动作 | 验证 |
|---|---|---|---|---|

## 八、一句话总结

- **dependency**：`core ← (reporting, api, route) ← web ← codegen`，`test-automation` 全量汇合；边界由 ArchUnit 硬门禁守护（新增 `L-API`：web 不得依赖 api）。**另有一条 ArchUnit 看不见的运行时边：web →(core SPI)→ route。**
- **三个判断**：codegen 依附 web ✅（编译期）；route 服务 web ✅（运行时，经 Playwright Page 缝 + core SPI 倒置）；api 与 web 应同级 ✅（**ARCH-1 已闭环**：`JsonUtils` 下沉 core、`ContextRegistryImpl` 对 `api.TestServices` 改反射，`web→api` 编译边已断开）。
- **致命面**：仅 **WEB-F1（FATAL）+ CORE-LANG（CRITICAL）**，且**都只在并行时触发**；串行配置安全。
- **方法学教训**：**依赖边判定必须基于 pom / 编译产物 / 架构门禁，关键词检索仅作线索**——`framework.route` 与 `framework.common.route` 的同词异域，足以让 grep 式分析系统性漏边。
