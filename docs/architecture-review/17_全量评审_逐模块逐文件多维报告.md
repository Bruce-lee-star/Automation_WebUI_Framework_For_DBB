### 1.2 一句话结论（每模块）

| 模块 | 一句话 |
|---|---|
| core | 安全与配置抽象做得比多数商用框架细（校验位识别、fail-closed 出口），但**出口脱敏会破坏日志本身**，且软断言/清理机制存在"看起来闭环、实际有洞"的路径 |
| web·生命周期 | 全仓最健康的部分：锁中介、线程前缀过滤、trace 真采集、崩溃重启回补 storageState。短板在**并发身份闸门有两套键空间** |
| web·页面层 | **缺陷密度最高**：字段绑定宿主错位（运行期已复现 ClassCastException）、推荐创建路径不注入、`child()` 恒空、超时整除退化为无限等待 |
| api | 分层与 schema 校验扎实；**配置环境覆盖被静默抹除**、脱敏出口在 `printf`/headers/payload 三处开洞 |
| reporting | 模板与聚合逻辑清晰，但**任一 null 字段即整份报告不产出**，且报告侧零脱敏 |
| route | 全仓工程化程度最高（参数化 SQL、Hikari、批量+重投、丢数据上报）；**MODIFY 路径仍在事件线程阻塞 30s**，`resolveUnified==null` 时 fail-open |
| codegen | 能力覆盖面惊人（frame/shadow/NLS/多策略），但**Java↔JS 契约串错位**让部分功能静默死掉，代码生成有三条产出非法 Java 的路径 |
| test-automation + CI | 门禁设计（ArchUnit 15+ 规则、标签注册表、基线）优秀，但**默认套件 124 条中约 118 条不可能通过**，CI e2e 结构性必红 |

### 1.3 依赖关系（实证）

```
core（地基）
 ├── reporting ──┐
 ├── api ────────┤（仅依赖 core+reporting）
 ├── route ──────┤（仅依赖 core+reporting；经 core SPI 被 web 驱动）
 └── web ────────┘→ codegen（编译期）
        └── web 反向仅经 SPI RoleCodegenBridge
test-automation → 全部模块（唯一汇合点）
```

- `route` 运行时服务 `web`：`RouteDsl.on(page())` 绑定 web 产出的 Page/Context；`PlaywrightManager`/`ContextRegistryImpl` 经 `RouteLifecycleRegistry.get()` 驱动 route 启停（**亲验**）。
- `web → api` 的编译期依赖仅剩 `NLUTils` 一处 JSON 工具（历史结论，本轮未复现冲突）。
- 架构边界由 ArchUnit 守护：`ArchitectureTest`（L1–L7）、`CodegenDecouplingArchTest`、`ReportingRouteDecouplingArchTest`、`LayeringArchTest`、`FeatureTagTaxonomyTest`（**亲验存在且规则丰富**）。

## 3. 致命缺陷清单（FATAL / CRITICAL）

> 每条：`现象 — 证据 — 致命机理 — 触发条件`。**亲验**标记 = 评审人本轮亲自读码或读产物确认。

### 🔴 F-01【FATAL·亲验】组合式 `@RoleElement` 字段绑定宿主错位 → 字段永不绑定 + 运行期 ClassCastException

- **现象**：`RoleElementBinder` 只有 `(BasePage self, Class<?> roleFileClass)` 两个形参，**没有字段宿主参数**，`bind()` 末行恒为 `ReflectiveField.set(field, self, new PageElement(...))`——把注解字段写回**页面宿主**（BasePage/委托实例）。
- **证据**：`web/.../page/binding/RoleElementBinder.java:31,48-51,217`；调用点 `web/.../page/engine/PageContextState.java:245-247,270`（G1 组合式路径传入 `pageOwner` 作 self）；**运行产物**：`final-full.log:1951` / `:2012`（重复 4 次）
  `ElementException: Init RoleElement field failed: languageLink`
  `Caused by: ClassCastException: Cannot cast AbstractManagedPage$1 to com.hsbc...tests.LoginPage`
- **致命机理**：组合式（零继承，G1 新模型）页面对象的字段声明在业务 POJO 上，却被写入委托 BasePage → 抛 ClassCastException 被包装成 ElementException；即便不抛，POJO 字段也永远为 null。这是**框架主推的新模型整体不可用**。
- **触发条件**：任何 `AbstractManagedPage` 子类 + 委托 POJO 持有 `@RoleElement` 字段（`tests/LoginPage` 即此形态）。

### 🔴 F-02【FATAL·亲验】`PageObjectFactory` 的 `ManagedPageAware` 注入位于反射 `else` 分支内 → "推荐路径"反而不可用

- **现象**：`if (supplier != null) { instance = supplier.get(); } else { …反射… if (instance instanceof ManagedPageAware) { …setManagedPage… } }`——注入代码在 else 内。
- **证据**：`web/.../page/factory/PageObjectFactory.java:381-420`（注入位于 `:414-419`）。
- **致命机理**：文档推荐、且脚手架生成器最可能采用的 `register()/customSupplier()`（编译期安全）路径**完全不注入受管 Page**，也不触发字段绑定 → `AbstractManagedPage.getPage()` 直接 `managedPage.get()` → NPE。即"越按推荐写法越坏"。
- **触发条件**：任何经 `register()` / `customSupplier()` 登记的组合式页面。

### 🔴 F-03【FATAL·亲验】`EntityBuilder.build(name, env)` 的环境覆盖被二次加载静默抹除

- **现象**：先按显式 env 加载配置，随即 new `Entity(entity)` 拷贝构造器**再次**加载配置且不带 env；而该路径已不再写 `System.setProperty(ENV)`。
- **证据**：`api/.../core/entity/EntityBuilder.java:45`（`ConfigProvider.config(entity, env)`）→ `api/.../core/entity/Entity.java:67`（`ConfigProvider.config(entity)`，env=null）；`EntityBuilder.java:78-86`（注释明确"不再触碰任何全局状态"）。
- **致命机理**：`withEnv("prod")` 之类显式环境覆盖**静默失效**，用例落到默认环境执行。对金融类测试，这是"打到错环境"级别的静默错误——比报错危险得多。
- **触发条件**：任何使用 env 覆盖的 API 用例。

### 🔴 F-04【FATAL·亲验】默认套件包含"无步骤实现 + 硬编码无效路径"的 feature → 122/124 场景不可能通过

- **现象**：两个中文 feature 的步骤在 `test-automation/src/test/java` 下**零定义**，且路径指向不存在的文件。
- **证据**：`test-automation/src/test/resources/features/role_element_scan_test.feature:1,9,13,20`（`@smoke @web`；`Given 打开录制测试页 "file:///d:/.../src/test/resources/scan-test-all.html"`；`When 点击 提交按钮`/`悬停到目标`）、`role_element_record_test.feature:12,16`；

### 🔴 F-05【FATAL/CI·亲验】CI e2e 结构性必红，主门禁对浏览器 E2E 0 覆盖

- **现象（三重叠加）**：
  1. 主门禁 `run: mvn -B verify -Psca -DskipITs -Dtags='not @skip'`（`build.yml:39`）→ **IT 全跳过**，浏览器回归在门禁上 0 条；
  2. e2e job `run: mvn -B verify -Dtags='not @skip'`（`build.yml:100`）跑全量 124 场景，其中 route 82 + api 11 条依赖 `localhost:8888/8899`（`steps/RouteDemoServiceSteps.java:62`），而 `route-demo-service`/`route-demo-web` **不在根 `pom.xml` modules**、CI 也从不启动它们；
  3. `serenity.conf:44 headless: false` + `:58 channel: "chrome"`，CI 未覆盖该值，runner 装的是 Playwright chromium 且无显示器（`build.yml:97`）。
- **致命机理**：CI 既跑不到真实 E2E（build job），真去跑又必然失败（e2e job）→ "CI 绿"与"测试真的通过"完全解耦。这是评审里**最有欺骗性的一个缺陷**。
- **触发条件**：每次 push / PR。

### 🟠 F-06【CRITICAL·亲验】codegen Java↔JS 拾取模式串契约错位 → 扫描态与键盘可达拾取静默失效

- **现象**：Java 下发 `scan_page` / `scan_region`（下划线），JS 全程比对 `scanPage` / `scanRegion`（小驼峰）。
- **证据**：`codegen/.../RolePickerConstants.java:38-39`（`MODE_SCAN_PAGE="scan_page"`）；映射出口 `RoleElementPicker.java:124-125`；

## 8. 一句话总结

> 这套框架的**架构意图和工程纪律已经在一线水准**（依赖倒置、SPI 解耦、ArchUnit 门禁、参数化持久化、trace 采集、fail-closed 脱敏设计）——
> 真正的风险不在"设计得不对"，而在**若干"最后一公里"未接通**：
> 组合式页面对象的字段绑定写错了宿主（运行期已复现）、推荐创建路径漏注入、环境覆盖被静默抹除、
> 默认套件里躺着 22 条必错场景、CI 的 E2E 要么不跑要么必红、并发隔离的两个前置条件未闭环。
>
> **修复顺序必须是：先让红灯可信（P0-4/5）→ 再让新模型可用（P0-1/2/3）→ 才谈并发（P1-1/2）。**
> 跳过任何一步，都会在"反馈不可信"的环境里做修复——那是这套框架当前最大的隐性成本。
