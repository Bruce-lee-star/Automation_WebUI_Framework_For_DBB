# 整改专项设计：Browser 生命周期边界收口（零配置）

> 状态：✅ 已落地（2026-09-20）
> 关联：WEB-P0-2 / WEB-P1-1 / WEB-P1-6 生命周期治理线
> 设计原则：企业级——线程安全、清晰 API 边界、可观测性、健壮错误处理、护盾验证

---

## 1. 背景与动机

### 1.1 问题根因

当前 Browser 生命周期绑在 **thread**，唯一回收点是套件末的 `cleanupAll()`；而 Browser 服务的 Context 早已是 **per-scenario** 全新。这是一对不对称边界，并落入「全局单点清理」反模式——平时不回收、全堆到套件结束。

### 1.2 直接后果（用户已确认不可接受）

- 窗口从套件开始一直开到 `cleanupAll()`，体感「挂一整晚」。
- 跨场景残留浏览器级状态（service worker、进程级缓存）。
- 回收不可预测、不可观测。

### 1.3 触发

用户反馈「Browser 一直留到套件结束才统一关」不合理，要求更及时、更合理的回收策略。

---

## 2. 设计原则

1. **单一边界规则**：Browser 生命周期 = 其服务 Context 的边界（per-scenario）。一句话讲清，无例外。
2. **零配置**：不引入任何新开关（否决三档枚举 + 有界寿命护栏方案）。
3. **懒创建 + 就地回收 + 懒重建**：调用方零感知，行为零回归。
4. **线程隔离天然保证**：键 `<threadId>:<configId>`，并行下绝不误伤邻居线程。
5. **公开 API 零变更**：`getBrowser/getContext/getPage/cleanupAll` 签名与语义不变。
6. **最小改动面**：回收动作就地挂到既有 scenario `@After` 钩子，`cleanupAll()` 降级为兜底。

---

## 3. 目标架构

```
[scenario 开始]
   └─ 首次 getBrowser() ── 懒创建 (key=<threadId>:<configId>) ──► Browser OPEN
[scenario 执行]  (context 已 per-scenario 全新)
[scenario @After]  (顺序敏感，见 §7)
   ├─ drain page errors / api assertions        (既有)
   ├─ closeContext()                             (既有)
   └─ closeBrowserForCurrentThread()  ◄── 新增就地回收
[下一 scenario] 首次 getBrowser() ── 懒重建 ──► 新的 Browser OPEN
```

- **状态机**（单个 Browser 实例）：`ABSENT → CREATING → OPEN → CLOSING → ABSENT`。
- **归属模型**：Browser 归属 `(thread, scenario)`；并行引擎下每 scenario 独占一个 worker 线程，故归属 = 当前线程键。
- **`cleanupAll()`**：仅作进程退出 / 异常中断兜底，关闭任何残留实例；不再是主回收路径。
- **feature 模式例外（精确对齐）**：当 feature 模式跨场景复用同一 Context（session 恢复 / `reuse-context-within-feature`）时，Context 不随 scenario 关闭，Browser 亦随之保留、直到 feature 收尾才关——避免复用的 Context 随 Browser 关闭而失活。这正是「Browser 跟随 Context 边界」的精确含义：Browser 仅在本 scenario **实际关闭了 Context** 时才关。

---

## 4. 并发与线程安全

- **Cucumber 并行引擎**（标准，如 WEB-F1 冒烟）：每 scenario 跑在独立 worker 线程；`closeBrowserForCurrentThread()` 关的是当前线程键下实例，无跨线程干扰。并行峰值窗口数恒 = `parallelism`（不增不减）。
- **`ConcurrentContextExecutor` 分区模式**（SSO 互踢）：该模式 Browser 走分区共享、线程池复用语义不同，**不适用** per-scenario 关。设计显式护栏：当 `partition.enabled=true` 时跳过 scenario 级 Browser 关闭，仍走既有 per-thread 复用（避免跨线程键错配）。
- **可见性与误报防护**：复用既有 `CLOSING_BROWSERS`（弱引用同步 Set）登记，`BrowserCleanup.closeBrowserInstance()` 收口关闭；`registerBrowserDisconnectGuard` 据此把「主动关闭」判为 DEBUG，不冒真实崩溃 ERROR（沿用 WEB-P3-N14 治理）。
- **锁**：复用既有 lifecycle 锁，不引入新锁；严格保持既有锁顺序，杜绝死锁。

---

## 5. 错误处理

- 关闭失败**不得**影响 scenario 结果（teardown 阶段）：`closeBrowserInstance()` 异常不向外吞，由 `PlaywrightSerenityBridge` 调用点 catch 并降级为 WARN/DEBUG 记录。
- 重建失败：下一 scenario `getBrowser()` 经既有语义抛出 `BrowserException` 快速失败（与现状一致），不静默降级。
- 异常中断场景：`@After` 始终执行（无论 pass/fail），Browser 必被回收。

---

## 6. 可观测性

- 在 scenario 边界关闭 / 重建时，经 `LoggerFactory.getLogger(PlaywrightManager.class)` 打 INFO（含 `threadId` + `configId` + scenario 名），保持生产溯源一致。
- 可选：在 `ListenerPerfStats` 增加 `browserOpenCount / browserCloseCount` 计数器（轻量、不引入新依赖）。

---

## 7. 回收顺序（铁律，不可变更）

scenario `@After` 内严格顺序：

```
drainPendingPageErrors()         // 既有
replayFailures()                 // 既有
closeContext()                   // 既有（先关 context）
closeBrowserForCurrentThread()   // 新增（后关 browser）
```

**理由**：Browser 关掉后其内部 context 一并失效；若先关 Browser 再关 Context 会触发 `TargetClosedError` 噪声。顺序必须与现状 context 收尾一致。

---

## 8. 改动点清单（最小面）

| 文件 | 改动 |
|------|------|
| `PlaywrightSerenityBridge` | scenario `@After` 以 `scenarioClosedContext` 标记精准对齐 Browser 与 Context 边界：仅当本 scenario 实际关闭 Context 时（restart=scenario 或 feature 无 session 且无 `reuse-context-within-feature`）才在 `closeContext()` 之后调用 `closeBrowserForCurrentThread()`；feature 模式跨场景复用同一 Context 时（session 恢复 / `reuse-context-within-feature）不关，由 `cleanupForFeature` 收尾统一关 |
| `BrowserCleanup` / `PlaywrightManager` | 新增 `closeBrowserForCurrentThread()`：按当前线程键移除 `STATE.browserInstances` 条目 + 登记 `CLOSING_BROWSERS` + 经 `closeBrowserInstance()` 收口关闭 |
| `PlaywrightManager.cleanupAll()` | 保留；现为兜底（关任何残留），逻辑不变 |
| `ConcurrentContextExecutor` 相关 | 新增护栏：`partition.enabled=true` 时跳过 scenario 级 Browser 关闭 |
| `ConfigKeys` / `WebFrameworkConfig` | **回退**工作树中未提交的 `serenity.playwright.close.browser.after` 三档配置（不再需要） |
| `BrowserCloseAfterScenarioTest`（已有 untracked） | 固化：scenario 后当前线程 Browser 被移除 + 标记 `CLOSING_BROWSERS` + 下一 `getBrowser()` 重建 |

## 9. 测试策略（护盾）

1. **单元（Mockito，不启真实浏览器）**：`BrowserCloseAfterScenarioTest` —— 验证 `closeBrowserForCurrentThread()` 移除条目、标记 `CLOSING_BROWSERS`、下一 `getBrowser()` 懒重建；`@After` 统一 `resetInstance/resetProvider` 防污染。
2. **并行冒烟**：WEB-F1 `CucumberRouteDemoParallelSmokeRunnerIT`（8 scenario）验证：任意时刻 `browserInstances` 规模回到基线、无窗口残留、无 `browser disconnected` ERROR 误报。
3. **全护盾回归**：`mvn -o -pl test-automation -am test` 须 0 失败 / 0 错误 / 0 跳过（基线 ~528），证明行为零回归。
4. **并发回归**：并行冒烟 8 scenario 跨线程，断言无跨线程键错配、日志无新增 ERROR。

---

## 10. 风险与缓解

| 风险 | 缓解 |
|------|------|
| R1 每 scenario 重开 chromium 开销（数百 ms～1–2s） | 接受为「干净」代价；懒创建保证仅用 Browser 的 scenario 才付费；API-only scenario 为 no-op |
| R2 `ConcurrentContextExecutor` 分区模式跨线程键错配 | §4 护栏显式跳过 |
| R3 `@After` 顺序错乱导致 `TargetClosedError` 噪声 | §7 铁律顺序，先 context 后 browser |
| R4 scenario 未用 Browser（API-only） | `closeBrowserForCurrentThread()` 无条目时为 no-op，安全 |
| R5 长串行套件累计启动开销 | 不在本期引入性能开关；若后续确需，单布尔逃生舱另议（非本期范围） |

---

## 11. 验收标准

1. 零配置（无新增开关）。
2. 全护盾 0 失败 / 0 错误 / 0 跳过。
3. 并行冒烟下任意时刻 Browser 实例数 = `parallelism`，且单窗口存活 ≤ 一个 scenario 时长（不再挂到套件结束）。
4. 公开 API 零变更。
5. 无新增「browser disconnected ERROR」误报。

---

## 12. 回滚

改动局部、收口于 scenario `@After` 钩子与 `closeBrowserForCurrentThread()`；出问题 `git revert` 单个提交即可，不影响其余生命周期协作者。

## 14. 落地记录（2026-09-20）

### 14.1 实施结果

- 生效范围：`PlaywrightSerenityBridge.cleanupForScenario()`（仅 `scenarioClosedContext=true` 时）与 `cleanupForFeature()`；`ConcurrentContextExecutor` 分区模式显式跳过。
- 新增能力：`BrowserCleanup#closeBrowserForCurrentThread()` —— 经 `closeBrowserInstance()` 收口（登记 `CLOSING_BROWSERS`，使 `onDisconnected` 识别为预期关闭）+ 移除 `<threadId>:<configId>` 条目；**保留**同键 Playwright 实例，下一场景仅重建 Browser。
- 门面：`PlaywrightManager.closeBrowserForCurrentThread()` 委托组合根对外暴露。
- 配置：工作树中未提交的三档开关已回退，确认**零配置**。
- 顺序仍为「先 context 后 browser」（§7）；Browser 只按当前线程键操作（§4）。

### 14.2 新增可观测性（取代原临时诊断）

`PlaywrightContextManager.createContext()` 的 `context.onPage` 由「一律记成 `detected via window.open()`」改为**归属判定**：

| 情况 | 日志 | 级别 |
|------|------|------|
| `createPage()` 期间触发（框架受管页） | `New page created by framework (managed): ctx=#… pages=1 url=about:blank [about:blank until first navigate — expected]` | verbose INFO |
| 非框架创建（业务弹窗 / 测试直接 `newPage` / 泄漏） | `[multi-page] Extra page (not framework-managed): ctx=#… pages=N url=… aboutBlank=…` | INFO |
| 同 Context 页数 > 1 | `[multi-page] Context=#… now holds N pages (expected 1 managed): [managed]/[extra] (new) …` | WARN |

判据实现为纯函数 `classifyNewPageEvent(...)`（配 `NewPageEvent` + `logNewPageEvent(...)`），使「受管 vs 额外」可被单测**确定性**固化（不受 verbose 全局开关影响）。

### 14.3 同时移除的临时诊断（已被上述日志取代）

- `PlaywrightSerenityBridge.warnOnMultiplePagesPerContext()`（scenario 初始化时的多页告警）—— 命中时点晚于建页、信息量更低，实时判定已覆盖。
- `PageRegistryImpl` 建页处的多参 debug 诊断 —— 由 `New page created by framework (managed)` 取代。

### 14.4 验证（全绿）

- 新增单测 `PlaywrightContextManagerNewPageClassificationTest`：**6/0/0/0**（不启浏览器）。
- `BrowserCloseAfterScenarioTest`：固化 scenario 收尾关本线程 Browser + 下一 `getBrowser()` 懒重建。
- 全护盾 `mvn -o -pl test-automation -am verify -Pparallel`（含 WEB-F1 并行冒烟 `CucumberRouteDemoParallelSmokeRunnerIT`）：**BUILD SUCCESS**；IT `Tests run: 8, Failures: 0, Errors: 0, Skipped: 0`。
- 并行冒烟日志判定对账：受管页 8 / 额外页 0 —— 真实场景路径恒为「1 Context = 1 受管 Page」。

### 14.5 已知「额外页」来源（非框架缺陷）

- `ConcurrentContextNoDeadlockTest`：为触发 `onPage` 验证连接读线程不自死锁，刻意 `ctx.newPage()`。
- `RouteUnifiedBindingBrowserE2ETest`：弹窗继承路由规则的 E2E，刻意 `context.newPage()` + `navigate("about:blank")`。
