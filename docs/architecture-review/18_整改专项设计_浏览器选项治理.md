## 1. 背景与目标

doc16 在 `CustomOptionsManager` 内部面收敛（Phase 4）时，识别出两块**更深**的 Browser 选项耦合未在本专项穷尽，建议并入独立专项：

## 2. 现状扫描（代码锚点）

### 2.1 flag 写入三处直写（偏差 C 起源）
`web/.../lifecycle/context/CustomOptionsManager.java`：
- L129 `applyCustomOption`：`set(CUSTOM_CONTEXT_OPTIONS_FLAG_KEY, true)` + `scheduleContextRebuild()`（**置位且触发重建**）。
- L283 `disableCustomOptions`：`set(..., false)`（**仅置位、不重建**，javadoc 明示需调用方手动重建）。
- L294 `enableCustomOptions`：`set(..., true)`（**仅置位、不重建**，供 Feature 模式在 Context 失效时标记需应用 storageState）。

三处语义不同（是否触发重建），故收口只能统一「**写入**」这一动作，不能统一整条路径。

### 2.2 Feature 模式会话保留（偏差 B 核心）
`web/.../lifecycle/serenity/PlaywrightSerenityBridge.java` `resetCustomContextOptionsForFeatureMode()`（L157-183）：
- `cleanupThreadLocals(false)` —— **保留** storageState 键。
- `preserveStorageState(path, json)`（L166）—— 原样回填 storageState 路径/内存（不置位 flag、不重建）。
- 「**修复问题3**」（L170-181）：先快照 `existingContext` 存活态，再决定 flag：
  - context `null`/已断开 → `enableCustomOptions()`（置位 flag，不重建），待下次 `getContext()` 应用 storageState；
  - context 存活 → **不置位 flag**。

### 2.3 重建与 storageState 应用路径
- `ContextRegistryImpl.scheduleContextRebuild()`（L109-140）：设选项时立即关 Page+Context，下次 `getContext()/getPage()` 用新配置建全新 Context；**多次连续 set 只关一次**。
- `ContextRegistryImpl.recreateContextIfCustomConfigNeeded()`（L149+）：Context 已存在且 flag 置位时重建。
- `PlaywrightContextManager` 建 Context 时应用 storageState（L364-373，位于 `configureCustomContextOptions` 内部，**该方法整体被 flag 门控** L108/L141）：**优先内存 JSON（零文件 IO），否则退回文件路径**；storageState 与 locale/viewport 等全部自定义选项**同受 flag 控制**，flag=null/false 时不应用（详见 §4.4）。
- `ScenarioLifecycle.cleanupForScenario()`（L68-78）：先桥关 Page/Context（桥内 synchronized 取 `CONTEXT_KEY`/`PAGE_KEY`），**桥之后**才 `removeAllThreadLocals()`（含 storageState 键全部清除）—— Scenario 模式**不保留**会话。

### 2.4 模式差异小结（偏差 B 实质）
| 维度 | Scenario 模式 | Feature 模式 |
|---|---|---|
| scenario 结束清理 | `removeAllThreadLocals()` 全清 | `resetCustomContextOptionsForFeatureMode` 保留 storageState |
| storageState 跨 scenario | 不保留 | 保留（preserveStorageState） |
| 重建触发 | 选项 set → `scheduleContextRebuild` | 选项 set → 重建；Feature 重置时按 context 存活决定 flag |

## 4. 偏差 B 治理（待做）

偏差 B 拆为两子项，均**先表征、后修复**。

### 4.1 B-1：storageState 会话保留与 Context 重建竞态

**已知保护**（勿重复造轮子）：「修复问题3」（PlaywrightSerenityBridge L170-181）已对「检查存活 vs 设置 flag」做快照，缩小竞态窗口。

**待澄清的残留点**（需表征测试锁定，不臆断）：
1. 快照读取 `existingContext.browser().isConnected()` 在**无任何锁**保护下执行；窗口后至 `enableCustomOptions` 之间 context 仍可能变化（旧 bug 的弱化版，是否可接受需量化）。
2. Feature 重置时若 context **存活**：仅 `preserveStorageState`、不置位 flag、不重建 → storageState 虽已写入 TestContext，但**现有存活 Context 不含该 storageState**，需等下一次重建才生效。这是预期（不打扰存活 Context）还是缺口（登录态未及时复用）？须以测试固化当前行为。
3. storageState 应用经 `PlaywrightContextManager` 与 flag **解耦**（非空即应用）。需确认 Feature 模式「context 存活不重建」场景下，后续重建是否**必然**重新建 Context 并应用 storageState（即保留是否真生效）。

**表征测试计划（Phase 1）**：
- `FeatureModeSessionPreservationTest`：
  - 场景 A：Feature 重置时 context 已断开 → 断言下次 `getContext()` 新建 Context 且 `storageState` 被应用（内存 JSON 优先）。
  - 场景 B：Feature 重置时 context 存活 → 断言 storageState 已被 `preserveStorageState` 写回、且 flag 行为符合当前实现（记录实际值，作为回归基线）。
  - 场景 C：连续多次设选项 + Feature 重置 → 断言 `scheduleContextRebuild` 只关一次、storageState 不丢失。
- 上述测试**仅固化现状**，不改行为；若现状即预期，则 B-1 收口为「无代码改动 + 测试固化」。

**表征测试结论（Phase 1，2026-09-10）**：新增 `FeatureModeSessionPreservationTest`（4 例）+ `OptionModeParityTest`（2 例），全护盾 519 例绿、0 违规。锁定当前语义：
- flag 为装箱 `Boolean`，`removeAllThreadLocals()` 清除之；Feature 重置后 context 死亡 → `enableCustomOptions` 置 `true`，存活 → **返回 `null`（非 `false`）**；消费者 `PlaywrightContextManager` 以 `customFlag != null && customFlag` 安全处理（L107-108）。
- storageState 由 `preserveStorageState` 回填（与 flag 解耦），但其**实际「应用」发生在 `configureCustomContextOptions`，该方法被 flag 门控**（PlaywrightContextManager L107-108）。故存活 context 的 Feature 重置使 flag=null。但这**并非缺口，而是良性、符合设计**（详见 §4.3 运行时会话缓存语义）：① Feature 模式命中复用的是**存活 context**，session 早已在其内，无需重应用；② 任何「重建」路径（不同 user / 未命中后登录）均经 `SessionManager.restoreSession` 重新 `setStorageState`（L460/L499）→ 重置 flag 并触发重建重应用（先 cache 后文件）。因此 flag=null 只在「存活 context 被复用且不重建」时出现，此时 session 本就在 context 中。

**Phase 2 结论：无需改行为**，仅把上述契约显式固化（即本专项目标），防止后续误改——**禁止**在存活 context 的 Feature 重置中强行置位 flag（会违背「不打扰存活 Context」原则，并重新引入修复问题3 要避免的重建竞态）。
- Feature 模式保留 storageState 但清除 locale 等其它选项；Scenario 模式全清（含 storageState）。两模式差异已固化，作为回归基线。

### 4.3 运行时会话缓存语义（用户澄清 + 代码佐证）

偏差 B-1 的「flag=null → 不立即重应用」疑虑，结合完整会话语义后确认为**良性**。用户澄清的运行期行为（与 `SessionManager.restoreSession`，L419-510 一致）：

**Feature 模式**
- 首次登录 → `saveSession` 落盘 + Guava 内存缓存（`META_CACHE`），并建出含 session 的 Context。
- 同 Feature 后续 scenario 若 `isFeatureSessionRestored(sessionKey)` 命中 → **直接复用当前存活 Context**（L425-429，不清理、不重建），session 已在其内。
- 不同 user（sessionKey 变化）→ 丢弃当前 Context（保留 custom options，L434-444）→ 走重建；重建时 `restoreSession` 先查内存内容缓存 `getStorageStateContent`、回退本地文件 `getSessionPath` → `setStorageState` 重置 flag 并重建重应用（L460-465）。
- 跨 feature 文件：Guava 内存缓存与本地文件均**不被 Feature 重置清除**，故「先 cache 后文件」加载始终成立。

**Scenario 模式**
- 每个 scenario 结束 `cleanupForScenario` 全清 in-memory custom options（含 storageState 键），但**本地 session 文件与内存缓存不随之删除**。
- 下次 scenario 登录/重建时 `restoreSession` 命中 → 从 cache（优先）或本地文件加载 → `setStorageState` → 重建重应用（L450-465）；未命中则走真实登录（单飞协调 L484-510）。

**结论**：storageState 的「跨 scenario / 跨 feature 复用」由 `SessionManager` 的**文件 + 内存缓存**承载；`CustomOptionsManager` 的 in-memory storageState 键只是 `restoreSession` 的**中转产物**。`resetCustomContextOptionsForFeatureMode` 保留该键是为「丢弃/rebuild 后能立即回填」，存活 context 复用路径则不依赖它（session 已在 context 内）。两套机制职责清晰、互不冲突，偏差 B-1 **无需代码改动**。

### 4.4 flag（CUSTOM_CONTEXT_OPTIONS_FLAG_KEY）的存在意义（契约固化）

用户追问「flag 的存在还有没有意义」——经核对 `PlaywrightContextManager.createContext`（L97-149）与 `configureCustomContextOptions`（L361-375）真实代码，结论：**flag 非冗余，承载「一次性应用闩锁」语义，且是 Feature 模式复用/重建二分得以成立的关键**。澄清：原 §2.3「storageState 与 flag 无关」表述不准确——storageState 应用点位于被 flag 门控的方法内部，故与全部自定义选项同受 flag 控制。

flag 的四重含义：
1. **一次性应用闩锁（核心）**：自定义选项（含 storageState）仅在 `createContext` 时 flag=true 才被 `configureCustomContextOptions` 应用，且应用后 `finally` 中 `disableCustomOptions` 立即复位 false（L141-144）。数据键可长期存活（Feature 模式保留 storageState 键供重建回填），但应用是**一次性**的，不泄漏到无关后继 context 构建。
2. **重建协调信号**：`applyCustomOption` 置 flag + `scheduleContextRebuild`；`ContextRegistryImpl.recreateContextIfCustomConfigNeeded` 据 flag 判断是否重建并应用。`enableCustomOptions`（不重建）仅置 flag，交由后续 `getContext()` 触发重建应用——此路径下 flag 是**唯一**信号。
3. **显式 opt-out**：`disableCustomOptions`（flag=false）表达「数据键仍在但本次构建不应用」，无法用「键是否存在」表达（键非空而本次不应用只能靠 flag）。
4. **支撑 Feature 二分**：`resetCustomContextOptionsForFeatureMode` 存活 context 分支令 flag=null（不置位、不重建、session 已在存活 context 内）；死亡 context 分支 `enableCustomOptions` 置 flag=true（下次重建重应用）。正是 flag 与数据键的**独立生命周期**使「复用存活 / 重建重填」两种语义并存不串扰。

> 若移除 flag、改为「数据键非空即应用并清空键」，将破坏 Feature 模式 storageState 跨 scenario 保留（清空键后重建无法回填），故 flag **不可删**，且禁止在存活 context 的 Feature 重置中强行置位 flag（违背一次性闩锁、并重新引入修复问题3 的重建竞态）。

### 4.5 并发语义（契约固化）

用户追问「并发运行如何？」——核对 `TestContextHolder`（`ConcurrentHashMap<Thread, TestContext>`，per-thread）、`CustomOptionsManager`（无状态单例，全状态经 `TestContextHolder.get()` + `ContextKey`）、`SessionManager`（按 sessionKey 单飞的 `loginGuards` + Guava `META_CACHE` `concurrencyLevel(16)` 单飞加载）后结论：

**1. flag / 自定义选项 / Feature 标记均为 per-thread（天然隔离）**
- `CUSTOM_CONTEXT_OPTIONS_FLAG_KEY`、`CUSTOM_STORAGE_STATE_KEY`、`FEATURE_SESSION_RESTORED`、`CURRENT_FEATURE_SESSION_KEY` 全部存于 `TestContextHolder`（per-thread）。N 个并行 scenario = N 份独立 flag/storageState/Feature 标记，`CustomOptionsManager` 无共享可变状态。
- 故并发场景下**任意线程设置 flag / 置 storageState / `enable/disableCustomOptions` 只影响本线程的下一个 `createContext`**，不串扰其它线程。本专项「一次性应用闩锁」语义在并发下依然成立、无需加锁。

**2. 唯一共享层是 SessionManager（按 sessionKey，非 per-thread）——已协调**
- 会话文件（`target/.sessions/<key>.json`）、内存缓存、登录单飞守卫 `loginGuards`（ConcurrentHashMap per sessionKey）跨线程共享，键为 sessionKey（user/env）而非线程。
- 不同 sessionKey 并行 → 不同文件，零竞争。
- 同 sessionKey 并行首次无文件 → `acquireOrAwait`（L528）单飞：仅一个 leader 真实登录，follower 等待后复用落盘文件（L494-510），避免 SSO 单会话互踢。

**3. 关键安全属性：storageState 在 `newContext` 时即被 Playwright 快照进 Context**
- `setStorageState(JSON)` 的内容在 `createContext` 经 `configureCustomContextOptions` 传入 `newContext` 后即固化进该 BrowserContext（副本，不再引用 `CUSTOM_STORAGE_STATE_KEY`）。故某线程后续改/清 storageState 键**不影响**其它线程已建好的 Context。这正是并发安全的核心。

**4. 仍须业务层约束的边界（非代码竞态，属业务级争用）**
- 同 user 真正并行（未开 `partition.enabled`）且其中一个 scenario 执行登出/清 session（`clearSession`/`saveSession` 改写共享文件），另一线程下次 `restoreSession` 将找不到文件 → 重登 → 触发 SSO 互踢。缓解由 `SessionManager` 单飞 + `partition.enabled=true`（同身份串行，见并发方案设计）承担，**不属本专项 CustomOptionsManager 范畴**。
- 并发执行器（ConcurrentContextExecutor）经 `TestContextHolder.capture/restore` 传播上下文，Feature 标记随之传播；但「复用存活 Context」仅限同一 worker 线程内的 scenario 序列，跨线程并行 scenario 各自建独立 Context（正确语义）。

**结论**：flag 与自定义选项治理在并发下**线程安全、无需改动**；共享争用仅发生在 SessionManager 的 per-sessionKey 文件/缓存，已有单飞协调。本专项不引入新的并发风险。
