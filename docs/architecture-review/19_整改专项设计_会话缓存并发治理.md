# 整改专项设计：会话缓存并发治理（Session Cache Concurrency Governance）

> 来源：`18_整改专项设计_浏览器选项治理.md` §4.5（浏览器选项治理专项识别的唯一残叉并发风险）
> 状态：**已完成** —— Phase 1 ✅（3 例绿）+ Phase 2 ✅（2 例绿，mock provider 无真浏览器），2026-09-10；Phase 3 ✅（全护盾暴露的 `evictIfExpired` 读盘竞争风暴根治，2026-09-10，commit a8602c4 @ DEV-V3）。专项共 5 例表征测试 + 1 处生产代码修复，固化 per-sessionKey 共享层并发契约
> 关联：`18`（浏览器选项治理）、T3-6（`SessionManager` 并发缓存）、`12`（CORE-P0-2 线程模型）、`13`/WEB-P0-2（可测试性 DI seam，供 Phase 2 单飞表征）

## 1. 背景与目标

doc18 §4.5 结论：flag / 自定义选项 / Feature 标记均为 per-thread（`TestContextHolder` = `ConcurrentHashMap<Thread, TestContext>`），并发天然隔离、无需加锁；**唯一共享层是 `SessionManager` 的 per-sessionKey 文件 / 缓存**（`META_CACHE`、`STORAGE_CONTENT_CACHE`、`loginGuards` 单飞），已有单飞协调。

但经核查既有测试：
- `SessionManagerCacheTest`（3 例）：仅**单线程**的 meta 缓存 / `clearSession` 失效 / 过期淘汰删除文件。
- `SessionManagerConcurrencyTest`（1 例）：仅 **per-thread Feature 标记隔离**（经 `TestContextHolder`），**未触及 per-sessionKey 共享层并发**。

故 **per-sessionKey 共享层并发语义从未被表征**。本专项以表征测试先行锁定当前并发契约，确认无数据竞争 / 文件损坏 / 未捕获异常，杜绝回归。本专项目标与 doc18 一致：**表征优先，无行为变更**。

**非目标**：`restoreSession`/`saveSession` 的真浏览器路径（需 `PlaywrightManager.getContext()`）——其单飞由 Phase 2 经 WEB-P0-2 mock provider 表征（无真浏览器）。

## 2. 现状扫描（代码锚点）

`web/.../web/session/SessionManager.java`：
- L70-96 `loginGuards`：`ConcurrentHashMap<String, LoginGuard>`，`CountDownLatch` 单飞（同 sessionKey 仅一个 leader 真实登录，follower 复用落盘）。
- L108-118 `META_CACHE`：Guava `LoadingCache` `concurrencyLevel(16)` 单飞 `load`（同 key 并发仅一个线程读盘）。
- L130-143 `STORAGE_CONTENT_CACHE`：Guava `LoadingCache` `expireAfterAccess`，加载器读 canonical `<key>.json` 一次。
- L356-370 `hasSession`（private）：触发 `evictIfExpired`。
- L378-396 `evictIfExpired`（private）：删 `.json`/`.meta` + `META_CACHE.put(ABSENT_META)`（粘滞化 absent 态，替代原 `invalidate`，消除读盘竞争风暴，见 §8），被 `loadHomeUrl`/`hasSession` 复用（"失效即删除"集中收口）。
- L582-629 `saveSession`（public）：**需 `BrowserContext`**（L596 `getContext()`）→ 非浏览器自由。
- L419-510 `restoreSession`（public）：命中路径调 `PlaywrightManager.getContext()`（L465）→ 非浏览器自由。

**浏览器自由、可无浏览器表征的 public 入口**：`loadHomeUrl` / `getHomeUrl` / `clearSession`（均经文件 + `META_CACHE`，不触真浏览器）。

## 4. 表征测试计划

### Phase 1（无浏览器，纯文件 / 缓存层）
`SessionManagerSharedConcurrencyTest`（同包 `web.session`，复用 `SessionManagerCacheTest` 的「直接写 `.meta`/`.json` 搭建状态」手法，避免真浏览器）：
- **场景 A 并发读一致**：写有效 session 文件，N 线程各并发 `loadHomeUrl(key)` 多轮 → 全部返回同一 `homeUrl`、零异常（锁定 `META_CACHE` 单飞 + 读盘一致性）。
- **场景 B 删除 / 读取竞争**：写有效 session，N 线程一半 `clearSession(key)`、一半 `loadHomeUrl(key)` 并发 → 终态稳定（`loadHomeUrl` 重复调用返回值不变），且每轮返回值**非 null 即精确 `homeUrl`**（从不返回半写 / 损坏串），零异常、文件不损坏。
- **场景 C 过期并发驱逐幂等**：写**已过期** session（lastAccessTime 远早于超时），N 线程并发 `loadHomeUrl(key)` → 全部返回 `null`、磁盘文件被删一次、零异常（锁定 `evictIfExpired` 并发幂等，重复删除被 catch 降级而非抛）。

### Phase 2（mock provider 单飞，无真浏览器）
- 经 WEB-P0-2 `RuntimeProvider` seam 注入 mock `Browser`/`BrowserContext`，`restoreSession` 同 key 并行时断言**仅一个 leader 触发 `saveSession` 路径**（单飞），follower 在 leader 完成后复用落盘、不二次登录；`STORAGE_CONTENT_CACHE` 单飞随之被覆盖。

## 6. 表征测试结论（Phase 1，2026-09-10）

新增 `SessionManagerSharedConcurrencyTest`（3 例），`mvn -o -pl test-automation -am test -Dtest=SessionManagerSharedConcurrencyTest` → **Tests run: 3, Failures: 0, Errors: 0, BUILD SUCCESS**。本次无生产代码改动，既有护盾不受影响。

锁定契约：
- **并发读一致**：8 线程 × 200 轮同 key `loadHomeUrl` → 全部返回同一 `homeUrl`、零异常（`META_CACHE` Guava 单飞 + 读盘一致成立）。
- **删除 / 读取竞争终态稳定**：8 线程混合 `clearSession` × `loadHomeUrl` × 100 轮 → 每轮读取仅观测 `null` 或精确 `homeUrl`（文件不被并发写损坏）；竞争结束后连续读取返回值恒定，零异常。
- **过期并发驱逐幂等**：8 线程 × 100 轮对已过期 session 并发 `loadHomeUrl` → 全部返回 `null`、零异常（`evictIfExpired` 并发幂等）。

**表征中暴露的良性边界（已处理，无需改行为）**：Windows 并发删除过期 `.json` 偶发 `java.nio.file.AccessDeniedException`（另一线程持句柄），被 `evictIfExpired`（L387-391）`catch (Exception)` 捕获并降级为 WARN（不抛、不损坏、幂等），过期文件最终由胜出线程删除。此属平台级文件锁竞争，已被现有 catch 正确兜住，佐证「并发安全、无需改动」结论。

**结论**：per-sessionKey 共享层并发契约经表征确认成立（线程安全、无损坏、无未捕获异常），与 doc18 §4.5「flag/选项 per-thread 隔离 + SessionManager 单飞协调」判定一致。偏差 B-1 同款「无行为变更、仅表征固化」收口路径延续。

## 8. Phase 3：全护盾暴露的读盘竞争风暴根因修复（2026-09-10，commit a8602c4 @ DEV-V3）

### 8.1 现象
专项收口后，在 528 例全护盾高负载回归中，`SessionManagerSharedConcurrencyTest.concurrentExpiredEviction_idempotentAndNoException`（场景 C：8 线程 × 100 轮过期并发 `loadHomeUrl`）偶发 30s 超时（`done.await(30, SECONDS)` 返回 false），隔离重跑则稳定全绿。属**活性（liveness）缺陷**：并发同 key 读取在高负载下未及时收敛，非断言错误、非数据损坏、非文件损坏。

### 8.2 根因
`evictIfExpired` 每次驱逐调用 `META_CACHE.invalidate(key)`，形成 **invalidate → 缓存 miss → 重新读盘** 的读盘竞争风暴：
- 8 线程 × 100 轮，每轮因 `invalidate` 必触发一次磁盘 `Files.exists` 探测（已删除文件），累计 ~800 次冗余磁盘读；
- 叠加 `evictIfExpired` 内部 `isSessionExpired(String)` **二次读盘**（自身一次 + 内部一次）；
- 528 例全护盾多模块并行（含真浏览器 E2E）下 CPU/磁盘争用，读盘竞争累积超 30s → 超时。

`evictIfExpired` 的并发幂等本身是**正确**的（重复 delete 被 `catch` 降级、零未捕获异常），问题纯在性能/活性，非并发安全。

### 8.3 修复（`web/.../web/session/SessionManager.java`，commit a8602c4）
1. **absent 态粘滞化**：驱逐后由 `META_CACHE.invalidate(key)` 改为 `META_CACHE.put(key, ABSENT_META)`。并发同 key 后续读取直接命中内存（与重新读盘得到的 `ABSENT_META` 等价但零 IO），从根上消除读盘竞争风暴。首个驱逐线程 `put` 后，其余线程以自身已加载的过期 meta 判 `isSessionExpired(meta)=true` → 重复 `delete` 被 `catch` 降级、`put` 幂等覆盖，全程零未捕获异常；`saveSession` 落盘后以新鲜值覆盖本条目，不掩盖真实写入。
2. **去冗余二次读盘**：`isSessionExpired(String)` 改为 `isSessionExpired(SessionMeta meta)`，复用 `evictIfExpired` 已加载的 meta，不再重复 `META_CACHE.get`。

行为零变更：过期驱逐的对外语义（返回 `null`、删盘、幂等）与缓存契约（命中/失效）完全等价，仅内部缓存失效策略由「invalidate」转为「粘滞化 absent」。

### 8.4 验证
- 隔离重跑 `SessionManagerSharedConcurrencyTest` **3 次全绿**（3/3，~1.3–1.5s，此前 30s 超时）；
- `SessionManagerCacheTest` 三契约（缓存存活 / `clearSession` 失效 / 过期驱逐删文件）不受影响；
- **全护盾 528 例 0 失败 / 0 错误 / 0 跳过，BUILD SUCCESS**（commit a8602c4，分支 DEV-V3）。
