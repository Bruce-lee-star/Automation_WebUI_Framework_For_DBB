## 1. 结论摘要（直接回答三个问题）

| 你的问题 | 结论 |
|---|---|
| **会不会出现时序竞态？** | **会，且已定位到 4 处真实竞态窗口 + 6 处潜在竞态。**最严重的是线程归属守卫自身的惰性确立是 check-then-act（`PageContextState:214-227`）——**并行安全的唯一根锚点本身不可靠**；其次是登录单飞超时后 follower 自任 leader 而原 leader 未被取消（`SessionManager:660-668`）→ 同 sessionKey 双登录；脱敏识别器被两把锁保护同一状态 → 丢失更新可致**值级脱敏静默失效**（合规红线）。 |
| **会不会资源泄漏？** | **会。已确认 1 处 FATAL 级泄漏路径 + 5 处中高危。**FATAL：`PlaywrightContextManager.createContext()` 在 context 已建件后若注册监听/配超时/启 tracing 抛异常，**finally 只重置标志、不关闭 context** → 每失败一次泄漏一个 BrowserContext（headed 下即一个真实窗口 + 一个 Chromium 进程）。运行期佐证极强：`hs_err_pid30332.log:660-663` 崩溃时**本 JVM 峰值工作集仅 337M**，而系统 24.4G 仅剩 2076M、页面文件 37.8G 仅剩 **4M** —— 耗尽内存的主体不是被测 JVM，最可能是**未被回收的浏览器进程/残留 JVM**。 |
| **会不会线程未即时清理？** | **会。**4 个静态观测池（`MonitorHandler`）与 `modify-observe` 池**从不 `shutdown()`**，靠 JVM 钩子兜底；`ModifyHandler.observeExecutor` **未纳入套件收尾排空**（`RouteLifecycleImpl:79-84` 只 drain MonitorHandler + FileStore）；`AsyncPool` 关闭是**单向门**且 `LazyInit` 无 reset → 关闭后所有异步任务**静默 no-op**；`pendingScheduleCount`/`pendingTimeoutCount` 计数不配对 → 观测失真并最终**静默失去超时保护**。 |

**整体判断**：这不是"框架不会并发"，而是**"并发闸门造得很好，但闸门上的铰链有三处是活的"**。骨架（依赖倒置、SPI、ArchUnit 门禁、有界队列、daemon 线程、ShutdownCoordinator 编排）明显是受过良好并发训练的设计；但**最后一段"异常路径 / 超时路径 / 关闭路径"的系统性收口仍不完整**——而这三条路径恰好是并发缺陷的唯一藏身处。

**并发专项评级：3.4 / 5**（设计意图 4.3，异常与关闭路径落实 2.5）

## 3. FATAL 详表（逐条：证据 · 为何是真问题 · 爆炸半径 · 修复 · 验收）

### CT-01 · 线程归属守卫的惰性确立是 check-then-act【已验证】

**证据**（`PageContextState.java:214-227`）
```java
private void assertOwningThread() {
    Thread current = Thread.currentThread();
    Thread owner = this.ownerThread;      // volatile：只保证可见性
    if (owner == null) {
        this.ownerThread = current;       // ← 读-判-写 三步非原子
        return;
    }
    if (owner != current) { throw new IllegalStateException(...); }
}
```
仅两处调用：`ensurePageValid():133`、`ensureContextValid():203`。

**为何是真问题**：`volatile` 提供可见性，**不提供复合操作原子性**。两个线程可同时读到 `owner==null`、各自写入、**双双 return 通过**。而这个守卫是整个并行安全模型的**唯一根锚点**——框架注释自述"把 Playwright 非线程安全的跨线程共享 Page 导致 `pipe closed` 类诡异失败转为清晰异常"。锚点自己漏了，后面所有"并行安全"结论都失去依据。

**爆炸半径**：`SINGLETON` 策略页面对象、被手工共享的 BasePage、场景上下文未绑定而回退线程键的路径。一旦漏过首帧，后续 `ensurePageValid` 会在同一 Playwright `Page` 上并发 `isClosed()/locator()`（官方明确 Page/Context/Locator 非线程安全）。当前测试集**零 cross-thread 断言覆盖**（grep `assertOwningThread|ownerThread` 于 `web/src/test` 无命中）——即该守卫从未被并发测试验证过。

**修复**：改用 `AtomicReference<Thread>`：
```java
private final AtomicReference<Thread> ownerThread = new AtomicReference<>();
private void assertOwningThread() {
    Thread current = Thread.currentThread();
    Thread owner = ownerThread.compareAndExchange(null, current); // 原子确立
    if (owner != null && owner != current) { throw new IllegalStateException(...); }
}
```
并补 `*ConcurrencyTest`：N 线程共享一个 BasePage 首次并发访问，断言"恰好 1 线程通过 / N-1 抛明确异常"。

**验收**：新增测试在上述实现下稳定通过；回退修复（`set(null)` 前）该测试必红。

### CT-02 · `createContext()` 半初始化泄漏【已验证】

**证据**（`PlaywrightContextManager.java:99-143`）
```java
BrowserContext context;
try {
    context = currentBrowser.newContext(contextOptions);   // ← 资源已创建
    context.onPage(...);                                   // ← 以下任一步抛异常
    PageEventMonitor.register(context);
    PageInteractionMonitor.register(context);
    registerDownloadHandler(context);
    configureTimeouts(context);
    enableTracing(context);                                //   例：trace 写盘失败
} finally {
    if (customFlag != null && customFlag) {                //   仅重置标志
        CustomOptionsManager.getInstance().disableCustomOptions();
    }
}                                                          //   ✗ 无 context.close()
return context;
```

**为何是真问题**：`newContext()` 成功即已占用一个真实浏览器上下文（headed 下是一个窗口 + 一个 Chromium renderer 进程，每个约 50–150MB RSS）。异常路径下该对象**无任何引用逃逸、也无 finally 关闭**，只能等套件级 `cleanupAll()` 兜底。这是典型"**资源已分配 + 异常路径无回收**"形态，不是设计取舍。

**爆炸半径**：`enableTracing` 在 CI（磁盘配额、并发写 trace 文件）与本地（磁盘近满）都易失败；`PageEventMonitor/PageInteractionMonitor.register` 遍历配置项也可能抛。每次失败泄漏一个窗口级资源。**这与 CT-20 的 native OOM 形态完全吻合**：崩溃时本 JVM 工作集只有 337M，说明吃内存的主体在 JVM 之外（浏览器进程/其它 JVM）。

**修复**：
```java
boolean ok = false;
try {
    context = currentBrowser.newContext(contextOptions);
    ...全部注册...
    ok = true;
} finally {
    if (!ok && context != null) { safeCloseIfAlive(context); }   // 半初始化即回收
    if (customFlag != null && customFlag) { disableCustomOptions(); }
}
```
注意 `context` 需先在 try 外声明并初始化 `null`。

**验收**：新增单测——用 Mock 使 `enableTracing` 抛异常，断言 `newContext` 产出的 context 被 `close()`（可经 `context.isClosed()` 或计数探针验证）。

### CT-03 · MockHandler 在 Playwright 事件线程同步 `route.fetch()`（≤30s）【已验证】

**证据**
- `MockHandler.java:242`：`APIResponse realResp = route.fetch(fetchOpts);`
- `:49-50`：`ROUTE_FETCH_TIMEOUT_MS = RouteUtil.getEnvDouble("ROUTE_FETCH_TIMEOUT_MS", 30000)`
- `:236-239` 注释**自述**："Playwright 的 `route.fetch()` 会在【事件线程】同步等待真实服务器返回"
- 分发链：`Dispatcher` 仅对 **MOCK+DELAY** 走延迟线程（`Dispatcher.java:260-265`），其余一律 `HandlerExecutor:229 handler.handle(...)` **同步**执行
- 反证：`MonitorHandler.handle():471-477` 明确声明"事件线程不再阻塞，只做轻量登记后立即返回"；`ModifyHandler.handle():188-204` 同样下沉线程池

**为何是真问题**：Playwright Java 用**单一连接派发线程**执行 route/handler 回调。在该线程上做 ≤30s 的同步网络等待，等于把"后端慢"放大成"该 context 下所有页命令与路由分发全部排队"。Monitor 与 Modify 都已整改，**唯 Mock 漏改**——这不是权衡，是遗漏。

**爆炸半径**：任一 `interceptRealResponse=true` 的规则；后端降级/网络抖动时触发；并行度越高、单 context 上 API 越密，越接近必现。表现是**难以归因的级联超时与假失败**（用例失败点与真正根因相隔很远）。

**修复**（二选一，建议 A）：
- **A（对齐 Monitor）**：`handle()` 只做 `isPageClosed` 守卫 + 登记，把 `fetch → 替换 → fulfill` 整体提交到专用 `ThreadPoolExecutor`（有界队列 + `AbortPolicy` + **拒绝时 `route.resume()` 放行并 `signalFailFast`**）。
- **B（最小改动）**：把 `ROUTE_FETCH_TIMEOUT_MS` 默认从 30000 降到 3000，并加熔断（连续 N 次 fetch 超时即对后续请求直接 `resume` 并记数据丢失）。

**验收**：用 `route-demo-service` 的 `SlowController`（既有慢接口夹具）造 10s 慢响应，断言"事件线程被占时长 < 500ms"（可用 `page.evaluate` 往返延迟度量）。

### CT-04 · 登录单飞超时后 follower 自任 leader，原 leader 未取消【已验证】

**证据**（`SessionManager.java:660-668`）
```java
boolean completed = existing.await(SINGLE_FLIGHT_TIMEOUT_MS);
if (!completed) {
    loginGuards.remove(sessionKey, existing);      // ← 摘掉守卫
    LOGGER.warn("... Timed out {}ms waiting ... → proceeding as leader", ...);
    return null;                                   // ← 本线程成为 leader，去执行真实登录
}
```
**关键缺口**：`existing`（原 leader）从未被 `interrupt()`、也没有"作废"标记；它仍会跑完真实登录并在成功后 `saveSession`。

**为何是真问题**：单飞（single-flight）的正确性依赖"**最多一个执行者**"。超时后接替 leader 而原 leader 继续执行 ⇒ 变成"**至少两个执行者**"。注释把超时归因为"leader 超时未落盘（登录失败/被中断/业务层未调 saveSession）"，但**这恰恰是最危险的情形**——被误判为"已死"的 leader 其实还活着。

**爆炸半径**：同 sessionKey 两次真实登录 → 服务端单会话策略互踢 → **随机 401 / 会话漂移 / 断言点漂移**。并行度提高、登录链路变慢时概率显著上升。这类失败最难排查（现象在登录之后的任意步骤，根因在登录之前）。

**修复**：
1. 给 `LoginGuard` 加 `invalidated`（`AtomicBoolean`）；超时分支先 `existing.invalidate()`，leader 在 `saveSession` 前检查 `invalidated`，若已作废则**放弃落盘并回滚**；
2. 或把 `SINGLE_FLIGHT_TIMEOUT_MS` 提到**严格大于登录最坏耗时**（含重试与 MFA），并在超时分支直接**抛异常**而非接替（fail-closed，让问题显形）；
3. 补测试：`SessionManagerRestoreSingleFlightTest` 已有并发骨架，追加"leader 慢于超时"用例，断言"真实登录恰好 1 次"（用计数探针）。

## 4. HIGH 详表（要点）

### 4.1 CT-06 · `MonitorHandler` 无超时 `join()` + `delayedExecutor` 落 commonPool【机制已验证/时序疑似】

**证据**
```java
// MonitorHandler.java:438-440
final CompletableFuture<Response> fut = new CompletableFuture<>();
scheduleExistingResponsePoll(fut, route, req, observationContext, deadlineNs);
return fut.join();                                  // ← 无超时！

// :463-465  —— 两参重载，无自定义 scheduler
java.util.concurrent.CompletableFuture.delayedExecutor(
        (int) EXISTING_RESPONSE_POLL_MS, TimeUnit.MILLISECONDS)
    .execute(() -> scheduleExistingResponsePoll(fut, route, req, observationContext, deadlineNs));
```
对照同文件 `:1015-1018` 的 `readResponseBodyWithRetry` **正确传了** `bodyReadScheduler`：

```java
CompletableFuture.delayedExecutor(intervalMs, TimeUnit.MILLISECONDS, bodyReadScheduler)
```
**同一文件内两种写法** → 属漏改，非风格差异。

**为何是真问题**：`fut.join()` 的完成完全依赖轮询链走到 `complete(...)`。而轮询体 `scheduleExistingResponsePoll` **没有任何 try/catch**：`req.existingResponse()`（:454）或 `RouteContextState.isContextClosed`（:449）抛任意 `RuntimeException`，或 commonPool 侧提交被拒，异常都会**吞在 Delayer/commonPool 线程里**，`fut` 永不完成 → `join()` **永久阻塞**。`deadlineNs` 只在轮询体内部被检查，**对"轮询链已断"这种情况不起作用**。

**爆炸半径**：`observationExecutor` 固定 8 线程（`MONITOR_OBSERVE_THREADS` 默认 8，:121）。每永久阻塞一个就少一个；逐个耗尽后所有后续观测走降级快照 → `signalFailFast` → **大面积假失败**。此外 commonPool 是**全局共享**资源，在 Windows/单核容器上并行度可退化为 0，会拖慢所有依赖 commonPool 的代码。

**修复**：
1. `delayedExecutor(ms, unit, scheduler)` 传入自建 `bodyReadScheduler`（或新建 `pollScheduler`）；
2. `fut.join()` → `fut.get(capMs + SLACK_MS, TimeUnit.MILLISECONDS)`，`TimeoutException` 时 `complete(null)` 并计数；
3. 轮询体包 try/catch，异常 → `complete(null)` + `MonitorDataLossReporter.recordLoss`。

### 4.2 CT-07 / CT-08 · AsyncPool「关闭单向门」与「超时计数泄漏」【已验证】

**CT-07 详解**：`AsyncPool` 的 `INIT = new LazyInit(...)`（:136）；`LazyInit.ensure()` 成功后 `initialized=true` **永不重跑且无 reset API**（`LazyInit.java:56-80`）。`shutdown():547-552` → `shutdownGracefully():441-499` 只关池，**不改 INIT 状态**。于是关闭后：
`submitTask` → `ensureInitialized()` 静默通过 → `POOL.submit` 抛 `RejectedExecutionException` → 被 `:291-299` 的**既定策略捕获并丢弃**（仅 `droppedOnRejectionCount++` + ERROR 日志）。

**为何是 HIGH**：调用方包括 `ApiTrafficLogger.record`（监控落盘）、monitor 回调、各类收尾任务——它们全部**静默失效且不影响用例结果**，属"最不可见的一类故障"。触发场景真实存在：`ShutdownCoordinator.reset()` 的设计目标就是"支持套件内重 init"（:130-139）。

**CT-08 详解**：
```java
pendingTimeoutCount.incrementAndGet();                 // :272
SCHEDULER.schedule(() -> { ... finally { pendingTimeoutCount.decrementAndGet(); } }, ...);  // :273 / :287
```
`schedule` 抛 `RejectedExecutionException` → 直接被外层 `catch (RejectedExecutionException e)`（:291）接走 → **287 行的 finally 永不执行**。计数单调上升到 `MAX_PENDING_TIMEOUTS`(500) 后，`:262` 的守卫让**所有** `runWithTimeout` 都不再投哨兵：
> "退化为「不强制超时」（任务仍会执行），并计数 + ERROR 留痕（不静默）"

——即**全进程静默失去超时保护**。而 `AsyncPool` 承载的正是"防挂死"类任务，这是保护机制自身的单点失效。

**修复**：
```java
// 先 schedule 成功，再增计数；或者用 try/catch 归还
try {
    SCHEDULER.schedule(sentinel, timeoutMs, MS);
    pendingTimeoutCount.incrementAndGet();
} catch (RejectedExecutionException rex) {
    LOGGER.warn("[AsyncPool] timeout sentinel rejected; task runs without timeout enforcement");
}
```
另增 `AsyncPool.resetForNewRun()`（配套 `LazyInit.reset()`）：重新读配置 → 建池 → 重新登记 ShutdownCoordinator，使"关闭可逆"。

### 4.3 CT-09 · MODIFY 拒绝 fail-open（丢断言不判红）

`ModifyHandler.java:195-203` 与 `MonitorHandler.java:547-556` 的策略**不对称**：后者走 `onObservationRejected(...)` → `signalFailFast` + `MonitorDataLossReporter.recordLoss`；前者只有 `warn` + `safeResume`。

后果是"**叠加 monitor 的 MODIFY 规则在高负载下静默丢断言 → API 假绿**"——这正是框架自己在 `MonitorHandler` 里花大力气消除的模式（RT-OBS 专项）。修复即对齐 MonitorHandler 的两步：`signalFailFast` + 数据丢失上报。

### 4.4 CT-11 · Context 重建路径绕过统一收口

统一收口在 `ContextRegistryImpl.closeContext():197-237`，它做了 6 件事：`RouteRegistry.clearContext` → codegen cleanup → `RouteEngine.stopContextEngine` → `PlaywrightContextManager.closeContext` → 清 `CONTEXT_KEY`/`CURRENT_CONTEXT_BY_THREAD` → **无条件**清 `TestServices` 与 `CustomOptionsManager` ThreadLocal。

而两条重建路径（`:120-134` 与 `recreateContextIfCustomConfigNeeded():146-174`）**只做 `existingContext.close()`**，前 4 项全部跳过。尤其 `stopContextEngine` 缺失会留下 `AsyncPool.CONTEXT_SCHEDULERS` 条目与守护线程；`DownloadRegistry` 以 **BrowserContext 强引用** 为键 → 条目无法回收。会话切换（`applyStorageState`）路径频繁触发重建，因此这是**热点路径**上的泄漏。

**修复**：把重建路径改为调用 `closeContext()`（或在关闭前后统一走同一个 `closeContextInternal(context)` 私有方法），不要在第二个地方重复实现"关 context"。

**解读**：并行下 Context 按 scenario 高频创建/关闭。这正是 CT-02（异常路径泄漏）与 CT-11（重建绕过收口）的**放大器**——单次泄漏在串行下被套件 `cleanupAll` 吸收，在并行高频重建下会累积成可观测的窗口/进程堆积。

## 9. 已确认健康清单（**勿返工**）

**线程与退出**
- 全部框架自建线程均为 **daemon**：`AsyncPool:92/166/183/365`、`MonitorHandler:101/128/158/187`、`ModifyHandler:99`、`DelayScheduler:202`、`ConcurrentContextExecutor:249`、`ScenarioTraceRecorder:83`、`ElementDiagnosticsCollector:56`、`BrowserStackLocalManager:277` → **不存在"JVM 无法退出"问题**（此前若有此类怀疑可直接撤销）。
- 多处登记 `ShutdownCoordinator`：`AsyncPool:199`、`MonitorHandler:257`、`ModifyHandler:70`、`RouteEngine:41`、`FileStoreMonitorCallback:152`、`ApiMonitoringRepository:245`、`HikariConfigFactory:108`、`ElementDiagnosticsCollector:65` → 退出期有统一编排。
- `ConcurrentContextExecutor.runAll` 在 `finally` 内 `shutdown → awaitTermination → shutdownNow`（:120-133），无池泄漏；`RUNNING.set(true)` 已移入 try（:97），修掉了"构造失败导致清理门控永久卡死"的历史缺陷。

**route 深度**
- `MonitorHandler.handle`（:478-557）与 `ModifyHandler.handle`（:188-204）在事件线程上**只登记即返回**，无 IO 无等待（CT-03 的 MockHandler 是唯一例外）。
- `DelayScheduler`：全局池关闭门闩（:99, 178-197）、`drainAbandonedDelayTasks`（:155-170）异常隔离、拒绝即立即执行（fail-safe 不丢 resume）；`PerContextEngine.close` 先取队列再关池；`delayScheduler()` 已关时抛异常阻止向死池提交。
- `RouteContextState.PENDING_TASKS` 注册/注销严格配对（`whenComplete`）+ context 关闭 cancel；`cancelPendingTasksFor` / `removeContextFromAllRegistries` 双重兜底。
- 弱引用键到位：`ApiCaptureContext.BY_CONTEXT` WeakHashMap + `ownerContextRef` WeakReference；`ApiCaptureManager.contextStores` WeakHashMap。
- `ApiCallAwaiter` / `ResponseStore.waitForApi`：注册 → 重扫 → `get` → `finally` 注销，超时亦注销，无失去唤醒（lost-wakeup）。
- 持久化：全参数化 SQL、事务 + commit/rollback + `autoCommit` 复位、连接 try-with-resources；DB 刷入为专属单 daemon 线程与通用池隔离；背压丢最旧且可观测。
- 全 route 主干**无 `Thread.sleep`**（ArchUnit 约束）。
- 事件线程**之外**的最大阻塞（`observationExecutor` 上 `consumeBody` ≈ 5.2s + body 预算 + 2s ≈ 12s）属工作线程，可接受。

**web / core 正向**
- `TestContextHolder` / `ThreadLocalTestContext`：`ConcurrentHashMap` + 真 `computeIfAbsent` → 消除 get-then-put 竞态；`resetForCurrentThread()` 同时清 `ThreadContextRegistry` 条目与 `INHERIT_SNAPSHOT` → 线程池复用无残留。
- `LazyInit`：双检 + volatile 发布 + 失败原因缓存 + `Error` 不包装 → 语义正确。
- `ConfigSource.resolvers()` 标准 DCL；`RouteLifecycleRegistry` 正确 DCL。
- `ConcurrencyGate`：`compute` 内取用 + `holds++`、`computeIfPresent` 对称释放、条目随最后持有者移除、`HELD_BY_THREAD` 每线程持有栈 + `remove()`、默认 fail-closed。
- `PageObjectFactory`：`putIfAbsent` 竞争发布（避免持锁回调外代码）；元素**不缓存 `Locator`**，每次经 `page.getPage()` 触发存活校验 → 消除 Locator use-after-close。
- `ConcurrentContextExecutor` 并发模式下按任务关 Browser 的 **Browser 键恒为 `threadId:configId`**（无共享模式），有 `BrowserInstanceKeyInvariantTest` 固化。
- 下载：同名去重 `Files.createFile(CREATE_NEW)` 原子占位 + 失败回滚；`saveAs` 卸载到 `AsyncPool`，不阻塞连接读线程。
- `ElementDiagnosticsCollector`：曾经的**无界 `newCachedThreadPool` 已修为**固定 8 线程 + `CallerRunsPolicy` + 登记关闭（历史 B-3 已闭环）。
- `PageFrameShadow.switchToFrameAndWait`：`AtomicReference.compareAndSet` + `CountDownLatch` + finally 解绑。
- `PageElement.defaultTimeoutSec()`（:547-549）`ceil + max(1,·)` 是**正确**换算（CT-10 是 `PageElementList` 未同步，不是这个类的问题）。

**reporting / api**
- 报告生成是**独立 JVM 单线程**（`exec-maven-plugin`），无并发写；`SummaryResultReporter` 用 `ConcurrentLinkedQueue` + `AtomicBoolean`；全部 IO try-with-resources。
- 报告已**不再 fail-closed**：片段失败降级可见占位、整模板失败降级最小报告、Sink 逐个隔离、外层 catch 不抛。
- API：connect/socket 超时 30s、重试 3 次/1000ms、退避用 `LockSupport.parkNanos`、非幂等不重试；`ApiTestContext` 前后双清。

## 11. 一句话总结

框架的**并发设计意图是一流的**（依赖倒置、SPI、ArchUnit 门禁、有界队列、全 daemon、统一 ShutdownCoordinator、弱键隔离、`computeIfPresent` 原子闸门），但**"异常路径 / 超时路径 / 关闭路径"这三条并发缺陷的唯一藏身处仍未系统收口**：3 处 FATAL 全部落在异常与超时分支上（半初始化不回收、事件线程同步 fetch、守卫自身竞态），而 `hs_err` 的 native OOM 已经用"本进程只吃 337M 却把机器逼死"的方式，把资源泄漏的后果摆在了台面上。

**行动建议**：先做 P0 四项（其中 P0-4「套件级资源回收断言」最值得优先——它把"疑似泄漏"变成"可复现的红色测试"，是后续所有泄漏类修复的度量基准），再放量 `-Pparallel`。
