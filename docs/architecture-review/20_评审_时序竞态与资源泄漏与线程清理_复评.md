## 1. 结论摘要

**并发专项综合评级：3.2 / 5**（设计意图 4.3，异常/超时/关闭三条路径的落实 2.3，**门禁有效性 1.5**）
较 doc 19 的 3.4 略降，原因不是代码变差，而是本轮的**门禁有效性**结论更差：框架里已有的并发回归测试（`test-automation` 下 12 个 `*ConcurrencyTest`）因模块脱离 reactor 而**从未在 CI 执行**；`build.yml` 的 `e2e` job 转正后依然空转。

| 维度 | 结论 |
|---|---|
| **时序竞态** | 有，且**根锚点不可靠**（CT2-03）。另有跨线程使用非线程安全 Playwright 对象的新路径（CT2-02） |
| **资源泄漏** | 有，**确定性泄漏** 3 处未修（CT2-05 / CT2-12 / CT2-02），另新增 codegen 静态 Map 无界增长（CT2-09） |
| **线程未及时清理** | 框架自建线程**全部 daemon**（不会挡 JVM 退出），但存在**池关闭不可恢复**与**任务静默丢弃/永久阻塞**（CT2-07 / CT2-17） |
| **门禁有效性** | **最弱环节**。E2E 与全部 IT、并发回归测试在当前 CI 下均不执行（CT2-01） |

**FATAL 3 项 / CRITICAL 4 项 / HIGH 9 项**，其中 **3 项 FATAL 全部经本人回读源码确认**。

### CT2-03（FATAL｜根锚点竞态）线程归属守卫自身不是线程安全的

```java
// PageContextState.java:214-227
private void assertOwningThread() {
    Thread current = Thread.currentThread();
    Thread owner = this.ownerThread;     // 读
    if (owner == null) {                 // 判
        this.ownerThread = current;      // 写 —— 三步非原子
        return;
    }
    if (owner != current) { throw new IllegalStateException(...); }
}
```

`volatile`（`:216` 字段）只保证**可见性**，不保证"读-判-写"原子。守卫的**唯一竞态窗口恰好是"实例首次被使用"**，而非"已确立归属之后"。

**这直接解释了为什么"测试绿"不能证明安全**——请看框架自己的用例：

```java
// test-automation/.../BasePageThreadOwnershipConcurrencyTest.java:60-73
BasePage bp = new BasePage() {};
bp.getPage();                          // 先在主线程【确立归属】
ExecutorService ex = Executors.newSingleThreadExecutor();
Future<Throwable> fut = ex.submit(() -> bp.getPage() ...);  // 再从另一线程访问
assertTrue(thrown instanceof IllegalStateException);        // 断言被正确拒绝
```

该测试覆盖的是"**归属已确立后**的跨线程访问"——这正是代码**能正确拒绝**的路径；
而**"两线程同时首次访问"**——唯一会漏的路径——**没有任何用例覆盖**。**测试的存在反而制造了虚假信心。**

**爆炸半径**：`PageContextState` 是并行安全的**唯一根锚点**。根锚点被穿透后：`BasePage` 的真实 `Page` 被两线程共享；叠加 `SerenityRecorder.serenityTestData` 为**实例级 `HashMap`**（非线程安全）→ 多线程并发 `put` 可致链表损坏/死循环。且守卫覆盖不全：`PageLifecycleCoordinator` 多行直读写 `bp.page`/`bp.context`，`getPageRaw()`（`:205`）/`getContextRaw()`（`:217`）直接返回字段，**跨线程后果是"静默操作到另一个线程的 Page"，不是明确异常**。

**修法**：`ownerThread` 改 `AtomicReference<Thread>`，用 `compareAndExchange(null, current)`；若返回值非 `current` 则失败。一句话修复，语义完全等价且无性能代价。
**验收**：新增"**两线程同时首次访问同一 `BasePage`**"用例（`CountDownLatch` 对齐起点 + `CyclicBarrier` 同时冲刺，重复 N 轮），断言**恰有一线程成功、另一线程抛 `IllegalStateException`**。以现有实现该用例应能稳定复现失败——**这就是修复前的红色基线**。
**连带**：为 `getPageRaw/getContextRaw` 与 `PageLifecycleCoordinator` 补齐守卫，或把 raw 访问限定为包内并加 ArchUnit 规则。

## 10. 一句话结论

**代码骨架仍是一流的，缺陷也仍是"老地方"——异常路径、超时路径、关闭路径。**
但本轮最重要的发现不是又多了几个泄漏，而是：**上一轮列出的每一条亲验缺陷都还在，而框架自己的 14 个并发回归测试从来没有被 CI 执行过。**
所以真正的 P0 不是"再修一个 bug"，而是 **P0-1：把门禁重新接到被测物上**，再加 **P0-2：资源回收守恒断言**。
这两件事做完，"疑似泄漏"才会变成可复现的红色测试，后面每一条修复才有度量、才不会回潮。
