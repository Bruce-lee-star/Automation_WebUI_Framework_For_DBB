### N-04 【CRITICAL】恒真判据：`String.equals(Map)`

`pw-codegen/.../RolePickerPanelController.java:709`：
```java

```
`curOrigin` 是 `String`，而 `LAST_PICK_ORIGIN` 是 **`Map<Page,String>`**（`RolePickerSessionState.java:38`）→ `String.equals(Map)` **恒为 false** → `originChanged` 在 `curOrigin` 非空时**恒为 true**。


**后果**：所有**同源**导航（含 SPA hash 变化、整页跳转）都被判为"跨域"，走 `else` 分支的**强制 `start()` 全量重注入**。而 `:712-718` 的注释正是为修复"跳转到新页面后元素成倍增加"而写的，它明确警告"反复重注入 + 反复合并"会导致**已拾元素成倍累积**。→ **该缺陷使一个已修复的 bug 复发。**

### N-05 【CRITICAL】"写失败仍清空"——静默数据丢失（假绿方向）

`pw-reports/.../common/reporting/SummaryReportGenerator.java:471-515`：

- `:468`（类文档）明确承诺：**"write 全成功后才统一 clear"**；
- 实现：`:489-496` 逐 sink 独立 try-catch，`sink.write()` 抛异常时**仅 `logger.warn`**；
- 随后 `:504-511` **无条件对全部 sink 执行 `clear()`**，与 `totalOwners > 0` 无关、与 write 是否成功无关。

→ **write 失败的 sink 的内存记录被丢弃且从未落盘**，报告侧显示"无监控失败"。这是与 N-04 同类但更危险的**假绿方向**缺陷：它不是崩溃，而是让"有失败"变成"没有失败"。

**建议修法**：`clear()` 仅对 `write()` 成功的 sink 执行（把成功集合记录下来），失败者保留以便重试并在报告中标记。

| 位置 | 代码 | 问题 |

## 7. 结论

**三个问题的答案仍然是"会"——但性质变了。**

- **时序竞态**：唯一的根锚点（线程归属守卫）**已原子化**，并有 200 轮屏障式用例守护。残留竞态集中在 codegen 面板（锁外读可变字段）与 Context 重建路径。**新增一处恒真判据（N-04）会使已修复的"元素成倍累积"复发。**
- **资源泄漏**：池 / JDBC / 流 / 单次泄漏点**已大面积收口**。剩余最大风险是"**泄漏不可观测**"（N-06）——`hs_err` 的 native OOM（JVM 外内存耗尽）至今没有归因手段。
- **线程未及时清理**：机制的**完备性**已显著提升（daemon、`ShutdownCoordinator` 登记、延迟任务排空、单向门可恢复）。问题从"没清理"变成"**清理失败没有声音**"。

**一句话总结本轮**：**上一轮的整改质量很高，但"让整改生效"的最后一米断在 CI 接线层**——`build` job 因一个 Windows-only 可执行名和一个不存在的插件而恒红，导致新写的反假绿 Gate 从未运行；同时唯一的分层门禁在模块改名中静默消失，而新建的文档引用门禁因正则不匹配输入而空转。**框架的"最后一米"问题没有消失，它从生产代码搬到了门禁自身。**

**下一步唯一值得先做的事**：P0-1（三行配置修复）。它是**唯一一个改完就能让 11 个真实 IT 与全部并发回归用例进入 CI 的动作**，也是后续所有修复的度量基准。

综合评级 **3.6 / 5**（设计意图 4.4，代码层落实 3.8，**门禁有效性 2.2**）。
