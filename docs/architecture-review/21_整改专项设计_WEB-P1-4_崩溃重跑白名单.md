# WEB-P1-4 整改专项设计：收窄崩溃重跑白名单

- **任务**：收窄崩溃重跑白名单（移除异常类名模糊匹配，重跑事件在 Serenity 报告显式标注）
- **来源**：`02_web模块评审.md` 问题 W-15（中）；`11_整改计划.md` 任务 `WEB-P1-4`
- **状态**：✅ 已落地（2026-09-10）
- **验收**：① 元素超时 / 断言失败**不触发**重跑；② 重跑事件在 Serenity 报告可见
- **工时**：2d

---

## 1. 背景与问题

金融级测试体系中，"自动重试"必须有严格白名单（仅限明确崩溃信号），不能用异常类名模糊匹配，否则会：
- 让真实产品缺陷被"重跑一次就好"掩盖（**假绿**）；
- 测试结果的**假绿**比"测试挂了"更危险——后者阻止发布，前者让缺陷流入生产。

### 1.1 原实现缺陷（`BrowserCrashGuard.isCrash`，整改前）

```java
public static boolean isCrash(Throwable t) {
    Throwable cur = t;
    while (cur != null) {
        String className = cur.getClass().getName().toLowerCase(Locale.ROOT);
        if (className.contains("playwrightexception")) {   // ❌ 按类名模糊匹配
            return true;
        }
        String msg = cur.getMessage();
        if (msg != null) {
            String m = msg.toLowerCase(Locale.ROOT);
            for (String sig : CRASH_SIGNATURES) {
                if (m.contains(sig)) return true;
            }
        }
        cur = cur.getCause();
    }
    return false;
}
```

**核心问题**：`PlaywrightException` 同时承载**崩溃**与**元素超时 / 断言失败**等正常业务失败（`TimeoutError` 是其子类）。按类名一律判为崩溃，会使：
- 元素超时（`TimeoutError: Timeout 30000ms exceeded`）→ 误判崩溃 → 自动重跑；
- 页面断言失败（包在 `PlaywrightException` 中）→ 误判崩溃 → 自动重跑；
- 即"重跑一次就好"掩盖真实缺陷，正是 W-15 警告的假绿根源。

### 1.2 信号列表歧义

`CRASH_SIGNATURES` 含两项会被正常流程触发的歧义信号：
- `"execution context was destroyed"`：正常 **SPA 导航竞态**也抛此消息（"Execution context was destroyed, most likely because of a navigation"），误判崩溃；
- `"browser process"`：与**启动期**消息（"Waiting for the browser process to start"）子串重叠，误判崩溃。

### 1.3 报告不可见

原重跑仅在 `ConcurrentContextExecutor.executeOne` 打 `LOGGER.warn`，**未写入 Serenity 报告**。即便最终成功，排障人员也无法从报告看出"该任务曾因崩溃被自动重跑一次"。

---

## 2. 设计目标

1. **仅明确崩溃信号触发重跑**：移除类名模糊匹配，`isCrash` 只基于消息特征匹配白名单。
2. **保持句柄损坏恢复能力**：`__adopt__` / `previewUpdated` 这类 Chromium 句柄注册表损坏仍需触发强制重建重跑。
3. **重跑事件报告可见**：在 Serenity HTML 报告中显式标注，且不在工作线程触碰事件总线（守桥接原则 9.3）。

---

## 3. 方案

### 3.1 收窄 `isCrash` 白名单（`BrowserCrashGuard`）

**移除类名模糊匹配**，仅按消息特征判定：

```java
public static boolean isCrash(Throwable t) {
    Throwable cur = t;
    while (cur != null) {
        String msg = cur.getMessage();
        if (msg != null) {
            String m = msg.toLowerCase(Locale.ROOT);
            for (String sig : CRASH_SIGNATURES) {
                if (m.contains(sig)) return true;
            }
        }
        cur = cur.getCause();
    }
    return false;
}
```

**收窄 `CRASH_SIGNATURES`**（移除歧义项、补 Playwright 真实崩溃消息）：

| 信号 | 含义 | 处置 |
|---|---|---|
| `target crashed` | Playwright 页面/目标崩溃（真实消息形如 "Target crashed"） | 新增 |
| `browser has been closed` | 共享 Browser 被关闭 | 保留 |
| `browser is closed` | Browser 关闭 | 保留 |
| `target page, context or browser has been closed` | 目标/上下文/浏览器关闭（明确崩溃） | 保留 |
| `target closed` | 目标关闭（崩溃常见消息） | 保留 |
| `connection closed` | 浏览器/管道连接断开 | 保留 |
| `connection prematurely closed` | 连接提前关闭 | 保留 |
| `playwright has been closed` | Playwright 关闭 | 保留 |
| `browser disconnected` | 进程断开 | 保留 |
| `browser crashed` | Browser 崩溃 | 保留 |
| ~~`execution context was destroyed`~~ | 正常导航竞态也抛 → 误判 | **移除** |
| ~~`browser process`~~ | 与启动消息重叠 → 误判 | **移除** |

> 元素超时（`TimeoutError`）、断言失败、业务校验失败均不含以上任何信号，故**不再触发重跑**。

### 3.2 恢复门槛纳入句柄损坏（`ConcurrentContextExecutor`）

原 `shouldAttemptRecovery` 仅调 `isCrash`，移除类名匹配后会漏判 `__adopt__`（`PlaywrightException` 子类、无崩溃信号文本）。修正为**崩溃信号或句柄损坏二者任一**：

```java
private static <T> boolean shouldAttemptRecovery(ContextTaskResult<T> r) {
    return BrowserCrashGuard.isEnabled()
            && r.getFailure() != null
            && (BrowserCrashGuard.isCrash(r.getFailure())
                || BrowserCrashGuard.isHandleCorruption(r.getFailure()));
}
```

`executeOne` 仍按 `isHandleCorruption` 路由到**强制重建**（`recoverForced`）或断开型恢复（`recover`），行为不变。

### 3.3 重跑事件报告标注（验收 ②）

**数据携带**：`ContextTaskResult` 新增三个不可变字段（工厂方法默认 `false/null/null`，不影响既有调用）：

- `boolean replayed` —— 是否因崩溃/句柄损坏触发过自动重跑；
- `String recoveryType` —— `"crash"`（断开型恢复）或 `"handle-corruption"`（强制重建）；
- `String firstFailureMessage` —— 触发重跑的首次失败诊断（类名 + 消息）。

新增静态工厂 `ContextTaskResult.replayed(base, recoveryType, firstFailureMessage)`，在 `executeOne` 重跑路径回填：

```java
if (recovered) {
    ContextTaskResult<T> replayedResult = runOnce(task);
    return ContextTaskResult.replayed(replayedResult, type, firstMsg);
}
```

**报告标注**：`SerenityBusBridge.recordCrashRecoveryIfAny(results)` 在**编排线程**（`runAll` 调用方）遍历 `isReplayed()` 的结果，写一条报告数据：

```java
Serenity.recordReportData()
        .withTitle("BROWSER CRASH RECOVERY / 浏览器崩溃恢复重跑")
        .andContents("Task '" + r.getTaskName() + "' was auto-replayed once after "
                + type + " (bounded to 1). First failure: " + firstMsg);
```

- 与 `StepFailureAggregator` 同款 API（`net.serenitybdd.core.Serenity.recordReportData()`）；
- 整段 `try/catch(Throwable)` 包裹，非 Serenity 环境（如离线单测）安全降级，仅记调试日志，不影响调用方断言；
- `runAll` 在返回前调用本方法，**工作线程从不触碰 Serenity 事件总线**（守桥接原则 9.3）；仅 `runAll` 的调用方（编排线程）标注。

## 4. 企业级约束对齐

- **线程安全**：`BrowserCrashGuard` 的恢复动作为 `volatile` 静态 seam，单测可注入；`REBUILD_LOCK` 进程级单飞保证并发崩溃仅首个真正重建（既有不变）。
- **可观测性**：`ContextTaskResult` 携带 `firstFailureMessage` 供排障；报告标注标题固定、内容含任务名/类型/首次失败，报告可读性强。
- **行为零回归**：正常业务失败零重跑；句柄损坏恢复路径不变；重跑严格有界一次（`MAX_REPLAY=1`）。

## 5. 验证

### 5.1 单测（`BrowserCrashGuardTest`，16 例全绿）

- `detectsCrashByMessageSignature`：明确崩溃信号（`target crashed`/`browser crashed`/`browser disconnected` 等）识别为真；
- `playwrightExceptionWithoutCrashSignatureIsNotCrash`：**`TimeoutError` 与无信号的 `PlaywrightException` 不触发重跑**（验收 ① 直接证据）；
- `playwrightExceptionWithCrashSignatureIsStillCrash`：含崩溃信号的 `PlaywrightException` 仍识别；
- `doesNotFlagNormalFailuresAsCrash`：断言失败 / 业务异常 / `Execution context was destroyed` 导航竞态 / `TimeoutError` 均不触发重跑；
- `crashTaskIsReplayedOnceAndSucceeds`：断言 `r.isReplayed()==true` + `r.getRecoveryType()=="crash"`（验收 ② 数据前提）；
- `handleCorruptionTaskIsReplayedAfterForcedRecovery` / `handleCorruptionRoutesToForcedRecoveryNotPlainRecovery`：句柄损坏仍走强制重建重跑（不受类名移除影响）。
