# WEB-P1-7 配置体系收敛（双 FrameworkConfig 改名与口径统一）

> 状态：✅ 已落地（2026-09-10）
> 验收：① 无同名类；② 两侧配置项均有 key/默认/描述三元组
> 全护盾：528 例，0 失败（仅 1 例 `SessionManagerSharedConcurrencyTest` 时序偶发，隔离重跑全绿、与本改动无关）

---

## 1. 背景与动机

`framework-web` 与 `framework-api` 是两个独立模块，各自持有一个名为 `FrameworkConfig` 的类：

- `web.config.FrameworkConfig`：约 42KB 的 **枚举**，每个常量已自带 `key / defaultValue / description` 三元组，并提供 `getValue()` / `getBooleanValue()` / `getIntValue()` / `getLongValue()` / `getKey()` / `getDefaultValue()` / `getDescription()`。
- `api.config.FrameworkConfig`：约 13.8KB 的 **class**，通过 `ConfigProvider.getConfig()`（Typesafe Config）读取，约 30 个静态 getter，绝大多数是 `config().hasPath("字面量键") ? config().getX("字面量键") : 字面量默认值` 形态，**缺少统一的 key/默认/描述 元数据**。

两个同名类造成：
1. 命名冲突（`api` 的 `FrameworkConfig` javadoc 自承「⚠️ 同名类消歧」）；
2. 口径不一致：web 侧是「枚举三元组」、api 侧是「散落字面量」，配置项不可被统一审计/文档化。

api 模块已依赖 `framework-core`，因此可在 core 抽出共享的 `ConfigKey` 元数据规范。

---

## 2. 现状数据

| 维度 | web `FrameworkConfig` | api `FrameworkConfig` |
|---|---|---|
| 形态 | enum（~42KB） | class（~13.8KB） |
| 三元组 | ✅ 已自带 key/默认/描述 | ❌ 缺（字面量散落） |
| 解析 | `ConfigSource.resolve` | `ConfigProvider.getConfig()`（Typesafe） |
| 引用文件数 | ~29（web main + 1 web test） | ~6（5 api main + 枚举自身） |

补充事实：
- `api` 已存在 `domain.enums.ConfigKeys` 枚举，但它只承载 **endpoint 结构键名**（toString 返回 key，**无默认/描述**），且 key 与 `FrameworkConfig` 不完全一致（`api.base.uri` vs `api.base.uri.default`），属不同抽象，不合并。
- `web.config.FrameworkConfigManager` 是独立的管理类（缓存/覆盖），不含 `FrameworkConfig` 三元组，改名时以负向先行断言 `(?!Manager)` 保护，保持原名。

---

## 3. 目标与验收

- **验收① 无同名类**：web 枚举与 api 类改名后类名互异。
- **验收② 两侧配置项均有 key/默认/描述三元组**：web 枚举常量经 `configKey()` 暴露；api 类配置项抽为 `ConfigKey` 常量。

---

## 4. 方案

### 4.1 共享 `ConfigKey` 元数据规范（core）

新增 `core.common.config.ConfigKey`（`public record`，不可变）：

```java
public record ConfigKey(String key, String defaultValue, String description) {
    public ConfigKey {
        if (key == null || key.isBlank()) throw new IllegalArgumentException("ConfigKey.key must not be blank");
        if (description == null || description.isBlank()) throw new IllegalArgumentException("ConfigKey.description must not be blank for key=" + key);
        if (defaultValue == null) defaultValue = "";
    }
}
```

构造期强校验 `key` 与 `description` 非空，保证每个配置项「可定位、可解读」。仅承载元数据，不含解析/解密逻辑（解析仍由各域负责，保行为零回归）。

### 4.2 改名消歧

- `web.config.FrameworkConfig`（enum）→ **`WebFrameworkConfig`**，`git mv` 同步文件名。
- `api.config.FrameworkConfig`（class）→ **`ApiFrameworkConfig`**，`git mv` 同步文件名。
- 改名按模块隔离（`web` / `api` 目录分别扫描），用正则 `FrameworkConfig(?!Manager)` 保护 `FrameworkConfigManager` 不被误改。
- 跨模块 javadoc 中指向兄弟类的 FQN（如 `web.config.FrameworkConfig` / `api.config.FrameworkConfig`）在改名后单独修正为 `WebFrameworkConfig` / `ApiFrameworkConfig`。

### 4.3 API 侧三元组落地

`ApiFrameworkConfig` 每个配置项抽为 `public static final ConfigKey X` 常量（key/默认/描述），getter 改为：

```java
public static int getConnectionTimeout() {
    return config().hasPath(HTTP_CONNECTION_TIMEOUT.key())
        ? config().getInt(HTTP_CONNECTION_TIMEOUT.key())
        : Integer.parseInt(HTTP_CONNECTION_TIMEOUT.defaultValue());
}
```

- **解析语义逐字等价**：`key` 与原字面量一致，`defaultValue` 与原字面量默认值一致（已逐条核对）。
- **布尔型**保留原语义 `config().hasPath(k) && config().getBoolean(k)`（键缺失即 false，与原实现一致）。
- 多键回退方法（`getSocketTimeout` 兼容 `http.socket.timeout.value` / `.fallback`；`getDefaultBaseUri` 兼容 `api.base-uri.default`）保留历史回退链，主键改用 `ConfigKey`。
- 动态消息解析（`getErrorMessage` / `getEndpointNullErrorMessage`）无固定键，按既有逻辑保留。
- 通用透传方法（`getConfig` / `hasPath` / `getString(path)` / `getInt(path)` / `getBoolean(path)`）保持不变。

### 4.4 Web 侧口径对齐

web 枚举常量本身已含 key/默认/描述，仅新增暴露点（不改动既有常量/方法）：

```java
public ConfigKey configKey() { return new ConfigKey(key, defaultValue, description); }

public static List<ConfigKey> allConfigKeys() {
    List<ConfigKey> keys = new ArrayList<>();
    for (WebFrameworkConfig c : values()) keys.add(c.configKey());
    return keys;
}
```

## 7. 全护盾结果

`mvn -o -pl test-automation -am test`：528 例，**527 通过 / 1 失败**。

失败项 `SessionManagerSharedConcurrencyTest.concurrentExpiredEviction_idempotentAndNoException`：
- 经核查该测试**零引用** `FrameworkConfig` / `WebFrameworkConfig` / `ApiFrameworkConfig` / `ConfigSource` / `getValue`，与配置改动无关；
- 属时序/竞态断言（期望 ~202ms 内超时），在 528 例全并行重载下偶发抖动；
- **隔离重跑 3 例全绿、BUILD SUCCESS** → 确认是预存时序偶发，非本改动回归。

覆盖相关：`ConcurrencyGateTest`(web) 4+ 例、`ConfigUnificationTest` 3 例均绿。

## 8. 关键坑（务必牢记）

1. **预置名二次替换污染**：若先以目标名（如 `ApiFrameworkConfig`）写入文件再跑「`FrameworkConfig`→`ApiFrameworkConfig`」脚本，`ApiFrameworkConfig` 内含 `FrameworkConfig` 子串会**再被替换一次**生成 `ApiApiFrameworkConfig`。
   正确顺序：先跑改名脚本（作用于原名 `FrameworkConfig`），再单独修正少数手工预置处的历史说明；或整文件重写覆盖。
2. **`(?!Manager)` 负向先行断言**：`FrameworkConfigManager` 含 `FrameworkConfig` 子串，盲目全局替换会误改为 `WebFrameworkConfigManager`；必须用 lookahead 保护。
3. **跨模块 javadoc FQN**：两个枚举文件的 javadoc 互相引用兄弟类，改名脚本会把对方 FQN 也误改（web 文件里 `api.config.FrameworkConfig`→`api.config.WebFrameworkConfig` 等），须改名后手动修正为 `ApiFrameworkConfig` / `WebFrameworkConfig`。
4. **PowerShell 引号**：`-Dtest=a,b` 与 `-Dsurefire.failIfNoSpecifiedTests=false` 必须整体加引号，否则逗号/`=` 被 PowerShell 拆成独立参数。
5. **UTF8 无 BOM**：批量改名脚本用 `[System.IO.File]::ReadAllBytes` + `UTF8Encoding($false)` 写回，避免 BOM 污染 java 文件。
