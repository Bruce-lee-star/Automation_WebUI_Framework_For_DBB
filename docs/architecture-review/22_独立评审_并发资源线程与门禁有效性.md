## 三、FATAL（1 项）

### A-01 构建脚本硬编码作者本机绝对路径 → `build` job 恒红 → `e2e` 永不执行

**证据（原文）**
- `tools/picker_merge_test.js:22-26`
  ```js
  const ROOT = 'd:/IdeaProject/Automation_WebUI_Framework_For_DBB';
  const RES = path.join(ROOT, 'pw-core/src/main/resources/scan/js');
  function readRes(f) { return fs.readFileSync(path.join(RES, f), 'utf8'); }   // 无 try/catch
  ```
- `pw-core/pom.xml:81-94`：该脚本被绑在 **`validate` 阶段**（`exec-maven-plugin:exec`），且 `<skip>${picker.js.validate.skip}</skip>`，属性默认 `false`（`pw-core/pom.xml:19`）。
- `.github/workflows/build.yml:46`：`mvn -B verify -Psca -DskipITs -Dcve.gate.skip=true` —— **未设置** `-Dpicker.js.validate.skip`。

**为何是真问题**
在 `ubuntu-latest` 上 `path.join('d:/…', 'pw-core/…')` 是**相对路径**，`fs.readFileSync` 相对 `process.cwd()`（exec 默认取 `${project.basedir}`）解析 → `ENOENT`。`readRes` 无捕获，异常自 `test()` 逃逸到顶层 → node 退出码 1 → `exec:exec` 失败 → **`pw-core` 在 `validate` 阶段即让 `mvn verify` 失败**。
反向佐证了它的"环境耦合"性质：本机（正是 `d:/IdeaProject/…`）能跑通，所以**门禁只在作者这台机器上是绿的**——任何同事 clone 到别的盘符/目录，本地构建同样必红。

**爆炸半径**
`build` job 恒红 → `e2e` job 声明 `needs: build`（`build.yml:111`）→ **真实浏览器 E2E、全部 IT、以及新写的「反假绿 Gate」(`build.yml:173-203`) 结构性永不执行**。与「参数改对了但路径没被执行」是同一失败模式，只是这次的凶手是硬编码路径。

**修法（4 行）**
`const ROOT = path.resolve(__dirname, '..');`（或由 pom 传 `${project.basedir}/..`），并给 `readRes` 加存在性检查 + 明确报错信息。

**重要对照：旧的那个 build 阻断点已修，所以 A-01 现在是唯一的**
本仓库历史上 `build` job 曾因 "`<executable>powershell</executable>` 在 Linux 上不存在"而恒红。本次实测确认**该问题已解决**：
- `pom.xml:106` `<cve.gate.executable>pwsh</cve.gate.executable>`（Linux 默认），`pom.xml:733-740` 的 `os-windows` profile 在 Windows 上覆盖为 `powershell` —— **OS 自适应，写法正确**。
- 同一轮整改里，上传 step 也已从 `if-no-files-found: error` 降级为 `warn` 并换成了真实存在的产物路径（`build.yml:78-93`）。
⇒ 也就是说：**这一轮修复把"解释器"和"上传产物"两个阻断点都摘掉了，但 `build` 仍然会红，因为 A-01 这个新的阻断点就在同一个 job 的更前面（`validate` 阶段）。** 修复的历史成效是真实的，只是"最后一米"再次转移到了另一个位置。

## 四、CRITICAL（3 项）

### A-02 `doc-drift` workflow 引用**不存在的 GitHub Action** → 该门禁整条从未运行

**证据**
- `.github/workflows/doc-drift-check.yml:29-33`
  ```yaml
  - uses: actions/checkout@v4
  - uses: microsoft/setup-powershell@v1
  - name: Verify README versions match pom
    shell: pwsh
    run: pwsh tools/check-doc-drift.ps1
  ```
- **实测**：访问 `https://github.com/microsoft/setup-powershell` 返回 GitHub 官方 **"Page not found"** → 该 action 不存在。
- 官方文档亦指出 `ubuntu-latest` **预装** PowerShell 7（`/opt/microsoft/powershell/7/pwsh`），本步骤本身多余。

**为何是真问题**
`uses` 无法解析时该 step 直接失败并终止 job → `doc-drift` job **恒红**，`pwsh tools/check-doc-drift.ps1` 一行代码都没跑过。该脚本承载**两类门禁**：① README 版本号与 `pom.xml` 属性一致；② `CT2-23` 新增的根 pom `<module>` 拓扑校验（`check-doc-drift.ps1:108-116`，能抓住模块改名/目录缺失）。二者**全部空转**。

**爆炸半径**
模块改名、版本号漂移、文档失准这类"改了名字没改引用"的问题，**没有任何门禁可抓**——而这类问题在这个仓库的历史上恰恰反复发生。

**修法**：删除 `microsoft/setup-powershell@v1` 一行（`shell: pwsh` + runner 预装已足够）；或改用真实存在的 action。

> 注：`check-doc-drift.sh`（POSIX 镜像）在仓库内存在，但 CI 只调用了 `.ps1`。

### A-03 幻影守卫：注释声称的守护测试**不存在**，且跳过逻辑正以它为理由

**证据**
- `pw-codegen/.../scan/RolePickerConstants.java:47`：`//  契约由 RolePickerModeContractTest 以「JS 实读字面量」方式守护。`
- `pw-codegen/.../scan/RolePickerScripts.java:22`：`… and {@code RolePickerScriptsJsValidationTest} which runs {@code node --check} on every composed constant).`
- `tools/validate_picker_js.js:22-30`：
  ```js
  // Fragments composed at runtime are NOT standalone-valid; their composed output is syntax-checked by
  // RolePickerScriptsJsValidationTest (node --check on START_SCRIPT / PANEL_SCRIPT). They are skipped here to
  // avoid false failures ...
  const isFragment = f => /-head\.js$/.test(f) || /-tail\.js$/.test(f)
    || /-core-[ab]\.js$/.test(f) || /-core-b[12]\.js$/.test(f);
  ```
- **实测**：全仓检索 `RolePickerModeContractTest|RolePickerScriptsJsValidationTest` 仅命中上述 **3 处注释**，**无任何类定义**。`pw-codegen/src/test/java/**` 实际只有 4 个测试类：`RolePickerStaticStateCleanupTest`、`RolePickerPanelControllerOriginTest`、`RoleElementPickerEvalLockTest`、`RolePickerQuietAndSessionCapTest`。

**为何是真问题**
被 `isFragment` 跳过的，正是**运行期真正注入浏览器的组合体**：`START_SCRIPT = picker-core-a + b1 + b2`、`PANEL_SCRIPT = panel-core-a + b`。跳过它们的唯一理由（"另有测试会校验组合体"）**指向一个不存在的类**。后果有两层：
1. **组合脚本零语法校验** —— `validate_picker_js.js` 只校验各片段之外的单文件；而每个片段都是**半个 IIFE**，单独看本就非法（这正是它要跳过的原因）。所以"两个片段各自合法、拼起来非法"这类错误会一路进入浏览器才炸。
2. **Java↔JS 命令契约零守卫** —— `CMD_*` / `MODE_*` / `STATE_*` 常量与 `scan/js/*.js` 里函数名字面量的一致性没有任何测试（历史反复出现的 `scan_page` vs `scanPage` 类问题），注释却宣称有。

**修法**：二者任选其一——补回这两个测试类（组合体用 `node --check`、命令名用实读 JS 字面量比对），或删除虚假注释并让 `isFragment` 的跳过有真实依据。

### A-04 单飞「夺取」后未重新登记守卫 → **N 重**真实登录（不是注释所说的双重）

**证据（`SessionManager.java:701-743`）**
```java
LoginGuard candidate = new LoginGuard();
LoginGuard existing = loginGuards.putIfAbsent(sessionKey, candidate);
if (existing == null) { MY_LOGIN_GUARD.set(candidate); return null; }   // 706-711 唯一 leader 登记点
boolean completed = existing.await(SINGLE_FLIGHT_TIMEOUT_MS);
if (completed) return existing;
if (existing.await(SINGLE_FLIGHT_GRACE_MS)) return existing;            // 宽限
if (hasUsableSession(sessionKey)) return existing;                     // 复用
existing.markSuperseded();
loginGuards.remove(sessionKey, existing);                              // 736 摘除守卫，但不再登记
long takeovers = SINGLE_FLIGHT_TAKEOVERS.incrementAndGet();
LOGGER.warn("... taking over as leader (potential twofold login; takeovers={})");
return null;                                                          // 743 本线程成为 leader
```

**为何是真问题**
1. **夺取路径无配对登记**：`putIfAbsent`（706）是唯一登记点，夺取分支（735-743）摘掉守卫后**没有**补登。守卫被摘后 map 中该 key 为空 → 后续任何线程 `putIfAbsent` 都会成功、**也**成为 leader。
2. **同时刻集体夺取**：所有 follower 等的是**同一个** `existing` 守卫，会在同一时间窗内陆续超时；`loginGuards.remove(key, existing)` 只有第一个成功，**但返回值被忽略** —— 其余线程照样 `return null` 成为 leader。于是同一 `sessionKey` 上可同时出现 **N 个真实登录**，而非注释所承认的 2 个。
3. **`completeLoginGuard:766` 按 key 摘除**：`LoginGuard guard = loginGuards.remove(sessionKey);` 不分身份 —— 任意线程调用（含非 leader 的 `saveSession`）都会摘掉**别人的**守卫并 `complete(success)`，把 follower 从等待中错误唤醒。

**爆炸半径**：同一账号并发真实登录 → SSO 单会话策略互踢 → **随机 401 / 登录失败**，且失败点离根因（登录协调）很远，极难归因。触发前提是"登录慢于 `singleFlightTimeoutMs + grace`"——在 SIT 网络抖动或并行度较高时并不罕见。

**修法**：夺取成功后 `loginGuards.putIfAbsent(sessionKey, candidate)` 并 `MY_LOGIN_GUARD.set(candidate)`；`completeLoginGuard` 改 `loginGuards.remove(sessionKey, mine)` 且仅当 `mine != null` 才 `complete`。

## 五、HIGH（7 项）

### A-05 `ModifyHandler` 在**工作线程**调用页面级 `page.waitForResponse`（框架自我违反线程契约）

- 契约出处（框架自己的话）：`PageContextState.java:228-233` —— *"Playwright Page/Context/Locator are not thread-safe; use a separate BasePage instance per thread/scenario."*
- 违反点：`ModifyHandler.java:195` 把整条观测链投到 `observeExecutor`（`modify-observe-N` 工作线程）→ `:666-701` 在该线程内 `page.waitForResponse(...)`，超时上限 `Math.min(30000, ROUTE_FETCH_TIMEOUT_MS)`（`:679-680`）。
- **对照证明这是"漏改"而非"设计取舍"**：同类问题在 `ElementDiagnosticsCollector.java:62-77` 已按同一契约修好——`CompletableFuture.supplyAsync(this::collect, Runnable::run)`，注释明写 *"诊断逻辑持有场景线程创建的 Locator/Page（非线程安全），绝不可交给诊断线程池执行"*。`ModifyHandler` 是同一形态的残留。
- 半径：跨线程驱动 Playwright 对象 → `Object doesn't exist` / 连接污染 / 偶发失败；单次最长占住工作线程 30s（4 线程池）。
- 修法：对齐 `MonitorHandler` 的本地轮询范式（`Request#existingResponse()`），彻底摆脱页面级 `waitForResponse`。

### A-06 防重标记 add/remove **不对称** → 重叠 pattern 下可二次 dispatch

- `Dispatcher.java:103-112`：`if (!bucket.add(route)) { LOGGER.warn("... skipping ..."); return; }` —— 本线程**未**加入成功，**未**置 `asyncHandled[0]=true`。
- `Dispatcher.java:295-303`：`finally { if (!asyncHandled[0]) { unmarkDispatched(route); } }` —— 于是**无条件移除**了这条 route 的标记，而该标记是**另一个 handler** 加的。
- 同文件 81-84 的注释明确了正确意图：*"避免提前清除 pending route 的门控导致重叠 pattern 二次 dispatch 失防"* —— 实现恰好违反了自己的注释。
- 触发前提：同一 context 内**≥3 个重叠 pattern** 命中同一 URL（≥2 时只是提前解防，尚不产生二次处理）。实际不失真：如"通用 `**/api/*` mock + 具体 `**/api/user` modify + 全局 monitor"即构成 3 个。
- 后果：第三个 handler 可再次 `bucket.add(route)` 成功 → 同一 Route 二次 `fulfill/resume` → Playwright 报 *"Route is already handled"* / `times` 双重递减 / MONITOR 记录翻倍。
- 修法：用 `final boolean[] marked={false}` 记录本分支是否 add 成功，`finally` 仅对 `marked[0] && !asyncHandled[0]` 释放。

### A-07 `StoppedCapabilityManager`：`ConcurrentHashMap` 里装**非线程安全**的 `EnumSet` 并**无锁迭代**

- `StoppedCapabilityManager.java:60-68`
  ```java
  Map<String, Set<RouteHandleType>> byPattern = RouteContextState.STOPPED_CAPS.computeIfAbsent(ctx, k -> new ConcurrentHashMap<>());
  Set<RouteHandleType> set = byPattern.computeIfAbsent(normalized, k -> EnumSet.noneOf(RouteHandleType.class));
  if (cap == null) set.addAll(EnumSet.allOf(RouteHandleType.class)); else set.add(cap);   // 锁外写非线程安全 value
  ```
- `:90-100`：`applyStoppedCapabilities` 里 `for (RouteHandleType t : stopped) rule.stopCapability(t);` —— **锁外迭代**同一 `EnumSet`。
- 问题：CHM 只保护 Map 结构，**不保护 value**。`RegularEnumSet` 用单个 `long` 位图，并发 `add` 会丢位；迭代期间并发 `add` 会抛 `ConcurrentModificationException`。
- 后果（fail-open 方向）：迭代被打断的异常若被 dispatch 兜底吞掉 → 整链 force-resume → **该停的能力没停 / 该改的没改**，用例表现为"规则像没生效"。
- 修法：value 直接换 `ConcurrentHashMap.newKeySet()`，或套用同仓 `RouteRule.stopCapability` 已验证的 volatile + 写时复制范式。

### A-08 `AxeCoreListener`：启用标志**套件作用域写、场景作用域读** → 无障碍扫描静默全空

- 写点：`AxeCoreListener.java:172` `testSuiteStarted(...) { initializeIfNeeded(); }` → `:61` `TestContextHolder.get().set(AXE_ENABLED_KEY, enabled);` —— 套件启动时**无场景绑定**，写入的是**线程**上下文。
- 读点：`:38-40` `isAxeEnabled() = TestContextHolder.get().get(AXE_ENABLED_KEY)`，被 `:88-94 scanCurrentPage` 使用 —— **场景内**调用，而 `TestContextHolder.get()`（`TestContextHolder.java:64-69`）**优先返回用例级上下文**。
- 二次写被短路：`:50-51` `if (!AxeCoreScanner.isInitialized())` —— 初始化成功后（`:75`），后续任何场景的 `initializeIfNeeded()` **直接返回**，不再补写标志。
- 结论链：套件级把 `true` 写进线程上下文 → 场景内读的是**另一个**（场景）上下文 → 恒 `null` → `false` → 每个场景 `return null` 且只留 debug 级日志 → 套件收尾 `testSuiteFinished` 在线程上下文读到 `true` → 生成**空报告**。**无任何 error/warn**。
- 成因判断：这是 `T3-1` 把 `static ThreadLocal` 迁入 `TestContext` 后的**回归**——同一 key 在迁移前两边都是线程作用域，迁移后读侧变成"场景优先"。同类风险适用于**所有**"套件级写、场景级读"的 key。
- 修法：套件级标志不要放在场景上下文中（改回静态字段 / 独立 ProcessContext），或在读侧做"场景→线程"回退。

### A-09 `PageObjectFactory.clearAll()` 在常规路径是**空操作**，却被**逐场景**调用

- 存放点：`PageObjectFactory.java:189-196` `threadInstances()` → `TestContextHolder.get().computeIfAbsent(THREAD_INSTANCES_KEY, …)` → 场景内**存进场景上下文**。
- 清理点：`:533-549`
  ```java
  TestContextHolder.forEachThreadContext(ctx -> { … ctx.remove(THREAD_INSTANCES_KEY); });   // 只遍历【线程】上下文
  ```
  → `TestContextHolder.forEachThreadContext` 只走 `ThreadContextRegistry.forEachContext`（`TestContextHolder.java:174-176`）。**场景上下文不在遍历范围内**。
- 即 `:523-531` 注释宣称的 *"三种作用域都必须全局清理…现改为遍历所有已登记线程的上下文清理"* —— **清的是那个在场景内根本没被使用的键**。名实不符。
- 调用频率很高：`PlaywrightSerenityBridge.java:355-356` 与 `:380` —— **每个 scenario 起始**都会调用（`restartStrategy=scenario` 分支）；`feature` 分支在重建时调用。
- 并发副作用：`clearAll` 会移除**其它 worker 线程**的 `THREAD_INSTANCES_KEY`。所幸这些键在场景内不被使用（见上），故**并发危害有限**；真实问题是 (1) 常规清理目标为 0，(2) 一旦有非场景绑定的路径使用该键，即成为跨线程摘键竞态。
- 修法：清理目标改为"当前场景上下文 + 线程上下文的**并集**"；并在并发模式下把清理范围收窄到当前线程。

### A-10 `ScenarioTraceRecorder`：单线程导出可被**永久卡死** → trace 静默丢失

- `ScenarioTraceRecorder.java:81-90`：`TRACE_EXECUTOR = Executors.newSingleThreadExecutor("pw-context-trace")`（daemon，已登记 `ShutdownCoordinator`）。
- `:205-228`
  ```java
  task = CompletableFuture.runAsync(() -> context.tracing().stopChunk(...), TRACE_EXECUTOR);
  task.get(exportTimeoutSeconds(), TimeUnit.SECONDS);
  ...
  } catch (TimeoutException toe) { task.cancel(true); deletePartialFile(file, "timeout(...)"); }
  ```
- 问题：`stopChunk` 是**阻塞式 Playwright 同步调用**，`cancel(true)` 只置中断位，**无法中断** native/管道等待。该池**只有一个线程**：一旦卡住，后续所有 `stopChunk` 排队 → 每个都超时 → 每个都 `deletePartialFile`。
- 后果：trace 全部静默丢弃（仅每文件一条 WARN），**且卡死的线程永久占用**（daemon，不影响 JVM 退出，但 trace 能力彻底失效）。诊断证据在"最需要它的失败场景"下最可能缺失。
- 修法：改为"超时后放弃该 thread 并重建池"，或限制单次导出并显式暴露"trace 导出已降级"到报告。

### A-11 Checkstyle 门禁**不覆盖 `pw-codegen`**，且根配置 `failOnViolation=false`

- `pw-codegen/pom.xml:22`：`<checkstyle.skip>true</checkstyle.skip>` —— 9442 行（含大量空 catch）完全在 Checkstyle 之外。
- 根 `pom.xml:584`：`<failOnViolation>false</failOnViolation>` —— 违规本身不卡构建。
- 唯一兜底是 CI 的"只减不增"计数门禁（`build.yml:56-68`），而它统计的是 `target/checkstyle-result.xml` 里的 `<error>` **总数**；被 skip 的模块**根本不产出报告**，其违规对总数贡献为 0 → 该模块的违规增长**结构性不可见**。
- 修法：移除 `checkstyle.skip`，或至少让基线门禁覆盖被 skip 的模块（否则"只减不增"名存实亡）。
