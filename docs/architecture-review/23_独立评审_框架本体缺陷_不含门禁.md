## 三、CRITICAL（1 项）

### B-01 单飞「夺取」后**不重新登记守卫** → 门控对后续线程完全失效；唯一兜底的跨进程锁自身可 fail-open

**【本轮亲验】证据（`SessionManager.java`）**

```java
// :735-743  夺取分支
existing.markSuperseded();
loginGuards.remove(sessionKey, existing);          // 736 摘除守卫
long takeovers = SINGLE_FLIGHT_TAKEOVERS.incrementAndGet();
LOGGER.warn("... taking over as leader (potential twofold login ...)");
return null;                                       // 743 本线程成为 leader —— 但【没有】putIfAbsent 补登
```

```java
// :766  释放路径按 key 摘除，不辨身份
LoginGuard guard = loginGuards.remove(sessionKey);
if (guard != null) { guard.complete(success); }
```

**为何是真问题（三层）**

1. **夺取后门控消失**：`loginGuards` 中该 key 被摘且**无人补登**。此后任何线程调用 `acquireOrAwait` 都会 `putIfAbsent` 成功 → **直接成为 leader**。即一次超时夺取之后，该 sessionKey 的单飞保护**永久失效**，直到某次 `saveSession` 才重建。
2. **同一时刻集体夺取**：所有 follower 等待的是**同一个** `existing` 守卫，会在同一时间窗内陆续超时。`remove(sessionKey, existing)` 只有第一个返回 `true`，**返回值被忽略** → 其余线程照样走到 `return null`。
3. **`completeLoginGuard` 会摘掉别人的守卫**：`:766` 按 key 摘除，非 leader 线程（如失败兜底路径 `:869`、`:835`）调用时会摘掉**他人**的守卫并 `complete(success)`，把 follower 以错误的结果唤醒。

**关于「唯一兜底」的重要精确化（本轮修正，避免夸大）**
`guard == null` 之后还有一层 `CrossJvmLoginLock.acquireForLogin(...)`（`:624-626`）用 **OS 文件锁**串行化，故「N 个线程同时真实登录」在很大程度上被它挡住 —— 只有持有文件锁者才是 leader。
**但该文件锁自身有三条 fail-open `return true`**（锁目录不可建 / 等锁超时 / 被中断，虽已计 `DEGRADED_ACQUISITIONS` + ERROR）。**一旦跨进程锁降级，B-01 的三层缺陷同时生效 ⇒ N 个并发真实登录**。
⇒ 结论：**B-01 不是"必然 N 重登录"，而是"单飞保护可被一次超时永久击穿，且剩余唯一兜底会 fail-open"**。

**爆炸半径**：同一账号并发真实登录 → SSO 单会话策略互踢 → **随机 401 / 登录失败**，且失败点（某次点击 401）离根因（登录协调）极远，极难归因。触发前提是"登录慢于 `singleFlightTimeoutMs + grace`"，SIT 抖动或并行度较高时并不罕见。

**修法（约 6 行）**
```java
existing.markSuperseded();
if (loginGuards.remove(sessionKey, existing)) {          // 只有真正摘成功者才接任
    loginGuards.putIfAbsent(sessionKey, candidate);       // 补登，恢复门控
    MY_LOGIN_GUARD.set(candidate);
    return null;
}
// 抢不到：说明已有别人接任，退回复用判定
return hasUsableSession(sessionKey) ? existing : null;
```
并把 `:766` 改为 `loginGuards.remove(sessionKey, mine)`（`mine = MY_LOGIN_GUARD.get()`），仅当 `mine != null` 才 `complete`。

## 四、HIGH（2 项）

### B-02 防重标记 **add / remove 不对称** → 重叠 pattern 下同一 Route 被二次 dispatch

**【本轮亲验】证据（`Dispatcher.java`）**

```java
// :89   try {          ← try 块起点在【防重门控之前】
// :103-111
if (bucket != null) {
    if (!bucket.add(route)) {          // 本线程【未】加入成功（是别人加的）
        LOGGER.warn("Route already handled by another pattern, skipping ...");
        return;                        // ← 直接返回，但会执行 finally
    }
}
...
// :295-303
} finally {
    if (!asyncHandled[0]) { unmarkDispatched(route); }   // ← 无条件移除【别人】的标记
}
```

**为何是真问题**：判重失败的线程**没有**取得标记，却在 `finally` 里把该 Route 的标记移除 —— 抹掉的是**异步 handler（A）刚加的、且仍需保留**的门控（A 已置 `asyncHandled[0]=true`，其生命周期由 `executeHandlerScheduled` 的 finally 负责释放）。
**同文件 `:81-83` 的注释写明了正确意图**：*"若此处提前清除，会导致重叠 pattern 二次 dispatch 失防"* —— 实现恰好违反了自己的注释。

**触发条件（精确）**：同一 context 内 **≥3 个重叠 pattern** 命中同一 URL。
- 2 个时：B 提前解防，只是让 A 失去保护，尚不产生二次处理；
- 3 个时：C 的 `bucket.add(route)` **会成功** → 同一 Route 二次 `fulfill/resume`。
配置并不失真：例如「通用 `**/api/*` MONITOR + 具体 `**/api/user` MODIFY + 全局 MOCK」。

**后果**：Playwright 报 *"Route is already handled"*；`times` 双重递减；MONITOR 记录翻倍（观测数据失真）。**因需 ≥3 个重叠项才显形，单元测试极难暴露。**

**修法**：用局部布尔记录本次是否真的 add 成功，`finally` 仅对 `marked[0] && !asyncHandled[0]` 释放。

### B-03 `ResponseStore` **持锁执行调用方传入的谓词与 CompletableFuture 后续动作**

**【本轮亲验】证据**

```java
// ResponseStore.java:105-151
synchronized (apiCallLock) {
    ... 入库、淘汰、notifyAll ...
    apiCallAwaiter.deliver(call);        // :150  ← 在【apiCallLock 内】调用
}
```
```java
// ApiCallAwaiter.java:48-62
void deliver(CapturedApiCall call) {
    synchronized (lock) {                       // 嵌套第二把锁
        ...
        if (predicate != null && predicate.test(call)) {   // :56 执行【调用方传入】的谓词
            it.remove();
            entry.getKey().complete(call);                 // :58 同步触发 CF 后续动作
        }
    }
}
```

**为何是真问题**
1. `deliver` 的 Javadoc 自己写着 *"谓词必须廉价（仅字段比对），绝不可阻塞"* —— 这是**文档契约，无任何强制**。谓词由调用方（业务步骤）提供，慢谓词或含 IO 的谓词完全可能出现。
2. 更关键的是 `:58` 的 `complete(call)`：`CompletableFuture` 的**同步后续动作会在完成线程上立即执行**，即**在同时持有 `apiCallLock` + `lock` 两把锁的情况下执行业务回调**。
3. 后果是**阻塞放大**：一次慢谓词/慢回调，会阻塞**全部** `storeApiCall`（含事件线程侧路径）与所有等待者投递 → 采集整体停滞 → 级联超时。
4. 锁顺序：本路径为 `apiCallLock → lock`；`register/unregister/reset` 只取 `lock`，**未发现反向取锁**，故判定为**阻塞放大**而非死锁（不夸大）。

**修法**：把 `deliver` 移出 `apiCallLock`（在 `synchronized` 块结束后调用），或改为把命中的 future 收集到局部变量、出锁后再 `complete`。
