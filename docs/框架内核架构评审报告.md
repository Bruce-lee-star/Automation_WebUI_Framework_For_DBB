## 一、架构总评

**分层合理性：8 / 10　　框架综合成熟度：7 / 10**

**亮点**

- 依赖方向严格单向收敛且无环：`core ← reporting / api ← web ← codegen`，`route` 独立依赖 `core + reporting`。
- `core` 仅 3 个外部依赖（HikariCP / logback / jackson-databind），且**零** JUnit / TestNG / Cucumber / Serenity 引用 —— 运行器解耦达到教科书水准。
- 两个原本会成环的边被正确打破：web→route 由 `core` 的 `RouteLifecycle` SPI 反转；codegen→web 由 `ServiceLoader` 运行时注入，且 codegen 缺席时 web 行为零回归。
- 有 ArchUnit 架构门禁（`ReportingRouteDecouplingArchTest` / `CodegenDecouplingArchTest`）、Enforcer `requireUpperBoundDeps`、Checkstyle、SpotBugs、JaCoCo、OSV-Scanner CVE 基线，治理设施完整。

**扣分项**

- `web` 一家占 43%（24,911 行），已成为"第二个 core"，内部二层分层（lifecycle / listener / page / config / cloud / concurrent）尚不足以抵消体量失衡。
- `core` 依赖 HikariCP（JDBC 连接池），一个 Web/API 框架底座引入持久化依赖，边界偏脏。
- 框架自测覆盖率极低：四个模块单测为 0，约 31,225 行（54%）无自测保护。
- `docs/` 为空、无 README。

## 二、逐维度评审

### 1. 核心抽象与封装 —— 8 / 10

**设计亮点**

- `PlaywrightManager` 是**纯门面**：类内无可变静态字段，状态根收敛到 `PlaywrightRuntimeState`，六个角色接口（browserStartup / browserRegistry / browserRestart / browserCleanup / contextRegistry / pageRegistry）经 `PlaywrightRuntime` 组合根可整体替换；`RuntimeProvider` seam 支持 `setProvider()` 换实现（WEB-P0-2 DI seam），是真正的多态而非 switch。
- 线程隔离键 `threadId:configId` 明确保证 Browser 实例不跨线程共享；共享 Browser 模式为显式 opt-in，且 `SHARED_BROWSER_MODE` 设计为 JVM 级不可变 —— 注释准确指出"运行期翻转会产生无法回收的孤儿实例"。
- API 侧 `AbstractRestJob.execute()` 模板方法把 5 个 `Rest*Job` 的逐字重复消除，子类只提供 HTTP 动作；SSL 策略由无条件 `useRelaxedHTTPSValidation()` 修正为默认严格 + 显式开关（安全基线修复）。
- 等待机制治理到位：全框架 `Thread.sleep` 仅 1 处（`PlaywrightInitializer:530`），route 明确禁用 sleep 改用调度器，`AsyncPool` 用 `LockSupport.parkNanos`。上层无散落 sleep。
- 并发由框架自建：`ConcurrentScenarioExecutor` + `ConcurrencyGate`（SSO 身份感知互斥），业务零并发代码。

**潜在风险**

- 全局静态门面 + `TestContextHolder` 服务定位：`PlaywrightManager` 全 `static`，测试必须全局 reset；`SHARED_BROWSER_MODE` 类加载期固化，若此时 Serenity 配置尚未就绪，开关会被永久固化。
- `PageWaits.retry()` / `retryWithValidation()` 是 `waitForTimeout(固定间隔)` 轮询，非条件等待；且中间轮次异常被静默吞掉，只在最后一次抛出 —— **丢失了首次失败的根因栈**。
- `BasePage`(479) / `PageElement`(967) 仍是 web 侧胖基类；API 侧是 `BaseStep`，两域无统一 Action / Assertion 抽象。

**重构建议**

- `retry` 改为条件驱动（Playwright `Locator` 原生 auto-wait 已具备重试语义，直接委托 `waitFor` + 自定义 condition），并把首次异常作为 suppressed 挂到最终异常上。
- 借 `PlaywrightRuntime.instance()` 已就绪的组合根，把 `PlaywrightManager` 的 static 调用逐步迁为实例调用，`static` 仅保留兼容壳。

### 2. 配置与环境管理 —— 6 / 10

**设计亮点**

- `ConfigSource` 四级优先级：系统属性 → 环境变量（点/连字符转下划线大写，与 Serenity 映射一致）→ SPI `ConfigResolver` → 默认值。core 不依赖任何配置框架，靠 `ServiceLoader` 实现依赖倒置。
- 透明解密：`ENC(<base64>)` + 裸 base64 自动识别，AES-256-GCM，主密钥三路解析（env `CONFIG_MASTER_KEY` → sysprop → `~/.dbb_automation_master_key`），解密失败保留原串、不中断启动。
- `ConfigKey` 记录（key / default / description）统一两域元数据并构造期强校验，具备"配置自描述"能力（可直接生成配置总表）。
- `SensitiveDataSanitizer`（927 行）质量突出：JSON 深度遍历（Jackson 树，超深节点整棵掩码而非放行）、XML/SOAP 元素+属性双通道、form-urlencoded、Bearer/JWT、URL userinfo、URLEncode 内层 JSON（BrowserStack caps 场景），并有 Luhn/IBAN/HKID/中国身份证/手机号/护照/港澳通行证/USCC 等值级识别器。

**潜在风险**

- **无框架级多环境 Profile 抽象**。`dev/test/pre-prod` 切换完全外包给 Serenity 的 `environment` 与 Typesafe Config 的 `application.conf`；core 层没有"环境"概念。后果：框架无法判定、校验、打印"当前跑在哪个环境"，配错环境只能等业务侧暴露（这是维度 3 之后最大的结构性缺口，也是致命缺陷 1 的成因）。
- `looksLikeCiphertext` 判定过宽：任何合法 base64 且解码长度 > 12 字节的**明文**都会被尝试解密。长度 ≥20 且字符集合法的普通配置值会被误判为密文，主密钥存在时解密失败仅打 ERROR 并保留原串（安全但噪音大）；若将来把"解密失败即 fail-fast"打开，会直接误伤正常配置。
- `ConfigSource.resolve` 每次都走 `getProperty` + `getenv` + SPI 遍历 + 解密，**无缓存**；`WebFrameworkConfig` 有 1514 行配置项，热路径高频调用有开销（`getenv` 尤甚）。
- 敏感信息只做了"读取时解密"，未做"输出时强制脱敏"的框架级拦截 —— 依赖调用方自觉调用 `sanitize*`。

**重构建议**

- 引入 `EnvironmentProfile` 抽象：core 提供环境解析 + 环境白名单 + 启动期打印 `当前环境=xxx`，未知环境 fail-fast。
- 密文判定收紧为仅 `ENC(...)` 显式标记；裸 base64 需显式开关才启用。
- `ConfigSource` 增加启动后冻结的不可变快照缓存。
- 增加 logback 脱敏 Converter，把脱敏从"调用方自觉"变成"出口强制"。

### 3. 日志与断言基础设施 —— 5 / 10

**设计亮点**

- `VerboseLogging` 统一按 `serenity.logging` 在运行时提升级别，避免代码里散落 `isDebugEnabled` 判断。
- 截图体系策略化：`PlaywrightScreenshotManager` + `FailureScreenshotHandler` + `ScreenshotStrategy`。
- 脱敏能力（同上）为日志安全提供了基础。

**潜在风险**

- **`logback.xml` 只有 ConsoleAppender，无任何 FileAppender / RollingFileAppender**。框架级不具备"日志落盘"能力：CI 构建结束只剩控制台输出，跨 job 取证困难；HTTP 请求/响应落盘也不存在 —— 现状是靠 `Entity.isApiRequestResponseLogsEnabled()` 逐个 opt-in 打到控制台。
- **无软断言**：全仓 grep `softAssert` 为零。断言能力三套并存（`ElementException` 抛异常 / Hamcrest / RestAssured `ValidatableResponse`），框架未提供统一断言门面，也没有 collect-then-report 的软断言机制。
- 无结构化（JSON）日志、无 MDC —— scenario / feature / thread 维度无法串联，并行执行时日志是大杂烩。
- `AsyncPool` 的监控指标（`getStatusSnapshot`）没有周期性落盘或对外暴露通道。

**重构建议**

- logback 增加 `RollingFileAppender`，按 scenario / 线程分文件；核心路径注入 MDC（scenarioId / threadId / env）。
- 提供 `FrameworkAssertions`（硬断言）+ `SoftAssertions`（收集失败后在 scenario 结束统一 assertAll 并写入 Serenity 报告）。
- 提供 HTTP 请求/响应统一落盘（经 `sanitize` 后写入 `target/logs/api`）。

### 4. 扩展机制与 Hook 设计 —— 6 / 10

**设计亮点**

- `ListenerRegistry` 双通道发现：`ServiceLoader` 主路径 + 包扫描回退；单类加载/实例化失败只 WARN 跳过（W-16 根治"单点失败全盘失败"）。
- `ThucydidesStepsListenerAdapter`（757 行）是把 Serenity `StepEventBus` 适配到框架侧的隔离层；`PlaywrightListener` / `StepFailureAggregator` / `AxeCoreListener` 均为适配产物。
- `codegen` 经 `RoleCodegenBridge` SPI 注入 web，缺 classpath 时行为不变；`RouteLifecycle` SPI 让 route 与 web 解耦。
- 报告模块有 ArchUnit 解耦测试守护。

**潜在风险**

- **`FrameworkListener` 是零方法标记接口**。框架没有定义自己的生命周期契约（onBeforeScenario / onAfterStep / onFailure…），"Hook"实际等价于直接注册到 Serenity 的 `StepEventBus`。一旦更换运行器（JUnit5 / TestNG），所有 listener 需重写 —— 适配层隔离了"报告引擎"，却没有隔离"运行器事件模型"。
- `ListenerRegistry` 仍保留 `Class.forName` 全量包扫描（含 jar 扫描）作为回退，classpath 大时启动开销与不确定性并存。
- 报告层直接依赖 5 个 serenity 构件，`SerenityReporter` / `SummaryReportGenerator` 直接以 Serenity 模型为输入 —— **没有框架自己的 TestResult 模型**，换报告引擎需重写。
- Allure / Excel 未引入，无适配层可供评审。

**重构建议**

- 把 `FrameworkListener` 提升为带默认方法的生命周期接口（beforeScenario / afterScenario / beforeStep / afterStep / onFailure），由官方 Adapter 桥接到 Serenity 总线；业务只实现框架接口。
- 定义框架自有 `TestResult` / `StepResult` 模型，让 `SerenityReporter` 退化为"模型 → Serenity"的单向适配器。

### 5. 资源管理与生命周期 —— 8 / 10

**设计亮点**

- `ShutdownCoordinator` 单一 JVM 钩子 + order 排序（100 API monitor flush → 200 route → 300 monitor → 400 async → 500 session IO → 600 diagnostics → 900 framework core），单任务异常不影响其余，幂等且可 `reset()`。
- `AsyncPool`：有界队列（200）、`DiscardOldest` 拒绝策略并计数、超时调度器、per-context 调度器集中登记与关闭、队列/线程/pending-timeout 三级阈值告警；monitor 回调队列满时**丢弃而非回退调用方线程**（注释准确指出回退会阻塞 Playwright 事件线程导致整轮卡死）。
- `FrameworkCore.handleException` 明确**禁止**调用 `cleanupAll()`（会关掉所有并发场景的浏览器），只做本 scenario 清理 —— 这是踩过坑才写得出的约束。
- `BrowserCrashGuard` / `BrowserRestart` / `rebuildSharedBrowser` 提供崩溃自愈；共享模式下重启降级为"仅重建本线程 Context"。
- `TestContextHolder` 用 `WeakHashMap<Thread, TestContext>` 防泄漏，并提供 `capture/restore` 跨线程传播与 `resetForCurrentThread`。

**潜在风险**

- **`HikariConfigFactory.createDataSource` 返回的 `HikariDataSource` 未登记到任何框架级资源注册表或关闭钩子**。core 提供了工厂却不定义"谁负责关"的契约；调用方忘记 `close()` 即连接泄漏，JVM 退出亦无兜底。
- `ThreadContextRegistry` 明确"不注册 ShutdownCoordinator"（注释说明：core→common 反向依赖会破坏 G1 架构门禁）—— 这是被架构约束逼出来的正确性取舍，说明 `ShutdownCoordinator` 放错了模块层次。
- `ThreadLocalTestContext.computeIfAbsent` 是 get-then-put，非原子。
- route 模块 38 处吞异常（六模块最高）叠加 0 单测，异常静默风险最大。

**重构建议**

- `HikariConfigFactory` 改为"创建即登记"（返回前注册到 `ShutdownCoordinator`），或返回必须由调用方 try-with-resources 管理的对象。
- 将 `ShutdownCoordinator` 下沉，消除"架构门禁 vs 正确性"的冲突。
- `computeIfAbsent` 改用 `ConcurrentHashMap.computeIfAbsent`。

### 6. 依赖管理与解耦 —— 9 / 10

**设计亮点**

- core 仅 3 个外部依赖，零运行器耦合；route 同样零运行器引用（0 个文件引用 junit/testng/cucumber/serenity）。
- 根 POM：`dependencyManagement` 统一钉版本 + ENG-P0-2 依赖下沉（各模块显式声明真实用到的依赖）+ Enforcer `requireUpperBoundDeps` + `banDuplicatePomDependencyVersions`。
- 门禁齐全：Checkstyle、SpotBugs（基线冻结）、JaCoCo、OSV-Scanner CVE 基线、ArchUnit 分层与解耦测试。
- codegen 可选化设计（不在 classpath 时 web 行为不变）。
- 依赖注释质量极高，几乎每处"为什么钉这个版本"都有根因说明（如 byte-buddy 1.17.8 覆盖 serenity 父 POM 的 1.14.18）。

**潜在风险**

- core 依赖 HikariCP：底座引入 JDBC 连接池，且 core 里唯一的持久化工厂实际只服务 route。
- web 显式钉 guava 33.5.0-jre（注释承认是为满足 `requireUpperBoundDeps`），与 serenity 父 POM 的 33.2.1 打架 —— 上游版本仍在漂移。
- SpotBugs 抑制基线：web 73 条 / route 34 条 / api 11 条，债务被"冻结"而非消除；当前仅产出基线，`check` 尚未成为硬门禁。
- serenity 4.2.0 是为适配 jackson 2.18.3 而降级的结果（CORE-P0-1），存在被动跟随上游的脆弱性。

**重构建议**

- 把 `HikariConfigFactory` 移到 route（唯一重度使用者）或独立 persistence 模块，让 core 回归"零存储依赖"。
- 给 SpotBugs 基线设定期限（如下季度起新增违规必须为 0），并把 web 的 73 条按包拆分到人。
- 制定 serenity 升级路径与回归验证清单。

## 三、致命缺陷排查（可能导致线上测试环境崩溃或数据污染）

### 缺陷 1（最高危）：route 的 mock / modify 能力无环境保护护栏

`RouteDsl` 提供 `.mock()` / `.modifyRequest()` / `.modifyRequestBody("$.role", "ADMIN")` / `.delay()`，能在浏览器层拦截并**改写真实 HTTP 流量**。全仓在 route 主代码中未发现任何生产/预发环境判定（grep `prod|production|allowlist|whitelist` 零命中），也没有 host 白名单或环境闸门。

风险：一份误提交或误配置的 route 规则跑在 pre-prod / prod-like 环境，会真实改写请求（例如把 `role` 改成 `ADMIN`）或 mock 掉真实响应，造成**数据污染与越权操作**；由于流量外表是"测试流量"，很难被监控发现。

建议：`RouteEngine` / `RouteDsl` 增加环境闸门 —— 仅当 `env ∈ {dev, sit, test}` 且 host 命中白名单时才允许 mock/modify（monitor/delay 可放宽），违反即 fail-fast；规则注册时强制打印 WARN。

### 缺陷 2：HikariDataSource 无框架级关闭契约（连接泄漏 + 意外写库）

`HikariConfigFactory.createDataSource` 直接 `new HikariDataSource` 返回，不登记 `ShutdownCoordinator`。`ApiMonitoringRepository` 自建连接池并按 50 条/2 秒批量 `INSERT route_monitor_record`，进程退出时强制 flush 剩余队列。

风险：同一 JVM 内多次 `init` 或调用方未 `shutdown` 时，会残留多个活跃连接池持续写库；测试结束仍 flush 队列 → **向监控库写入非预期批次**；若该库与业务库同实例，即构成数据污染。

### 缺陷 3：并发场景下的"全量清理"误伤（已注释防范，但无机制约束）

`FrameworkCore.handleException` 明确注释：`cleanupAll()` 会关闭**所有线程**的 Browser/Playwright 实例，并行运行下单个 scenario 的异常会关停其余全部场景。但 `PlaywrightManager.cleanupAll()` 仍是 `public`，任何新同学误调用或未来重构改回，都会导致并行整轮集体失败，且故障现象与根因完全脱节。当前仅靠注释约束。

建议：降级为包级私有，或标记 framework-internal 并加运行时断言（仅在非并发、套件结束时允许）。

### 缺陷 4：吞异常导致断言失效 → 假绿

`MonitorHandler` 的 fail-fast 是"置标志位"而非中断；叠加 route 38 处 / web 22 处 `catch (ignored)`，若标志位未在正确时机被检查（并发场景、context 提前关闭等），失败的 API 断言会被静默吞掉 —— 测试显示通过但实际接口已异常。

这是**测试有效性**层面的致命缺陷，比崩溃更危险，因为它提供错误的安全感。

### 缺陷 5：共享 Browser 开关的类加载期固化

`SHARED_BROWSER_MODE` 是 `public static final`，在类加载时经 `PlaywrightRuntime.instance().browserRegistry.resolveSharedBrowserMode()` 解析。若此时 Serenity 配置尚未就绪，开关会被永久固化；一旦与实际并发模型不符，会产生"按 threadId 创建、按 shared 键清理"的孤儿实例或误关闭。

### 缺陷 6：启动路径的 `Thread.sleep(1000)`

`PlaywrightInitializer:530` 是框架内唯一真实 `Thread.sleep`，位于浏览器启动路径。多 Browser 并发初始化时会被放大，造成启动串行化。

---

## 四、Top 3 重构优先级

### P1：给 route 的 mock/modify 加环境闸门 + 建立框架自测底线

前者是唯一可能真实污染外部系统与数据的框架级能力，且当前零护栏；后者（core / route 单测从 0 到有）是让其余 5.8 万行代码的任何重构都可控的前提。**没有自测，P2 / P3 的重构都是在黑暗中改**。
交付物：环境闸门 + fail-fast；core 与 route 首批单测 + JaCoCo 阈值入 CI。

### P2：补齐"日志落盘 + 软断言 + 统一断言门面"，并把 HikariDataSource 纳入框架级资源登记

CI 取证、失败定位、断言一致性是日常高频痛点；资源登记是消除连接泄漏与意外写库的最小改动（高杠杆）。
交付物：`RollingFileAppender` + MDC；`FrameworkAssertions` / `SoftAssertions`；HTTP 报文脱敏落盘；数据源创建即登记。

### P3：定义框架自有生命周期 Hook 契约 + TestResult 模型

把零方法的 `FrameworkListener` 提升为带默认方法的生命周期接口，并定义框架自有 `TestResult` / `StepResult`，让 Serenity 侧退化为单向适配器。这是"框架可演进"的分水岭 —— 今天所有 hook 与报告都直接长在 Serenity 上，换运行器/报告引擎的成本被推迟但仍在累积。
同步把 web（24,911 行）按 lifecycle / page / config 二次拆模块，缓解单模块体量失衡。
